# 金标任务评分标准（`qa/goldset/scoring.md`）

> 依据：`docs/architecture-phase4.md` §9.7（P4-20 金标任务集）。
> 适用范围：`qa/goldset/T01.yaml` ~ `T20.yaml` 共 20 条金标任务的交付物评分。
> 本文是**唯一评分口径**。`run.py` 只自动算「无技术暴露」与「结构自检」，
> 其余四维由**人工按本文锚点打分**，`run.py` 负责把人工分按权重合成总表——改本文必须同步改 `run.py` 的 `WEIGHTS` 常量，二者漂移由 `run.py --validate` 拦住。

---

## 1. 五维权重（合计 **100%**）

| # | 维度 | 权重 | 一句话定义 | 谁打 |
| --- | --- | --- | --- | --- |
| D1 | 完整性 | **25%** | 该有的产出是否都给了，需求里的每条约束是否都落到了 | 人工 |
| D2 | 准确性 | **30%** | 给的东西对不对：事实、算法、口径、边界条件有没有错 | 人工 |
| D3 | 可直接使用 | **25%** | 能不能不改就发给对方——贴进仓库、粘进编辑器、打印开会 | 人工 |
| D4 | 无技术暴露 | **10%** | 面向业务人员的文案里有没有内部技术词（项目铁律：技术黑盒化） | **机器自动** |
| D5 | 可核查 | **10%** | 说的每一条能不能被第三方独立验证（来源、链接、可复算数字） | 人工 |

**权重合法性**：25 + 30 + 25 + 10 + 10 = **100**。`run.py --validate` 会断言 `sum(WEIGHTS.values()) == 100`，不等即退出码 4（用例/口径格式错）。

**为什么准确性最高（30%）**：一个「不完整但正确」的产出可以靠追问补齐；一个「完整但错误」的产出会被直接发出去，代价无法回收。
**为什么无技术暴露只占 10%**：它是**一票否决项**（见 §4），不是用来拉开分差的维度——权重小但违反即整条判不合格。

---

## 2. 单维评分锚点（1 / 3 / 5 分）

评分只取 **1 / 3 / 5** 三档（`run.py` 只接受这三个值）。需要更细的表达时，用「3 分 + 备注扣分理由」，不要写 2 或 4——三档制是为了让两个评分人之间的一致性可测。

### D1 完整性（25%）

| 分 | 判定标准 |
| --- | --- |
| **5** | `pass_criteria.completeness` 全部满足；`expected_artifact` 里声明的每一类产出都有实物；需求原文里的每一条约束都能在产物中定位到落点 |
| **3** | 核心产出齐全，但 `pass_criteria.completeness` 中有 1 条未满足（如缺一个用例场景、缺一个段落）；缺的部分不影响主线使用 |
| **1** | 缺 ≥2 条，或缺的是**主线产出**（该给的文件没给、该有的结论没下）；或产物只有目录/提纲没有实体内容 |

### D2 准确性（30%）

| 分 | 判定标准 |
| --- | --- |
| **5** | 事实、数字、口径、边界条件全对；`pass_criteria.accuracy` 全部满足；用输入原文能逐条反查通过；没有「听起来对但没依据」的断言 |
| **3** | 主线正确，但有 1 处非致命错误（措辞把「优先」写成「必备」、日期格式不统一、合计差 1 元的四舍五入问题）；用户自己看一眼能改 |
| **1** | 有 ≥1 处**会被直接采信的错误**：编造数字/案例、把未定当已定、算错合计、把未覆盖说成已覆盖、伪造「已完成」状态 |

### D3 可直接使用（25%）

| 分 | 判定标准 |
| --- | --- |
| **5** | 零改写可用：代码能编译、CSV 能导入、邮件能发送、文档能下发；无占位符残留（除**显式声明**的待填项）；格式与目标载体一致 |
| **3** | 小改可用：需要替换 1-2 处占位、补一个 import、调一下段落顺序；改动量 <5 分钟 |
| **1** | 需要重写：给的是伪代码/片段/带「此处省略」；或格式与目标载体不符（该给 CSV 给了带 Markdown 表格的段落）；或含 3 处以上未声明占位 |

### D4 无技术暴露（10%，**机器自动**）

规则来源：`apps/web/scripts/check-banned-terms.mjs` 的 `TERM_GROUPS`（由 `docs/prd-phase2-increment.md` 第 7 章术语对照表生成）+ `tests/integration/test_grant_and_backlink.py` 的 `FORBIDDEN_TERMS`。`run.py` 用同一份词表扫描产物中**面向用户可见的文本**。

| 分 | 判定标准 |
| --- | --- |
| **5** | 扫描命中 **0** 次 |
| **3** | 命中 1-2 次，且全部落在「技术分析/代码注释」这类**允许区域**（见下）——即产物主体干净，边界擦到 |
| **1** | 命中 ≥1 次落在**用户可见文案**（正文、邮件、JD、稿件、提示语、提交说明）中 |

**允许区域（不算命中）**：

1. 代码标识符与代码注释（`token`、`index`、`segment_count` 作为变量名合法）；
2. `T01`/`T02`/`T04` 的「技术方案」章节中讨论实现时使用的中性词——但**方案摘要**（会被人事/客户看到的那段）仍按用户可见文案计；
3. 引用用户原话（用户自己说了「接口」就允许在原因说明里出现一次）。

**扫描词表（与本项目禁词口径一致，`run.py` 内置同一份）**：

```
模型名 / GPT / Claude / Qwen / DeepSeek / Gemini / 向量 / embedding / RAG / Agent /
召回 / 分块 / 切片 / 索引 / 相似度 / 阈值 / prompt / token / top_k / score / chunk /
segment / milvus
```

> 注意「模型」是**子串**匹配词（`TERM_GROUPS` 里 `kind: sub`），所以「数据模型」「商业模式」也会命中——这是既有门禁的已知行为，评分时按 §4 的**豁免**处理：命中词只出现在「数据模型」「商业模型」等复合词中且语义与 AI 模型无关时，按 **5 分**计并在 `notes` 里写明豁免理由。

### D5 可核查（10%）

| 分 | 判定标准 |
| --- | --- |
| **5** | 每条断言都能被第三方独立验证：有来源（文档名+小节）、有链接、或数字可复算；`pass_criteria.verifiable` 全部满足 |
| **3** | 主体可核查，但 1-2 处只能「信作者」（如「两条意见被采纳」没有会议记录出处），不影响主要结论 |
| **1** | 关键结论无法验证：无来源的标准数字、写成「已完成」但无回执/链接、时间表述为「下周」而无绝对日期 |

## 3. 合成总分与合格线

```
总分 = D1×0.25 + D2×0.30 + D3×0.25 + D4×0.10 + D5×0.10      （满分 5.00）
```

- **合格线 3.5 / 5**。`>= 3.5` 判 `pass`，`< 3.5` 判 `fail`。
- 分档参考（用于报告表述，不参与判定）：

| 总分 | 含义 |
| --- | --- |
| ≥ 4.5 | 可直接交付，无需人工复核 |
| 3.5 ~ 4.4 | 合格，交付前需按备注微调 |
| 2.5 ~ 3.4 | 不合格，退回重做 |
| < 2.5 | 能力不达标，需回到需求/方案层 |

- **加权和必须由 `run.py` 计算**，不允许人工先算好再填。`run.py --recompute` 从原始产物 + 人工分 JSON 重算，结果应逐字节一致（这就是「可复算」的判据）。

---

## 4. 一票否决（无论总分多少，直接判 `fail`）

以下任一成立，该条判 `fail`，且**不得**用其他维度高分把总分拉回 3.5：

| # | 否决项 | 检测方式 | 关联用例 |
| --- | --- | --- | --- |
| V1 | **编造事实**：编造数字、案例、客户名、机构名、单据、已发布回执 | 人工核对 + 产物中数字与输入/知识库逐一比对 | T07 T11 T13 T18 |
| V2 | **伪造完成状态**：未接通就写「已发布/已提交/已发送」 | 人工核对回执字段与执行日志 | T01 T09 T12 |
| V3 | **技术暴露**：用户可见文案中出现任意禁词（D4 = 1 分） | `run.py` 自动扫描 | 全部 20 条 |
| V4 | **越权交付**：用户明确只要拆解却给了代码（T03），或明确要求留空却填了金额（T13） | 人工核对 `must_not_contain` | T03 T13 |

> V3 与权重的关系：D4 占 10%，但一旦落到 1 分即触发 V3 → 整条 `fail`。这不是「加权被无视」，而是**合规项不参与平均**——与项目里「技术黑盒化」的定位一致：它是门槛，不是加分项。

## 5. 评分操作流程

1. 跑一条用例，拿到产物目录：
   ```bash
   python qa/goldset/run.py --case T07 --out results/
   # 产物落在 results/<YYYY-MM-DD>/T07/
   ```
2. `run.py` 自动填 D4（扫描）与结构自检结果，写入 `results/<date>/T07/auto.json`。
3. 人工按 §2 锚点给 **D1/D2/D3/D5 四维**打 1/3/5，写入 `results/<date>/T07/scores.json`：
   ```json
   { "D1": 5, "D2": 3, "D3": 5, "D5": 3, "notes": "D2：日期格式混用 MM-DD 与 YYYY-MM-DD" }
   ```
   **不要写 D4**——它由扫描器算，手填会被 `--recompute` 判格式错（退出码 4）。
4. 复算总表：
   ```bash
   python qa/goldset/run.py --recompute --run-dir results/2026-10-30
   # → results/2026-10-30/summary.csv
   ```
5. 两个评分人独立打完 20 条后，比较总分差异 >0.5 的条目，按 §2 锚点对齐——**锚点文字是仲裁依据**，不是谁资历高听谁的。

## 6. 与 `run.py` 的契约（改本文必须同步改 `run.py`）

| 项 | `run.py` 中的位置 | 漂移时的行为 |
| --- | --- | --- |
| 五维键名 `D1..D5` | `DIMENSIONS` / `DIMENSION_KEYS_BY_CODE` | `--validate` 断言用例 `pass_criteria` 的五个键能映射到 `D1..D5`（中文口径名与 yaml 里的 ASCII 书写名两种都收，同一维重复书写判错） |
| 权重 `25/30/25/10/10` | `WEIGHTS` | `--validate` 断言合计 100 |
| 合格线 `3.5` | `PASS_LINE` | 只影响 `summary.csv` 的 `verdict` 列 |
| 禁词表 | `BANNED_TERMS` + `EXEMPT_COMPOUNDS` | 与 `apps/web/scripts/check-banned-terms.mjs` 的 `TERM_GROUPS` 手动对齐 |
| 允许分数 `{1,3,5}` | `ALLOWED_SCORES` | `--recompute` 遇到 2/4 报错退出 4 |
| **D4 不可人工覆盖** | `AUTO_DIMENSIONS` | `scores.json` 里出现 `D4` 即判格式错退出 4——否则「无技术暴露」这条合规门槛能被手填 5 分绕过去 |
