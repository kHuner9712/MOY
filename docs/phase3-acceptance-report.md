## 七、方法与过程教训（本阶段最重要的产出之一）

这一阶段在"判据本身是否正确"上投入的精力，超过了功能开发。四条通用结论已写入团队规范：

1. **引用任何数字前，先验恒等式**（`covered + missing == total`、`在库 = 应有 − 缺`）。
   本阶段同一错法出现三次（lead、QA、PM 各一次），每次都是"拿一个字段名当它的定义"（`num_partial_branches` 是"部分分支未走的**行数**"，不是未覆盖分支数）。
2. **门槛取整方向必须使门槛不降低**（`≥` 向上、`≤` 向下）；下限必须 ≥ 历史实测值，否则它不是底线而是"允许再退一步"的授权。
3. **门禁要么全绿，要么把所有不满足项一次报全**——只报第一条会把一次修完变成 N 轮往返。
4. **扫描/解析类门禁上线前必须在"已知正确的样本"上跑出 0 误报**：假红会让人去查不存在的缺陷，比漏检更浪费时间。

**六起"幽灵引用"**（`switchable`、`R2-c`、单值无单位、§1.1 草稿、46 条样本、14 道门禁）全部是"讨论层产物被当成既定事实"。对策已固化为：**消息里点名的规则名/行号/数字，必须能在仓库 `grep` 得到；点不出路径就不许当依据。**
