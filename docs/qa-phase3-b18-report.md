## 9. 判据设计三原则（本批沉淀，后续批次复用）

「禁止类」断言要成立，必须同时满足三条，**缺任一条都会给出错误的"通过"**：

| 原则 | 防的是什么 | 反例（本阶段真实出现过） |
| --- | --- | --- |
| **① 场景对**：前置条件单独断言成立 | 在**不该出现的场景**里"通过" | `TC-P3-PL03-11` 若不断言"确实未安装"，实现顺手建了安装行时，三条断言仍全绿，而它把已装当未装——错得更多 |
| **② 副作用真没有**：计数/存在性断言（审计条数、表行数、`version` 不变） | 只断言返回值，放过"报错但已写库" | `PL14` 只断 `16003` 会放过"报错但已写 `plugin_grant`" |
| **③ 不误判合法实现**：判据不得窄于契约允许的实现集合 | 把更安全的实现判成不合格 | 越权读只允许 `403`；实际 `404` 更安全（不暴露存在性） |

> **三层递进（区分"绿了"与"被覆盖"）**：断言**存在**（写了）→ 断言**成立**（绿了）→ 判据**被覆盖**（它测的正是要防的那件事）。
> `test_b2` 是"存在 + 成立、但未覆盖"的典型：PASSED 只证明断言成立，**不证明判据被覆盖**——中间那层最容易被"绿"骗过。

## 10. 台账记法（B19 起强制执行）

**规则：「✅」必须带证据行，否则 ✅ 只是主张。**

| # | 断言 | 结果 | 证据（贴原始行） |
| --- | --- | --- | --- |
| ① | `GET /plugins/installed` 不含该 `plugin_id`（**前置**） | ✅ | `installed.items = []`（该 `plugin_id` 0 命中） |
| ② | 返回 `16003`（非 `16004`/非成功） | ✅ | `{"code":16003,"message":"该插件还没有添加…"}` |
| ③ | `plugin_grant` = **0 行**（`plugin_id + user_id` 双键） | ✅ | `count(*) → 0` |
| ④ | 审计 `plugin.capability_grant` = **0 条** | ✅ | `count(*) → 0` |

理由：**"✅"与"已验证"是同一类主张**。既然已区分「PASSED ≠ 覆盖」，台账若只写 ✅，读者仍只能"相信"不能"复核"；**有证据行的 ✅ 才可被第三方复算**。

### 10.1 断言排序依据（pm 提出，采纳）
一条断言是否排在最前，取决于 **"它红的时候能不能让后面全部作废"**：
- **前置断言**（场景是否成立）天然排第一——它红说明后面验的是错场景；
- **全局不变量**（如「任务状态仍 `completed`」「总行数不变」）紧随其后；
- 具体字段断言最后。

> 反例：`TC-P3-PL03-11` 若把「返回 `16003`」排第一、前置排最后，实现顺手建了安装行时，前三条可能全绿，最后一条才红——**排查者会先怀疑码值，实际错在场景**。

> **缺陷层：`open = 1`**（`P3-B18-04`，**P2**，版本表孤儿行，不影响 `--apply`，到期 `--prune-orphans`）。

两句必须并存：**"交付行为达标"成立**，**"零 open 缺陷"不成立**。把二者合成一句会与台账冲突，而台账是机器引用真源。


### 11.4 定级补充原则：**先确认因果链在代码里存在，再定后果面**
本轮 `P3-B18-04` 差点被判成"迁移失败（P0 级后果）"，因为「版本表残留旧行 → `--apply` 失败」听起来完全合理。
但代码里**没有这条路径**（`build_plan` 只遍历 `available`）。**"听起来合理但不存在"的因果链，是等级定错的主要来源**——它把 P2 说成了 P0 级后果。

> 规则：定级前先回答"这条后果在代码里由哪一行触发"；答不出来就不能按该后果定级。

### 11.5 待补：`open` 缺陷需要到期机制（`due_batch` / `due_action`）
`DEFECT_LEDGER` 目前只有 `pinned_by`（谁钉住它），**没有"该在哪批关掉"**。建议扩字段：
```python
{"id": "P3-B18-04", "level": "P2", "status": "open",
 "pinned_by": "test_real_postgres_migration_is_idempotent",
 "due_batch": "B19", "due_action": "--prune-orphans"}
```
断言：`status == "open"` 必须同时有 `due_batch` 与 `due_action`；且**当前批次 ≥ `due_batch` 仍 open → 红**。

**"当前批次"必须是运行时输入，不能是常量**（pm 指出，采纳；我最初建议"`CURRENT_BATCH` 常量每批人工改"——那正是 `EXPECTED_XFAIL` 双份漂移的翻版）：
```python
current_batch = os.environ["OA_BATCH"]   # 缺失即红，不给静默默认
```
| 项 | 性质 | 正确归属 |
| --- | --- | --- |
| `EXPECTED_XFAIL` / `DEFECT_LEDGER` | **配置/事实**，跨运行不变 | 代码常量（唯一真源） |
| **当前批次** | **运行时上下文**，每次不同 | 调用方传入（env/参数），缺失即红 |

**为什么不能"默认成最新批"**：最新批的 `due_batch` 最宽松，一切都会绿——**"默认"恰好指向最危险的方向**（该红的不红，P2 永久挂账）。

理由：**P2 最容易"永远挂在下一批"**——它不阻塞签收，没有到期机制就会被无限推迟；而 P2 累积即技术债复利。`due_action` 还回答"怎么关"，避免下一批重新调研。


> **常量改名说明**（`6e471a1`/`a27d03b`）：`EXPECTED_OPEN → EXPECTED_OPEN_CASES`、`OPEN_HISTORY → OPEN_CASES_HISTORY`。
> 原因：`EXPECTED_OPEN_CASES` 数的是**断言层**（xfail + red），而 `DEFECT_LEDGER` 的 `status="open"` 是**缺陷层**；
> 同词不同轴必须进名字，不能只靠注释——注释在读代码时最先被跳过。

## 12. 取证可信度：两个必要条件（B19 起执行）

可信证据 = **目标正确** + **目标稳定**，缺一即无效。

| 条件 | 判据 | 失败时的表现 |
| --- | --- | --- |
| **目标正确** | 扫描类门禁必须带 `--dir <归档目录>`，报告记录「扫描绝对路径 + 归档 sha」 | 扫到"已安装包路径"→ 验错树（G-26 实例） |
| **目标稳定** | 主工作区有 WIP 时**不得从主树取证据**；只在 `git archive <sha>` 导出树跑 | WIP 中间态的红被记成批次缺陷（本轮实例） |

### 12.1 轻量判据：**连跑两次，报错不一致 → 立即停手**
本轮实测同一命令在数分钟内先后报 `ImportError: get_audit_service` 与 `NameError: app_router`——**报错形态在变，说明树在变**，此时任何红都不可归因（不是"缺陷在演进"）。
比查 `git status` 更轻，且不依赖他人告知。

### 12.2 到期机制的四象限（B19 必测，缺一即无效）

| # | 场景（`B18-04`，`due_batch=B19`） | 期望 | 防的是什么 |
| --- | --- | --- | --- |
| 1 | `OA_BATCH=B19` + `open` | **红** | 过期未关 |
| 2 | `status=fixed` | 绿 | 关闭后不再报 |
| 3 | `OA_BATCH` **未设** | **红** | 缺失不默认（默认不能放行） |
| **4** | **`OA_BATCH=B18` + `open`** | **绿** | **尚未到期不应红** |

**为什么必须有第 4 条**：若实现写成「只要 `status=open` 就红」，前三条**全部通过**（1 碰巧对、2 绿、3 红），
但后果是**任何一个 P2 一登记就让所有批次变红** → 团队只能二选一：**不登记缺陷**（更糟）或**把 P2 全标 fixed**（自欺）。
第 4 条是唯一能识别这种实现的判据。

> **用例命名提醒**：`status=fixed`（已关闭→绿）与 `current < due`（未到期→绿）是**两个不同的绿**，
> 必须分别命名并在报告里指出各自验的是哪条分支——否则下一批复验的人会以为"置 fixed 通过"已经覆盖了"未到期"。
> 本轮实测即遇到：`-2-2` 的四条里，承担"未到期"职责的是 `OA_BATCH=B18 + open`，而"置 fixed"那条验的是 `status` 分支。

**第 5 种状态：`open` 但无 `due_batch`（配置不完整）→ 红，且文案须区别于"已过期"**
| 状态 | 期望 | 建议文案 | 处置性质 |
| --- | --- | --- | --- |
| `open` + 无 `due_batch` | **红** | 「open 缺陷未登记到期批次」 | **配置错误**（补登记即可） |
| `open` + 已过期 | **红** | 「缺陷已过期未关闭」 | **流程违规**（真去修复） |

两者都红，但**处置完全不同**：前者几分钟能修，后者可能阻塞批次。混用文案会让人看到红就默认"又是那个到期检查"，从而忽略其中的流程违规。

**正确判据不是"存在性"，而是比较**：
```python
status == "open" and current_batch >= due_batch   # → 红
# 其余（current < due、fixed、无 due 的 P4）→ 绿
```
> **"未到期的 open"是正常状态，不是欠账**——把它判红等于把"已知待办"与"逾期未办"混为一谈，而两者处置完全不同。

第 3 与第 4 条方向相反但都正确：**判据要区分"条件未满足"与"条件已违反"**——这正是 `>=` 而非"是否存在"的价值所在。

## 13. 判据完整性的四层（本轮沉淀，从单条到测试集）

| 层 | 要求 | 若缺失的后果 | 反例 |
| --- | --- | --- | --- |
| 单条断言 | **能红**（改错实现必红） | 恒真断言：改错也绿 | `assert True` / 空列表恒等 |
| 断言组 | **断前置**（场景对） | 在错场景里"通过" | `TC-P3-PL03-11` 未断"确实未安装" |
| 单条判据 | **配计数/存在性**（副作用真没有） | 放过"报错但已写库" | 只断 `16003`，不查 `plugin_grant` |
| **测试集** | **错实现通不过**（象限完整） | 三边界全过、错实现照样绿 | 到期检查缺"未到期应绿"象限 |

> **最后一层最难自查**：因为测试集绿的时候，没人会想"它能不能被一个错的实现通过"。
> 一条实践判据：**先假想一个最省事的错误实现，再看它能不能过你这套测试**——能过，说明测试集不完整。

### 14.1 区间样本矩阵（`8000-10000` 由"漏网"转"正样本"）

**R2 加"区间优先"分支**（置于原 R2 之前，日期先由豁免清单剔除）：
```
(?<![\d-])\d{3,7}\s*[-–—~～至]\s*\d{3,7}(?![\d-])
```

| 类别 | 样本 | 期望 | 实测（HEAD 工作树） |
| --- | --- | --- | --- |
| 区间命中（四类分隔符） | `月薪 8000-10000` / `8000–10000` / `8000~10000` / `8000至10000` | R2 命中 | ✅ 四条全命中，且**整段被吃掉**（`8000-10000` 而非 `000`） |
| 区间命中（原正样本回退） | `薪资 12000-15000` / `月薪 8000` / `薪资 8,000` / `待遇 1,500` | R2 命中 | ✅ 未回退 |
| **不命中** | `-5~-3`（负数）、`2026-11-01`（日期）、`订单 A-100200`（编号） | **不得命中** | ✅ 三条均不命中 |
| 不命中（需豁免剔除） | `工号 EMP1234` | 由 `EMP\d{4}` 豁免先剥离 | ⚠️ 不剥离时 R2 会命中 `1234`——**证明豁免清单必须先行，不能靠正则自己躲** |
| R1 8/8 未回退 | `15k`/`1.2万`/`1.2万元`/`8000每月`/`3 亿元`/`1200 亿`/`0.5 亿`/`3亿` | 全命中 | ✅ |
| R1 7/7 未回退 | `8000`/`8,000`/`1,500`/`2026-11-01`/`3 个月`/`30%`/`按公司标准执行` | 全不命中 | ✅ |

> **顺序不可反**：区间分支必须在原 R2 之前；且**豁免（日期/工号/百分比）必须比两条 R2 分支更早执行**——否则 `EMP1234` 会被当成裸金额。

**工号必须两种写法各一条样本**（实测）：
| 样本 | R2-a | R2-b | 由谁保护 |
| --- | --- | --- | --- |
| `EMP-1234`（带连字符） | — | — | **lookbehind 的 `-`**（位数机制） |
| `EMP1234`（无连字符） | — | **命中 `1234`** | **只能靠豁免剥离** |

> 只测 `EMP-1234` 时，实现把**豁免删掉**仍能通过——因为连字符写法本来就不命中。
> 两种写法各一条，才能同时锁住"lookbehind 有效"与"豁免有效"这两个**独立机制**。

### 14.2 样本必须能排除"捷径实现"（通用要求）

单一正样本会指向**一个错误但能通过**的实现。实例（本轮）：
- 只测 `月薪 8000-10000` → 实现只要**放开连字符**（去掉 lookbehind 的 `-`）就能过，代价是 `2026-11-01` 全部误报；
- 只测 `EMP-1234` → 实现只要**删掉豁免**就能过，代价是 `EMP1234` 误报。

> **判据设计时先假想"最省事的错实现"，再为它准备一条样本**——这与"测试集必须让错实现通不过"是同一要求，只是落到了样本粒度。

### 14.3 扩豁免必须配"反向守卫样本"（否则修假红会开出漏检）

为消除编号误报而**放宽豁免**时，极容易连带放走真实金额写法。实测：

| 样本 | 当前 R2-b | 用宽豁免 `[A-Za-z]{1,5}-?\d{4,}` 剥离后 |
| --- | --- | --- |
| `EMP1234` / `PO2024001` / `A100200X` | 命中 `1234` / `2024001` / `100200`（**须豁免**） | 被剥掉 ✅ 符合预期 |
| **`RMB8000`** | 命中 `8000`（**须继续命中**） | **被剥掉 → 漏检 ❌** |
| **`K8000`** | 命中 `8000`（**须继续命中**） | **被剥掉 → 漏检 ❌** |

**结论**：豁免不能用"任意字母 + 数字"的形状，必须**前缀白名单**（`EMP|PO|SKU|ORD…` 等业务编号前缀）；
且**每加一条豁免，必须同时加一条"仍应命中"的守卫样本**（`RMB8000` / `K8000` / `¥8000` / `CNY 8000`）。

> 通则：**放宽豁免是在移动边界**——只测"误报消失"等于只验移动的一半；另一半是"原本该抓的还抓得到"。

**为什么必须写"已知误报"**：R1 的本质是**形状匹配**，`服务 2000 万用户` 与 `年薪 2000 万` 形状相同。作用域（只扫 `output_key=offer`）是唯一防线——**不写下来，将来有人把范围放宽到公文全篇时，会以为这条从无风险**。

**为什么必须写"已知漏网"**：`8000-10000` 是最常见的薪资区间写法，而 R2 的 `(?<![\d-])…(?![\d-])` 为排除日期/编号而禁止连字符两侧——**两个规则同时漏掉它**。已知漏网不写，验收到 B20 时会以"规则已覆盖"结案。
