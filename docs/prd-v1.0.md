## 二、产品目标与定位

### 2.1 产品定位（严格引用总方案 1.1 节，不得发散）

面向企业与团队用户的**跨生态、全场景、可私有化的办公 AI 平台**。

- 不绑定任何单一办公生态，打通主流办公工具，解决混合办公断点
- 以插件化体系覆盖全岗位工作流，依托开源生态实现深度场景能力
- 支持云端 SaaS 与纯本地私有化双部署模式，保障企业数据主权
- 极致易用，所有 AI 技术细节完全屏蔽，普通职场用户开箱即用

### 2.2 V1.0 产品目标

| # | 目标 | 衡量口径（对应总方案） |
| --- | --- | --- |
| G1 商用基线 | 首版即达到可直接付费交付的成熟度，体验与能力对标大厂办公 AI 产品 | 6.1 基础能力覆盖度不低于大厂通用版；6.2 体验验收；6.3 性能指标 |
| G2 差异化落地 | 落地跨生态工具打通与插件化岗位工作流，形成跨生态中立性、私有化部署、岗位级场景插件三大差异化 | 6.1 首批 5 款工具深度打通；3 个标杆插件端到端可用 |
| G3 商业化就绪 | 双部署模式 + 计量计费 + 运营后台闭环，可对外销售与交付 | 6.5 SaaS 注册/付费/使用可用；私有化一键部署纯离线；文档齐全 |

### 2.3 核心设计原则（引用总方案 1.2 节，强制执行）

1. **首版即商用**：拒绝 Demo 级产物，V1.0 必须达到可直接付费交付的成熟度。
2. **技术黑盒化**：前端严禁出现模型名称、向量库、RAG、Agent 等技术术语；所有错误提示使用业务语言，禁止抛出代码报错与堆栈。
3. **适配层唯一原则**：所有上层业务代码、场景插件只能调用自研统一适配层标准接口，严禁直接调用 Dify 原生 API/SDK。
4. **合规优先**：所有开源组件必须经过协议审核，GPL/AGPL 等强传染协议组件禁止进入核心代码库。
5. **体验一致性**：全产品 UI、交互逻辑、文案风格 100% 统一，插件不得使用独立设计规范。

### 2.4 技术路线概述（引用总方案第二章、7.2 节）

基于成熟开源底座二次开发（Dify 底座 + Open WebUI 前端参考）+ 自研统一适配层解耦 + 插件化场景扩展；复用优先、接口先行，研发资源优先投入跨生态、场景插件、体验打磨等差异化领域，底座能力够用即可。

> 排期与里程碑以总方案第四章为准，本 PRD 不重复排期，仅在需求池中标注需求所属阶段（S1-S4），供架构排期参考。

## 七、关键业务流程说明

### FLOW-01 新用户首次对话（R1）

- **触发**：用户注册/登录后进入产品。
- **步骤**：
  1. 进入对话主页，系统默认创建新会话并聚焦输入框（无任何参数配置项）。
  2. 用户输入问题或上传附件，系统即时反馈（输入状态/加载动画）。
  3. AI 流式回复，首字响应 ≤ 1s（AC-08）；引用知识库时展示引用来源。
  4. 用户连续追问，AI 结合上下文与记忆延续对话。
  5. 会话自动归档至侧边栏，可重命名、切换、归档。
- **关键规则**：界面无模型名称与参数调节（附录 A）；任何错误以自然语言提示并给出解决建议（5.5）。
- **完成标志**：用户完成一次完整问答并可继续第二轮对话。

### FLOW-02 知识库文档上传与问答（R1/R2）

- **触发**：用户需要基于企业文档获得带来源的答案。
- **步骤**：
  1. 进入知识库页，创建或选择知识库。
  2. 上传文档，页面展示索引进度（进度可见）。
  3. 索引完成后，用户在对话中选择知识库提问，或在知识库页直接提问。
  4. 系统返回答案 + 引用片段 + 来源文档（3.2 RAG 服务接口出参）。
  5. 知识库可见范围按权限控制（3.3，S2 第 9-11 周）。
- **关键规则**：分块策略、向量库、召回参数等技术细节对用户不可见（附录 A）。
- **完成标志**：用户获得带引用溯源的答案。

### FLOW-03 插件安装到启用（R1/R5）

- **触发**：用户在插件市场发现岗位工作台插件。
- **步骤**：
  1. 进入插件市场，浏览/搜索，查看分类、使用说明与评分。
  2. 点击安装，弹出权限授权页（展示插件声明的权限，3.4-4）。
  3. 用户授权后插件启用，界面出现插件入口（统一组件库渲染）。
  4. 用户使用插件；可随时卸载或升级版本。
- **关键规则**：插件前端组件 100% 使用平台统一组件库，无自定义 UI；未授权不得调用对应工具与数据。
- **完成标志**：插件启用并成功完成一次任务或展示可用状态。

### FLOW-04 工作流任务执行（R1）

- **触发**：用户在插件内输入任务（前端需求/运营主题/招聘需求）。
- **步骤**：
  1. 系统创建工作流任务并开始执行。
  2. 工作流可视化页展示当前步骤与整体进度，步骤可展开查看详情。
  3. 任务完成展示最终结果（代码提交 / 稿件排期 / 公文）。
  4. 历史任务可查询与追溯。
- **关键规则**：步骤失败时以自然语言说明原因并给出重试或替代方案（5.5）；工作流编排细节、源码对用户不可见（3.5 移除工作流源码编辑）。
- **完成标志**：任务产出符合插件交付标准（3.4）的结果物。

### FLOW-05 团队邀请与权限配置（R2/R3）

- **触发**：团队需要新增成员或调整权限。
- **步骤**：
  1. 企业管理员搭建组织架构（部门/层级）。
  2. 创建/分配角色，配置细粒度权限点。
  3. 邀请成员（发送邀请），成员接受后归属组织并继承角色权限。
  4. 管理员随时调整成员角色与数据可见范围。
  5. 邀请、权限变更、数据导出等关键操作写入审计日志。
- **关键规则**：权限校验经适配层用户权限服务接口统一执行（3.2），业务代码不得自行判权。
- **完成标志**：成员以正确权限访问平台，操作记录可审计。

### FLOW-06 套餐订阅与付费（R2/R3）

- **触发**：用户需要开通或变更套餐。
- **步骤**：
  1. 在个人中心/团队管理查看当前套餐、使用统计与剩余额度。
  2. 选择套餐（免费/专业/企业）与席位数量，下单支付。
  3. 支付成功后席位与额度即时开通，功能按套餐解锁。
  4. 平台按 token 用量、调用次数、席位数量三维度持续计量。
  5. 到期前提醒续费；支持升级/降级与席位增减。
- **关键规则**：定价与额度假设见 Q5；用户端展示口径见 Q7；私有化 License 授权独立于 SaaS 订阅（3.6）。
- **完成标志**：支付成功且套餐能力正确生效，计量数据准确。

### FLOW-07 私有化部署交付（R3 + 交付团队）

- **触发**：企业客户采购私有化版本。
- **步骤**：
  1. 交付团队确认客户环境假设（规模/网络/合规，见 Q3），交付完整离线镜像包（移动介质）。
  2. 客户服务器执行 Docker Compose 一键部署（3.6）。
  3. 激活 License，运行模式配置为私有化纯本地。
  4. 按需加载本地模型，初始化管理员账号与组织架构。
  5. 断网验证核心功能（对话、知识库、插件），交付部署手册与运维工具。
- **关键规则**：与 SaaS 共用同一套代码，仅通过配置区分模式（3.6）；私有化模式移除所有外网依赖（3.1-5）。
- **完成标志**：客户环境断网完成部署与核心功能验证，进入验收（AC-15）。

## 八、非目标（Out of Scope）与产品边界

1. **不自研训练大模型**：聚焦模型调度、适配与应用层，不自研基础模型（3.1 底座职责；7.2 复用优先）。
2. **不对 Dify 核心做深度魔改**：仅做必要的功能补全与 Bug 修复，不做上游深度定制（第二章架构核心说明 2）。
3. **不向终端用户提供技术向功能**：模型参数调节、提示词工程、工作流源码编辑等面向开发者的功能一律不提供（3.5）。
4. **不支持插件自定义 UI**：插件不得使用独立设计规范，V1.0 不存在完全自定义界面的插件形态（1.2；3.4-3）。
5. **不开放第三方插件市场**：V1.0 仅内置官方插件，第三方开发者接入仅为"预留能力"（3.4）。
6. **跨生态工具仅交付首批 5 款**：其余工具属 V1.x 扩充范围（1.3；联动 Q1）。
7. **不覆盖总方案 1.3 之外的能力**：总方案未列入 V1.0 交付范围的功能（含一切总方案未提及的通用办公套件能力）均不在本期范围。
8. **私有化交付不含定制实施服务**：交付边界为"一键部署包 + 离线镜像 + 文档 + 运维工具"，客户现场定制开发不在 V1.0（3.6 交付形式）。
9. **运营管理后台不向企业客户开放**：仅面向平台内部运营角色使用（3.3）。

### Q1 首批 5 款办公工具的具体选型

- **背景/歧义**：总方案 1.3 要求"跨生态工具打通（首批 5 款）"但未指定清单；3.4 中三个标杆插件分别对接 GitHub（前端研发）、公众号/小红书/抖音（内容运营）、邮箱/企业微信/飞书/招聘平台（行政人事），候选工具合计已超过 5 款，"首批 5 款"与插件依赖工具的关系未定义。
- **建议方案**：以"3 个标杆插件端到端可用"反推 5 款必备工具——① GitHub（前端研发插件交付标准硬依赖）；② 企业微信；③ 飞书（行政人事邀约与通知）；④ 邮箱（JD/邀约/入职通知）；⑤ 微信公众号（内容运营主发布平台）。理由：全部为总方案 3.4 已明确出现的工具，不引入总方案之外的新生态；优先保障 P0-08 硬验收。小红书/抖音等发布环节建议纳入 P1-02 扩充，内容运营插件首版发布范围联动 Q4 决策。
- **待用户决策**：(a) "首批 5 款"是否从插件依赖工具中选取，还是作为独立通用办公工具清单另设；(b) 是否替换其中某款（如增加钉钉、抖音、小红书）；(c) 内容运营插件"多平台定时发布"验收是否接受首版仅覆盖公众号。

### Q2 首批模型矩阵的接入优先级

- **背景/歧义**：3.1 列出 7 个模型（豆包、GPT-4o、Claude 3.5、通义千问、Qwen2.5、Llama 3.1、DeepSeek-Coder）但未给接入优先级与排期；私有化纯离线要求至少一个可本地部署模型（3.1-5）。
- **建议方案**：第一批（S1，第 1-5 周）接入豆包（国内商用云端主模型）+ Qwen2.5（私有化本地主模型）+ DeepSeek-Coder（代码辅助场景必需）；第二批（S2）接入通义千问、GPT-4o、Claude 3.5、Llama 3.1，补齐多模型调度与备用切换能力（呼应 7.1 备选方案）。
- **待用户决策**：(a) 闭源 API 在私有化环境是否允许使用（联动 Q3 网络与合规假设）；(b) 各模型 token 成本预算约束；(c) 是否按使用场景固定默认模型（用户侧不展示模型信息，见附录 A）。

### Q3 私有化部署目标客户的环境假设

- **背景/歧义**：3.6 已定 Docker Compose 单服务器开箱即用 + 完整离线镜像包 + License，但未定义目标客户规模、硬件规格、网络条件与合规基线。
- **建议方案**：V1.0 按"中小团队/部门级"场景设计——并发 ≤ 200 用户；单机 8 核 32G 内存起步，GPU 可选（GPU 用于本地 Qwen2.5/Llama 3.1 推理，无 GPU 时以 API 模式运行）；离线镜像包通过移动介质交付，支持零外网运行；合规基线按国内网络安全等级保护二级准备（非承诺认证）。以上为容量与场景假设，非承诺指标。
- **待用户决策**：(a) 目标客户规模上限（100 / 200 / 500 并发）；(b) 是否承诺 GPU 环境，或必须支持纯 CPU 可行；(c) 客户合规要求（等保级别、行业监管、数据不出境）；(d) 离线包的更新与补丁分发方式。

### Q4 3 个标杆插件的依赖关系与优先级

- **背景/歧义**：3.4 与 6.1 要求 3 个插件在 V1.0 全部端到端可用，排期上同处 S3 第 19-20 周开发，依赖关系与资源冲突未分析。
- **建议方案**：
  - 依赖分析：前端研发工作台 ← 通用代码辅助（P0-05）+ GitHub（Q1）+ Agent 服务接口 + 工作流可视化；内容运营工作台 ← 知识库/RAG（P0-04，素材检索）+ 多平台发布工具（Q1）+ 工作流可视化；行政人事工作台 ← 邮箱/企业微信/飞书（Q1）+ 工作流自动化 + 公文生成。
  - 建议开发顺序：① 前端研发工作台（流程最标准化、无外部发布依赖、3.4 交付标准最明确）；② 内容运营工作台（依赖已打磨的 RAG + 首批工具）；③ 行政人事工作台（外部对接方最多、协调成本最高）。工作流可视化页面为三者共享依赖，建议先行开发。
- **待用户决策**：(a) 三个插件是否均维持 P0 硬验收；若 S3 资源受限，行政人事插件的"面试邀约安排"环节是否可降级为半自动并移至 V1.1；(b) 内容运营插件首版发布平台覆盖范围（联动 Q1）。

### Q5 计费套餐的定价假设

- **背景/歧义**：3.3 明确三级套餐（免费版/专业版/企业版）与三维计量（token 用量/调用次数/席位数量），但无价格、额度与超额策略。
- **建议方案**（量价模型设计假设，非最终定价）：免费版面向个人试用，基础对话与知识库受限额度；专业版按席位订阅，开放全量基础能力 + 插件市场；企业版订阅制并叠加私有化 License 选项，解锁组织架构、权限、审计等企业能力。用户端计量展示以"使用量/额度"业务语言呈现（联动 Q7）。
- **待用户决策**：(a) 各档目标价格与席位阶梯；(b) 免费版额度上限与升级触发策略；(c) 私有化 License 计费模式（一次性买断 / 年费 / 按节点）；(d) 套餐超额后的策略（限速 / 停服 / 按量付费）。

### Q6 长上下文记忆的能力边界

- **背景/歧义**：1.3 与 6.1 要求"长上下文记忆"，但未定义记忆范围（是否跨会话）、用户是否可查看/删除记忆、保留期限。
- **建议方案**：V1.0 先做"单会话长上下文 + 跨会话轻量偏好记忆（如常用称呼、团队语境）"，并在个人中心提供记忆管理入口供用户查看与删除（呼应 5.4 数据权利与 3.5 个人中心）。
- **待用户决策**：(a) 是否要求跨会话记忆及其深度；(b) 用户是否可查看/删除记忆；(c) 记忆保留期限与租户隔离策略。

### Q7 用量与计费信息的用户端展示口径

- **背景/歧义**：1.2 技术黑盒化禁止界面出现技术术语，而"token 用量"本身即技术术语；3.5 要求个人中心具备使用统计，两者存在张力。
- **建议方案**：对普通用户仅展示业务化用量（如"本月对话次数/文档解析次数/剩余额度"），token 精确值仅企业管理员（成本核算）与平台运营可见。
- **待用户决策**：(a) 普通用户可见的用量维度与文案口径；(b) 企业管理员是否可见 token 明细；(c) 套餐超额提醒的触达方式（站内/邮件等）。
