## 0. 适用范围与阅读约定

1. **本文件只讲增量**。阶段一（对话、知识库 Demo、基础权限、邮箱与代码仓库工具）与阶段二（知识库五项、5 款工具、组织权限、计量计费、运营后台、10 页前端）已验收的能力不重复描述；`/plugins` 与 `/workflows` 两页在阶段二只是「工具展示 + 任务列表」的雏形，本阶段做实质深化。
2. **端点点注约定**：`[复用]` 路径与字段零改动；`[扩展]` 在既有端点做**向后兼容**的字段/筛选项新增（旧字段不删、不改语义、新字段可选）；`[新增]` 本阶段新端点。
3. **插件域端点**属总方案 3.4「场景插件层」的配套业务能力，按架构红线「前端只能通过适配层唯一出口访问后端」，仍在适配层出口暴露，不计入原 30 端点基线，归「业务域端点基线」（与阶段二口径一致）。
4. 本文件出现的所有技术名词仅用于内部沟通，**任何一条都不得出现在用户界面**（第 8 章为增量红线表，与阶段二第 7 章合并使用）。
5. **本阶段一切「插件」默认指官方内置插件**。第三方插件开放（P1-01）明确不在 V1.0，边界见第 7 章。

| P0-P3-23 | HR | Offer 文案 + 行政公文自动化（通知 / 纪要 / 请示 / 周报） | Offer 中金额字段**必须为空**由人工填写；4 类公文各 1 篇可导出为文档文件 |
| P0-P3-24 | UI | 工作台宿主页与市场入口（一套宿主渲染全部插件） | 3 个插件共用同一宿主路由，差异仅来自插件声明；入口在导航「插件与工作台」下且与权限一致 |
| P0-P3-25 | UI | 文案与合规门禁（禁词 / 禁占位 / 禁插件自定义 UI） | 扫描脚本 0 命中；插件资产目录 0 个 `.css`/`.jsx` 自有样式与脚本；界面 0 处错误码与堆栈 |

### 3.2 逐条详述

> 格式：用户价值 / 功能口径 / 端点 / 验收标准（可机械判定）。三个标杆插件的完整「输入→步骤→产出→达标判据」在第 5 章，本节只列口径与最小断言。

#### 3.2.1 插件标准与运行时（P0-P3-01 ~ 05）

**P0-P3-01 插件声明标准与机械校验（PL）**

- **用户价值**：声明统一，插件才能被统一渲染、统一授权、统一审计，用户才不会遇到「每个插件长得都不一样」。
- **功能**：① 声明含 6 段——基本信息（`plg_` 标识、名称、简介、分类、图标、版本、开发者「官方」）、能力清单、输入定义（表单字段：类型 / 必填 / 上限 / 业务文案）、输出定义（产物类型：文件 / 链接 / 表格 / 稿件 / 文档）、界面描述（仅声明区块顺序，**不携带脚本与样式**）、步骤定义（序号 + 业务语言标题 + 每步产物类型）。② 加载时机械校验：必填段缺失、字段类型非法、步骤序号不连续、版本号不规范、声明文案命中禁词 → 拒绝加载。③ 校验失败不产生空白页：市场不展示该插件，运维侧留一条原因记录。④ 同一标识重复注册 → 拒绝并保留原条目。
- **端点**：不对外暴露（经 PL1/PL2 读取）。
- **验收标准**：① 3 个非法声明（缺步骤定义 / 版本写 `abc` / 序号 1,3,4）均不加载，`GET /plugins/market` 不含，且留 3 条失败原因；② 名称写「RAG 助手」→ 拒绝加载；③ `GET /plugins/market/{id}` 的 `step_titles[]` 与声明逐项相等；④ 重复注册失败且原条目字段不变。

**P0-P3-02 插件运行时与生命周期（PL）**

- **用户价值**：装好能稳定跑、能随时停、跑太久能停掉，用户才有掌控感。
- **功能**：① 状态机 `not_installed → installed → enabled ⇄ disabled → not_installed`，非法跳转返回业务错误（不隐式创建）。② 执行入口只允许工作台宿主页发起（P0-P3-24），一次执行建一个自动化任务并携带 `plugin_id`。③ 单次执行超时由声明配置（默认 900 秒），超时任务置「未完成（超时）」，**已产生的步骤产物保留可看**。④ 同一企业同一插件并发 ≤3，超出排队并提示「前面还有 N 个任务在跑，稍后自动开始」。⑤ 停用后入口置灰 + 「该插件已停用，请联系管理员启用」；在跑任务继续完成；受保护能力调用返回业务错误。
- **端点**：`[复用]` A1（`[扩展]` 请求新增可选 `plugin_id`）、A3、A4、A5、A6。
- **验收标准**：① 未安装状态调 `PATCH /plugins/{id}/state` → 业务错误，`GET /plugins/installed` 不含该项；② 执行后 `GET /agent/tasks?plugin_id=plg_dev_workbench` 能筛出且 `plugin_id` 非空；③ 超时压到 5 秒构造长任务 → 状态未完成且已完成步骤产物可取；④ 并发上限 3 时第 4 个提示排队，最终 4 个全部完成不丢；⑤ 停用后按钮置灰且有提示，已发起任务最终完成。

**P0-P3-03 能力声明与安装时授权（PL，G3-2 核心）**

- **用户价值**：装插件前必须知道「它要读我什么、写我什么」，这是企业采购与合规硬门槛（总方案 3.4-4）。
- **功能**：① 能力固定 6 项枚举（V1.0 不开放自定义）：个人数据类 — ①读取你本人的知识库内容 ②使用你已连接的办公工具 ③读取你本人上传的文件；企业数据与写入类 — ④读取企业通讯录与组织架构 ⑤写入代码仓库 ⑥向外部平台发布内容。② 授权页每项展示 3 件事：业务语言名称、为什么需要、「不同意会怎样」。③ 默认全选可逐项取消：取消**必需能力** → 「同意并安装」置灰并显示原因；取消**可选能力** → 允许安装，对应步骤执行时降级为「未完成：未授权…」+ 授权入口。④ 授权持久化到「成员 × 插件 × 能力」；可在「已安装 → 管理权限」增减（**写授权走 PL14**，其中 `required: true` 的能力**不允许撤销**，须引导「停用」或「卸载」），撤销后下一次调用立即生效（缓存 TTL ≤5s，沿用阶段二 §6.3）。⑤ 企业级能力（④⑤⑥）需管理员在团队设置开启总开关（Q3-2），**开关状态必须由端点返回**（PL4 读、PL13 `PUT /plugins/capability-policy` 写，前端禁止硬编码）；未开启时安装第 2 步提示「需要管理员开启「写入代码仓库」能力」+「复制申请说明」（纯前端复制，无新端点）。
- **端点**：`[新增]` `GET /plugins/{plugin_id}/capabilities` → `items[{capability_key, display_name, reason, denial_effect, category(personal|org), required, org_switch_enabled}]`；`[新增]` `POST /plugins/{plugin_id}/install`（`{grants{}, settings{}}` → `{plugin_id, status, granted_capabilities[], denied_capabilities[]}`）。
- **业务化文案**：能力 → 「需要用到的能力」；授权 → 「同意并安装」；**禁止出现** scope / permission / grant / token。
- **验收标准**：① 能力条数与声明一致（研发工作台 = ②③⑤ 三项）；② 取消必需能力②后安装 → 失败，按钮下显示「该插件需要「使用你已连接的办公工具」才能提交代码」；③ 只授权②③、拒绝⑤ → 安装成功，第 5 步「未完成：未授权写入代码仓库」且有「去授权」；④ 撤销② → 下次执行在需工具支持的步骤失败并提示重授权，恢复后重试成功；⑤ **用户可见文案与 DOM** 中 scope/permission/grant **0 命中**（后端字段名如 `plugin_grant`、`permissions` 与代码标识不计，见勘误第 5 条）。

**P0-P3-04 版本管理与升级、恢复上一版本（PL）**

- **用户价值**：升级不能打断工作，升坏了要能退回去。
- **功能**：① 已安装页展示当前/最新版本，有更新时出「有可用更新」标记与「更新」按钮；更新二次确认（说明「正在执行的任务不受影响」）。② 只保留**最近 1 个**版本快照，可执行一次「恢复上一版本」，再退提示「只能恢复到上一个版本，如需更早版本请联系管理员」。③ 升级/回退不删历史任务与产物；历史任务按创建时的步骤定义渲染。④ 重复点更新幂等（不产生两个版本）；声明要求的最低平台版本高于当前 → 拒绝升级并提示「该插件需要更新版本的产品后才能使用，请联系管理员」。
- **端点**：`[新增]` `POST /plugins/{plugin_id}/upgrade`（`{target_version}`）、`POST /plugins/{plugin_id}/rollback`。
- **验收标准**：① 发 v1.1 后出现更新标记，更新后 `GET /plugins/installed` 版本为 `1.1.0` 且标记消失；② 连点两次 → 仅 1 条版本记录；③ 恢复上一版本 → 回到 `1.0.0`，再点返回业务错误且版本不变；④ 升级后打开升级前的历史任务 → 步骤标题与升级前一致。

**P0-P3-05 插件开发文档与样例（PL）**

- **用户价值**：第 17-18 周明确交付物，也是后续第三方的唯一说明来源（V1.0 不开放提交）。
- **功能**：一份开发文档 + 1 个可运行样例插件（内部使用、不进市场），必须含 6 节：声明字段表（必填 / 类型 / 上限）、6 项能力枚举与申请口径、输入定义规范、输出产物类型、界面描述规范（**必须用平台组件库，禁止自带样式与脚本**）、标准接口调用清单（只列允许调用的适配层端点）。
- **验收标准**：① 6 节齐全，QA 按文档可复跑样例插件并跑通一次任务（不额外口头指导）；② 文档「允许调用的接口」清单与适配层实际端点逐条对应，无「文档有、代码无」；③ 明确写出「不得自定义 UI」「不得直连底座」「V1.0 仅官方内置插件」三条边界。

#### 3.2.2 插件市场（P0-P3-06 ~ 10）

**P0-P3-06 市场浏览、分类、搜索、排序（MK）**

- **用户价值**：用户按岗位找插件，而不是翻一个长列表。
- **功能**：分类 6 个（研发 / 内容运营 / 行政人事 / 数据分析 / 协作办公 / 其他）；关键字搜索（名称 + 简介）、排序（官方推荐 / 最新上架 / 评分）、12 条/页；卡片展示 名称、一句话简介、分类、评分、版本、状态徽标（未安装 / 已安装 / 已启用 / 有更新）。市场内 V1.0 共 6 个内置插件（3 个标杆工作台 + 3 个轻量工具型），最终数量以架构批次拆分为准。
- **端点**：`[新增]` `GET /plugins/market?category=&keyword=&sort=&page=&page_size=` → `items[{plugin_id, name, summary, category, rating_avg, rating_count, latest_version, installed_status}], meta, categories[]`。
- **验收标准**：① `category=dev` 返回项分类全为 `dev`；② 关键字大小写/空格差异返回一致，无匹配时返回空列表 + 空态文案（非报错）；③ 第 1、2 页 `plugin_id` 无交集且 `total` 与累计一致；④ 套餐不支持插件时市场页**照常展示**插件卡片与详情（列表项 `installable=false`），仅在点「安装」/「启用」时拦截并给「查看套餐」入口，**不得**整页降级为升级提示页。

**P0-P3-07 插件详情页（MK）**

- **用户价值**：安装前能一次看全「是什么、要什么能力、几步、别人怎么评」。
- **功能**：区块顺序固定：头部（名称 / 分类 / 评分 / 版本 / 主按钮）→ 介绍（≥120 字使用说明）→ 需要用到的能力（逐项说明）→ 执行步骤预览（有序标题）→ 版本历史 → 评价区（汇总分 + 最近 10 条）。主按钮随状态变化：安装 / 启用 / 打开工作台 / 更新。
- **端点**：`[新增]` `GET /plugins/market/{plugin_id}` → `{…, capabilities[], step_titles[], changelog[], installed_status, installed_version}`。
- **验收标准**：① `capabilities[]` 条数 = `GET .../capabilities` 条数；② `step_titles[]` 顺序与工作台执行步骤逐项一致；③ 无评价时显示「还没有人评价，用过后可以来说说」（非空表格）；④ 主按钮文案与 4 种状态的映射断言全对。

**P0-P3-08 安装 / 启用 / 禁用 / 卸载（MK，G3-1 核心）**

- **用户价值**：一次装好就有入口，不用就停掉；卸载后历史还能查。
- **功能**：① 安装 → 授权抽屉（P0-P3-03）→ toast「已添加，可在「插件与工作台」中使用」→ 导航出现入口；安装即启用（Q3-3）。② 禁用二次确认「停用后工作台入口将不可用，已发起的任务会继续完成」。③ 卸载二次确认必须展示两条后果：「历史任务记录会保留但不能再发起新任务」「已生成的产物 180 天后清理」。④ 卸载不删历史任务与产物，任务详情仍可打开（只读）。⑤ 有任务执行中时允许卸载，但提示「有 N 个任务正在执行，卸载后当前任务会继续完成」。
- **端点**：`[新增]` `PATCH /plugins/{plugin_id}/state`（`{status: enabled|disabled}`）、`DELETE /plugins/{plugin_id}`（→ `{plugin_id, uninstalled, running_task_count}`）、`GET /plugins/installed`。
- **验收标准**：① 安装后 `status=enabled`；② 禁用 → `disabled` 且宿主页置灰，再启用 → 可执行任务；③ 卸载后 `GET /plugins/installed` 不含该项，`GET /agent/tasks?plugin_id=X` 仍返回历史任务且详情可打开；④ 两个确认弹窗中的后果文案均存在（字符串断言）。

**P0-P3-09 评价与使用说明（MK）**

- **用户价值**：同事的真实使用反馈比官方介绍更可信。
- **功能**：已安装用户可提交 1-5 星 + ≤200 字评价；同一成员同一插件再次提交为**覆盖更新**；展示姓名（可匿名，匿名为「某位同事」）+ 部门 + 时间 + 评分 + 内容；评分**仅展示、不参与排序**（Q3-4，防刷分）；使用说明取插件声明，展示在详情页与工作台右侧帮助区。
- **端点**：`[新增]` `POST /plugins/{plugin_id}/reviews`（`{rating, content, anonymous}`）、`GET /plugins/{plugin_id}/reviews?page=&page_size=`。
- **验收标准**：① 同成员提交两次 → 仅 1 条且为第二次内容；② 未安装用户提交 → 业务错误 + 「使用过这个插件才能评价」；③ `rating=6` → 参数错误 + 「评分请选择 1 到 5 星」；④ 匿名提交列表 `author_name` = 「某位同事」，不含真实姓名。

**P0-P3-10 已安装管理与「有可用更新」（MK）**

- **用户价值**：一屏掌握「我用着哪些、哪些该更新、最近用过没」。
- **功能**：表格列：插件名称、分类、当前版本、状态（已启用/已停用）、可用更新（有则显示版本号 + 更新按钮）、最近使用时间、操作（打开 / 启用停用 / 管理权限 / 卸载）；顶部按状态筛选。
- **端点**：`[复用]` PL3（P0-P3-08 已列）。
- **验收标准**：① 后台发新版本后该行出现目标版本号，更新后变「已是最新」；② 「最近使用时间」= 该插件最近一次任务创建时间（无任务显示「尚未使用」）；③ 筛选「已启用」只返回 `status=enabled`。

#### 3.2.3 工作流执行可视化（P0-P3-11 ~ 14，FLOW-04）

**P0-P3-11 步骤级进度与状态时间线（WF）**

- **用户价值**：长任务最怕黑屏等待；看得见每一步才敢离开页面。
- **功能**：① 顶部：任务名（插件任务标题 + 输入摘要）、发起人、开始时间、总耗时、总进度（= 已完成步骤数 / 总步骤数，不用不可解释的权重）、状态徽标。② 垂直时间线每步：序号、业务语言标题（来自插件步骤定义）、状态（等待 / 进行中 / 已完成 / 未完成 / 已跳过）、耗时、「查看产物」。③ 执行中经事件推送增量刷新（A6）；断线重连按 A3 + A4 全量补齐，**不丢步骤**，冲突以服务端为准。④ **不展示**节点类型、编排源码、提示词、模型名；步骤标题不得含英文与技术注解。
- **端点**：`[复用]` A3（`[扩展]` 见附录 A.2）、A4（`[扩展]` `steps[].artifacts[]`、`steps[].failure`）、A6。
- **验收标准**：① 执行中 5 秒内至少刷新一次，状态序号序列非递减；② 断网 30 秒恢复后步骤数与 A4 一致，无重复、无缺失；③ **可见文本** 0 命中 `node`/`step_id`/`workflow`/`prompt`（`href`、`data-*`、`id`、`class` 等属性值与路由路径不计，见勘误第 4 条）；④ 6 步任务完成 3 步时进度显示 50%。

**P0-P3-12 每步产物展示与下载（WF）**

- **用户价值**：产物挂在步骤上，用户才知道「哪一步给了我什么」。
- **功能**：产物按类型渲染——文件（名称 + 大小 + 下载）、链接（标题 + 跳转）、表格（前 5 行预览 + 下载 CSV）、稿件（标题 + 正文预览 + 复制）、文档（导出 docx）；归属步骤明确，禁止全部堆在任务级；任务级「结果物汇总」按步骤顺序聚合。
- **端点**：`[扩展]` A4 `steps[].artifacts[]`（`artifact_id / type / name / size_bytes / download_url / url / preview_text`）。
- **验收标准**：① 连跑 3 次任务，产物均挂在产生它的步骤下且不跨任务串（`artifact_id` 与 `task_id` 一对一校验）；② 「已完成」步骤 `artifacts.length ≥ 1`，「未完成」允许 0；③ 超过留存期点击 → 「产物已过期，可重新发起任务」，不显示错误码。

**P0-P3-13 失败原因、重试与人工接管（WF）**

- **用户价值**：失败时能只重跑卡住的那一步，不用从头再来。
- **功能**：① 失败步骤三段：发生了什么（一句话）、可能原因（1-2 条可执行）、下一步（按钮组）。② 动作固定 3 个：`重试本步`（已成功步骤不重跑）、`从头重试`、`联系管理员`（复制诊断说明，**不含堆栈与错误码**）。③ 需人工接管必须显式暂停并提示：提交代码前确认（P0-P3-17）、发布前确认（P0-P3-20）、Offer 金额填写（P0-P3-23）；接管态任务状态为「等待你确认」，给确认/放弃。④ 重试生成**新任务**并以 `retry_of` 关联，原任务记录永久保留不改状态。
- **端点**：`[新增]` `POST /agent/tasks/{task_id}/retry`（`{from_step?}` → `{task_id, retry_of, status}`）。
- **验收标准**：① 注入「工具未连接」→ 出现原因 + 3 个动作；点「重试本步」后新任务 `retry_of` = 原任务且前序步骤不重跑（耗时显著小于全量）；② 未失败任务调用 retry → 业务错误，界面不出现重试按钮；③ 接管态保持「等待你确认」，15 分钟不自动继续；④ 「联系管理员」复制文本中 `\b[1-3]\d{4}\b` 0 命中、无 `Traceback`/堆栈特征。

**P0-P3-14 任务历史与结果物核查（WF，AC-02 溯源）**

- **用户价值**：AC-02 要求「结果物核查」，清单化才能被复核，而不是靠演示。
- **功能**：① 列表筛选：插件 / 状态 / 发起人 / 时间范围；列：任务名、插件、发起人、状态、进度、耗时、创建时间、操作（查看 / 重试）。② 详情结果区固定展示**核查清单**：名称、类型、状态（已核查 / 待人工确认）、链接或下载。清单项固定——研发 4 项（需求要点 / 代码文件 / 用例文件 / 提交记录与合并请求）、内容运营 3 项（三平台稿件 / 排期表 / 发布回执）、行政人事 4 项（JD / 筛选评分表 / 面试提纲 / 公文或 Offer）。③ 只读约束：已完成任务的整体结果**不可被流程改写**，点产物默认只能预览、下载、复制链接；**唯一例外**（见勘误第 9 条 / WF2）：`draft`（稿件/JD/Offer/公文正文）、`doc`（方案文档）、`table`（评分表/排期表）三类产物可由发起人就地编辑并生成新版本，而 `link`（提交记录、合并请求）与 `file`（代码文件）**一律只读**——否则「仓库提交记录可编辑」会直接毁掉本条的核查客观性。
- **端点**：`[扩展]` A2（新增 `plugin_id`、`status`、`initiator_id`、`created_from`、`created_to`）；`[扩展]` A3 `result.checklist[]`（`{name, type, status: verified|pending_manual, link, artifact_id}`）。
- **验收标准**：① 四维筛选各自返回正确子集（4 条断言，含 1 条组合筛选）；② 三插件完成 1 次任务后 `checklist` 项数分别 = 4 / 3 / 4 且名称与本节逐字一致；③ 已完成任务产物卡片无「编辑」入口（DOM 断言）；④ 非发起人且无团队管理权限者访问他人任务 → 无权限错误 + 「你没有权限查看该任务」。

#### 3.2.4 三个标杆插件（P0-P3-15 ~ 23）

> 完整流程表（输入 / 产物 / 失败与人工接管 / 达标判据）见**第 5 章**；本节只列口径与最小断言，第 5 章各节末的「达标判据」是本组需求的最终判定依据。

**P0-P3-15 前端研发工作台：需求输入与方案拆解（DEV）**

- **用户价值**：把「一句话需求」变成可执行的方案，而不是直接吐代码。
- **功能**：表单 = 需求标题（≤80 字）、需求描述（≤4000 字）、目标仓库（下拉，必填）、分支策略（新建分支 / 指定分支）、技术栈偏好（可选）。步骤 1「理解需求」产出要点 ≥3 条；步骤 2「生成技术方案」产出方案 + 影响文件清单，随后**暂停等待确认**（人工接管点 1），可「确认继续」或「补充要求重做方案」（只重跑步骤 2）。
- **端点**：`[复用]` A1 + PL10（插件配置：默认仓库/分支）。
- **验收标准**：① 缺任一必填项 → 提交置灰并指出缺哪项（标题 / 描述 / 仓库 3 条断言）；② 未连接代码仓库时下拉显示「还没有连接代码仓库」+ 连接入口（非空列表、非报错）；③ 步骤 1、2 完成后任务为「等待你确认」；重做方案时步骤 1 不重跑且方案版本 +1。

**P0-P3-16 前端研发工作台：代码与用例生成（DEV）**

- **用户价值**：产物落到具体文件路径，研发能直接审阅而不是复制粘贴。
- **功能**：步骤 3「生成代码文件」产出 ≥1 个文件（含路径与改动内容，路径必须 ⊆ 方案清单）；步骤 4「生成单元测试」产出 ≥1 个测试文件。空产出、路径越界、文件数与清单完全不符 → 该步判失败可重试；页面以「改动内容」呈现（新增/删除行颜色区分）。
- **验收标准**：① 代码文件路径 ⊆ 方案清单（集合断言）；② 测试文件 ≥1 且命名含被测文件名主干；③ 构造空产出 → 步骤 4 未完成并给重试，重试后完成；④ 界面 0 处 `diff`/`patch`。

**P0-P3-17 前端研发工作台：提交到指定仓库并可核查（DEV，AC-02 核心）**

- **用户价值**：交付物不是「看着像代码」，而是仓库里真实存在的一次提交。
- **功能**：步骤 5 提交前**必须**确认（展示仓库名、分支名、将提交文件数，防误提交生产分支），确认后创建提交与合并请求，产出 2 个链接产物；步骤 6 把提交状态写入核查清单。只走已连接的代码仓库工具（复用 T 系列），不新增直连通道。
- **验收标准**：① 未点确认 → 仓库提交数不变；② 确认后 2 个链接产物可打开，抽 1 个文件内容与预览**逐字一致**；③ 仓库授权过期 → 原因「代码仓库的授权已过期」+「重新连接」，重连后重试本步成功；④ 目标分支已被他人更新 → 提示「目标分支已有新的改动，建议新建分支提交」并给「改用新分支重试」。

**P0-P3-18 内容运营工作台：素材与多平台策划（CNT）**

- **用户价值**：先解决「写什么」，再解决「怎么写」；没素材必须说出来而不是硬编。
- **功能**：表单 = 运营主题、目标平台（多选，公众号 / 邮件 / 小红书 / 抖音，≥1）、目标受众、时间窗（必填）、素材来源（知识库 / 上传文件）。步骤 1 产出素材要点 ≥3 条且每条标来源，**无来源时标「未找到可靠素材」**；步骤 2 为每平台产出 1 个角度 + ≥3 标题候选 + 目标字数。单次平台数 ≤4。
- **验收标准**：① 未选平台 → 提交置灰 + 「请至少选择一个发布平台」；② 勾 3 平台 → 3 组选题、每组标题 ≥3；③ 空素材场景下稿件中「据…」「数据显示」类事实表述 0 处；④ 标题字数 公众号 ≤64、其他 ≤40。

**P0-P3-19 内容运营工作台：多平台稿件与配图建议（CNT）**

- **用户价值**：一次成稿、按平台适配，减少来回改写。
- **功能**：步骤 3 每平台 1 篇稿件（标题 / 正文 / 标签，字数达标 ±20%），为**可编辑草稿**（保存产生新版本，旧版本可回看）；步骤 4 每篇 ≥1 条配图建议（描述 + 尺寸），可上传本地图片替换（V1.0 不做图片生成）。
- **验收标准**：① 稿件数 = 勾选平台数且 `platform` 互不相同；② 字数偏差 ≤20%（目标 800 → 640~960）；③ 编辑保存后版本 +1，切回上一版本内容逐字一致；④ 配图建议 ≥1/篇。

**P0-P3-20 内容运营工作台：排期发布与排期表（CNT，AC-02 核心）**

- **用户价值**：交付物是一张能直接交给主管看的排期表，不是几段文字。
- **功能**：步骤 5 生成排期表（平台 / 标题 / 计划时间 / 状态），时间不得早于当前、同日同平台不得重复；步骤 6 对已接入平台（公众号、邮件）发布并写回执，未接入平台（小红书、抖音）标「待人工发布」+ 稿件下载 + 发布指引；发布前一次确认（人工接管点 2）。
- **验收标准**：① 排期表 4 列齐备、行数 = 稿件数；② 计划时间早于当前 → 该步失败并指出冲突行，改时间后可重试；③ 公众号「已发布」且有回执、小红书「待人工发布」且有下载入口；④ 发布失败 → 稿件保留、状态「发布未成功」、可「重新发布」（稿件版本号不变）。

**P0-P3-21 行政人事工作台：JD 与简历筛选初评（HR）**

- **用户价值**：把初筛从「一上午看 20 份」压缩到一次审阅，但结论必须可辩驳。
- **功能**：步骤 1 生成 JD 草稿（职责 / 要求 / 加分项，可编辑保存）；步骤 2 上传简历 ≤20 份（pdf / docx），每份输出 匹配分（0-100）/ 亮点 ≥2 / 风险 ≥1 / 结论（建议面试 | 待定 | 不通过）/ 理由 ≥30 字。**「风险」为空判该行失败**。
- **验收标准**：① 3 份简历 → 评分表 3 行字段齐全、「风险」非空、结论在枚举内；② 第 21 份 → 「一次最多 20 份，请分批上传」；③ 加密或损坏文件 → 该行标「无法读取，请解除保护后重新上传」，其余行正常（部分失败不拖垮整体）。

**P0-P3-22 行政人事工作台：面试提纲与邀约安排（HR）**

- **用户价值**：面试官拿到提纲就能问，邀约不用手工复制粘贴。
- **功能**：步骤 3 为每位「建议面试」候选人产出 ≥5 问（含考察点与参考追问）；步骤 4 选时间 / 面试官 / 渠道（企微 / 飞书 / 邮件）发送邀约并取回日程或消息回执，失败给替代动作（换渠道 / 复制邀约文本手动发送）。
- **验收标准**：① 提纲份数 = 建议面试人数，每题含考察点字段；② 渠道未连接 → 选项置灰 + 「还没有连接企业微信」+ 连接入口；③ 时间与面试官日程冲突 → 提示「该时间段面试官已有安排」并给 2 个可选时间；④ 邀约成功返回日程或回执标识。

**P0-P3-23 行政人事工作台：Offer 文案与行政公文（HR）**

- **用户价值**：公文与 offer 都是对外的正式文件，格式与合规不能出错——尤其是钱。
- **功能**：步骤 5 产出 offer 草稿（岗位 / 部门 / 报到日期 / 试用期 / 福利），**薪资、试用期薪资、股权、奖金等金额字段一律留空并标「请人事填写」，AI 不得生成任何金额**；未填金额不允许导出。模块 B 四类公文（通知 / 会议纪要 / 请示 / 周报）生成正文并可导出文档文件（docx）。
- **验收标准**：① 3 个金额字段为空字符串且页面有「请人事填写」提示；② Offer 全文按**双规则扫描** 0 命中——R1 带单位金额、R2 金额上下文窗口内的裸数字（规则与豁免清单见追溯表 §3.4），固定输入可复现；③ 4 类公文各 1 篇可导出**真 docx 文件**（可解压出 `word/document.xml` 且正文去标签字数 >0；docx 由平台统一生成、插件不自带依赖，见勘误第 6 条）；④ 未填金额点导出 → 提示「请先填写薪资信息」。

### 4.2 逐页要求（仅新增 / 深化）

**① `/plugins` 插件与工作台（深化）**

- 三标签：市场 / 已安装 / 办公工具。市场标签内：搜索框 + 分类横向筛选 + 排序下拉 + 卡片网格（3 列）。

- 错误态：「插件列表加载失败，请重试」。
- 关键交互：卡片「安装」→ 右侧授权抽屉（宽 520px，逐项能力 + 后果说明）→ 底部「同意并安装」；抽屉内能力项可逐项取消，取消必需项时按钮置灰并显示原因。

**② `/plugins/{pluginId}` 插件详情（新增）**

- 区块顺序：头部 / 介绍 / 需要用到的能力 / 执行步骤预览 / 版本历史 / 评价。
- 空态：无评价「还没有人评价，用过后可以来说说」。
- 错误态：「插件信息加载失败，请重试」；插件已下架 → 「该插件已下架」+「返回市场」。

**③ `/workbench/{pluginId}` 工作台宿主（新增，三插件共用）**

- 布局：左侧主区（输入表单 → 执行中的步骤时间线 → 结果区与核查清单），右侧 320px 帮助栏（使用说明、可用能力、最近 3 次任务）。
- 加载态：表单骨架 + 右侧骨架。
- 空态：无历史任务「还没有执行记录，填好上面内容就能开始」。
- 错误态：「工作台加载失败，请重试」；插件已停用「该插件已停用，请联系管理员启用」。
- 关键交互：提交后按钮变「执行中，可离开此页」并显示进度；离开页面任务继续，回来时按服务端状态补齐。

**④ `/workflows` 任务列表（深化）与 `/workflows/{taskId}` 任务详情（新增）**

- 列表：筛选条（插件 / 状态 / 发起人 / 时间范围）+ 表格 8 列 + 分页。
- 详情：状态头卡 / 垂直步骤时间线 / 每步产物卡片 / 结果物核查清单 / 底部动作组（重试本步、从头重试、复制诊断说明）。
- 空态：列表「还没有自动化任务，添加岗位工作台后即可使用」；详情无产物「该步骤没有产出内容」。
- 错误态：「任务详情加载失败，请重试」；无权限「你没有权限查看该任务」。
- 关键交互：步骤点击展开产物；失败步骤默认展开并高亮；「等待你确认」态在页面顶部固定一条确认条。

## 5. 三个标杆插件端到端流程（P0-08 / AC-02）

> 判据原则：**每个插件必须有「离开界面也成立」的结果物**（仓库提交、稿件与排期表、公文文件），页面演示不作为达标依据。

### 5.1 前端研发工作台（适用：R1 研发岗；需要能力 ②③⑤）

| 步 | 步骤标题（用户可见） | 输入 | 输出物 | 失败与人工接管 |
| --- | --- | --- | --- | --- |
| 1 | 理解需求 | 需求标题、描述、目标仓库、分支策略 | 需求要点 ≥3 条（产物：列表） | 需求描述过于笼统 → 提示补充 3 个要素，可重试；不跳过 |
| 2 | 生成技术方案 | 步骤 1 产物 + 目标仓库只读结构 | 方案文档 + 影响文件清单（产物：文档） | **人工接管点 1**：方案需用户确认或补充要求重做（只重跑本步） |
| 3 | 生成代码文件 | 确认后的方案 | ≥1 个代码文件（路径 ⊆ 清单） | 产出为空或路径越界 → 本步失败可重试；连续 2 次失败提示联系管理员 |
| 4 | 生成单元测试 | 步骤 3 产物 | ≥1 个测试文件 | 同上；允许用户「跳过并继续」（标记为待人工补测） |
| 5 | 提交到指定仓库 | 步骤 3/4 产物 + 仓库授权 | 提交记录链接 + 合并请求链接 | **人工接管点 2**：提交前必须确认（显示仓库/分支/文件数）；授权过期（工具授权类错误）→ 「重新连接」后重试本步；分支冲突 → 建议新建分支重试；无能力⑤ → 步骤未完成 + 「去授权」，产物仍可下载 |
| 6 | 结果核查 | 前 5 步产物 | 核查清单 4 项 | 任一项缺失 → 该项「待人工确认」，不允许标为已核查 |

**达标判据（结果物核查）**：① 仓库中存在该提交，且至少 1 个文件内容与产物预览逐字一致；② 合并请求链接可打开且指向同一提交；③ 核查清单 4 项均非「待人工确认」；④ 任务详情可复现上述 3 点（刷新、换设备、次日再查均一致）。

### 5.2 内容运营工作台（适用：R1 内容/市场岗；需要能力 ①②③⑥）

| 步 | 步骤标题 | 输入 | 输出物 | 失败与人工接管 |
| --- | --- | --- | --- | --- |
| 1 | 检索素材 | 运营主题、素材来源（知识库 / 上传文件） | 素材要点 ≥3 条（每条带来源） | 无可靠素材 → 标注「未找到可靠素材」并继续（不编造）；允许用户补充上传后重试本步 |
| 2 | 选题策划 | 主题 + 勾选平台 + 受众 | 每平台 1 角度 + ≥3 标题候选 + 目标字数 | 平台数 >4 时提示缩减（V1.0 单次 ≤4 平台） |
| 3 | 生成稿件 | 步骤 2 产物 + 素材要点 | 每平台 1 篇稿件（标题/正文/标签） | 稿件字数偏差 >20% → 自动重生成 1 次，仍不达标则标「待人工调整」；用户可编辑保存为新版本 |
| 4 | 配图建议 | 稿件正文 | 每篇 ≥1 条配图建议（描述 + 尺寸） | 无建议不阻断，标「建议手动配图」 |
| 5 | 安排发布排期 | 稿件 + 时间窗 | 排期表（平台/标题/计划时间/状态） | 时间早于当前或同平台同刻重复 → 本步失败并指出冲突行；可改时间重试 |
| 6 | 发布 | 排期表 + 已连接平台账号 | 发布回执（已接入）/ 稿件下载 + 发布指引（未接入） | **人工接管点**：发布前一次确认；发布失败 → 状态「发布未成功」+ 「重新发布」（不重新生成稿件）；平台未连接 → 引导连接 |

**达标判据**：① 勾选 3 平台 → 稿件 3 篇、排期表 3 行且 4 列齐全；② 已接入平台有发布回执，未接入平台状态为「待人工发布」且有可下载稿件；③ 排期表可导出（CSV），导出内容与页面一致；④ 24 小时后回看，稿件版本与回执仍可追溯。

### 5.3 行政人事工作台（适用：R1 人事/行政岗；需要能力 ①②③④⑥）

| 步 | 步骤标题 | 输入 | 输出物 | 失败与人工接管 |
| --- | --- | --- | --- | --- |
| 1 | 生成招聘说明 | 岗位名称、部门、职责要点、硬性要求 | JD 草稿（职责/要求/加分项） | 职责要点 <2 条 → 提示补充；JD 可编辑保存为新版本 |
| 2 | 简历筛选初评 | JD + 简历（≤20 份） | 评分表（匹配分/亮点/风险/结论/理由） | 加密或损坏文件 → 单行标「无法读取」不影响其他行；「风险」为空该行判失败重跑 |
| 3 | 生成面试提纲 | 结论为「建议面试」的候选人 | 每人 ≥5 问 + 考察点 + 参考追问 | 候选人为 0 → 步骤跳过并说明「本次没有进入面试的候选人」 |
| 4 | 安排面试邀约 | 时间、面试官、渠道（企微/飞书/邮件） | 日程或消息回执 | 渠道未连接 → 该渠道禁用 + 连接入口；时间冲突 → 建议 2 个可选时间；失败 → 复制邀约文本手动发送 |
| 5 | 生成 Offer 文案 | 岗位、部门、报到日期、试用期、福利 | Offer 草稿（**金额字段留空**） | **强制**：AI 不生成任何金额；未填金额不允许导出，提示「请先填写薪资信息」 |
| 6 | 撰写行政公文 | 公文体（通知/会议纪要/请示/周报）+ 要素 | 公文正文 + 导出文档文件 | 要素缺失 → 提示补齐（列出缺哪几项）；导出失败 → 保留正文可复制 |

**达标判据**：① 从 1 份 JD + 3 份简历走到 3 份提纲 + 1 份 Offer 草稿，链路无断点；② 评分表每行「风险」非空、结论在枚举内；③ Offer 金额字段为空且全文 0 处金额臆造；④ 4 类公文各 1 篇可导出并打开；⑤ 全部产物在任务详情核查清单中可点开。

## 6. 权限与授权模型（增量）

| 层 | 规则 |
| --- | --- |
| 插件可见/可用 | 由「已安装 + 已启用 + 已授权能力」三者共同决定；任一不满足则入口置灰并给原因 |
| 安装权 | 成员可自行添加（Q3-2 默认）；企业级能力（④⑤⑥）需管理员在团队设置开启总开关后方可用，未开启时给「复制申请说明」 |
| 调用权 | 插件执行时以**发起人**身份调用适配层接口，权限按发起人判定（禁止以插件身份越权）；插件不得读取与本次任务无关的数据 |
| 数据边界 | 插件只能拿到本次任务的输入与经由授权能力返回的数据；对话原文、文档全文、其他成员数据不得进入插件上下文 |
| 撤销即时性 | 撤销能力授权 / 停用插件 / 卸载后，下一次调用立即生效（缓存 TTL ≤ 5s，沿用阶段二 §6.3） |
| 审计 | 安装、授权变更、启用/停用、卸载、升级/回退、每次任务执行均写操作记录；运营侧看不到对话内容与文档原文（沿用阶段二 R5 红线） |

## 7. V1.0 范围边界（必须是明确的「不做」，不允许留成「未做」）

> WF2 说明（冻结后补，见勘误第 9 条）：① 缺口来源——P0-P3-19 ③（稿件改字保存、版本 +1、可回看）、P0-P3-21 ①（JD 可编辑保存）、P0-P3-23 ④⑤（金额违规后改字段重新导出）三处都要求"改产物内容"，而 A3/A4 只读，无写产物端点，不补则内容运营与人事两个插件的交付物"只能看不能改"，AC-02 的岗位实用标准站不住；② **只有 `type ∈ {draft, doc, table}` 可编辑**，`link`（提交记录/合并请求）与 `file`（代码文件）**一律只读**；③ **版本只增不删**、历史版本可查看，**不设回退端点**（回退 = 再编辑一次），保证产物链可追溯；④ **保存即重新渲染**，禁止"存了但下载还是旧文件"；⑤ 编辑**不改变任务状态**（`completed` 仍是 `completed`），**不得触发整条流程重跑**；⑥ 保存时**重算内容指纹并重跑敏感信息脱敏**——用户手工粘贴的内容不得绕过脱敏（否则可把手机号/密钥贴进产物、绕开扫描）；⑦ 权限：任务发起人本人，需 Bearer 鉴权 + `Idempotency-Key`。

> PL14 说明（冻结后补，见勘误第 8 条）：① P0-P3-03 ④ 要求「可在『已安装 → 管理权限』增减授权」，而 PL4 只读、**无写授权端点**，不补则这条 P0 只能靠「卸载重装」实现，功能上等于没做；② **`required: true` 的能力不允许撤销**（撤了插件跑不动，应引导「停用」或「卸载」，返回参数类错误）；③ 只改「本人 × 该插件 × 能力」，**登录即可调用**；**管理员改他人授权不在 V1.0 范围**，且不动角色权限点（权限点总数仍 20）；**只能在本人在该插件上已由 PL5 首次授予的能力集合内增减**——未安装直接调 PL14 一律按「该插件还没有添加」拒绝，首次授权仍由 PL5 完成（防「没装就先改授权」的边界，QA 不要把它当缺陷报）；④ 响应返回 `granted_capabilities[]`、`denied_capabilities[]` 与 **`required_capabilities[]`**——前端据后者把「不可撤」项直接置灰并给原因，不许靠前端猜；⑤ **需 Bearer 鉴权 + `Idempotency-Key`**（写接口统一口径，见本附录开头「鉴权与幂等的分工」）。

> PL13 说明：① 权限点 `team:role:manage`（仅 owner / org_admin），需携带鉴权 Key；② **按能力维度存**而非按插件存——「写入代码仓库」与「读取知识库」必须能分别开关，否则关一个死一个（新增插件也不需要改所有插件的配置）；③ 写入后必须返回**全量 6 项**（不只是被改的项），前端据此直接刷新，**禁止前端自行拼状态**；④ 字段名与 PL4 对齐（`capability_key` / `org_switch_enabled` 同义同名字段），读侧**只走 PL4**，团队设置页读法：PL1 取插件列表 → PL4 取 6 项 → PL13 写入 → PL4 回读验证（单一读源）。

> PL5 说明（冻结后补，见勘误第 10 条）：① **首次安装** → `200` + `already_installed=false`；② **已安装再次调用** → `200` + `already_installed=true` + 现状返回，**授权与设置不变**（授权变更一律走 PL14，禁止在安装入口顺手改授权）；③ `already_installed` 为**常驻字段**，禁止只在重复安装时出现（条件字段会让前端拿到 `undefined`、让 QA 的 schema 断言变成「有时有有时没有」）；④ 为何不报错：客户端发出安装、服务端已落库、响应丢失后用户重试——此时返回「该插件还没有添加」与事实相反，会把用户带入重复点击循环；⑤ `16003` 仅用于「未安装却调 `PL6`/`PL7`/`PL8`/`PL9`/`PL10`/`PL12`/**`PL14`**」，**PL5 不再返回 `16003`**。

### A.3 错误码需求（**不指定码值，交架构统一分配**）

> 约束：① 不得与既有 `10001-10005` / `11001-11007` / `12001-12005` / `13001-13006` / `14001-14008` / `15001-15009` / `20001-20008` / `30001-30004` 冲突；② `16001` 曾在阶段二被提议后废弃，**不得复用该值**；③ 前端兜底表以 `code` 为键，同一语义不得出现两个码，同一码的细分文案不超过 2 种。
