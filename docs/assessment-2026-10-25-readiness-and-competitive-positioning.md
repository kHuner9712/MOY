## 摘要

**一句话结论**：Moy 已具备「可演示、可验收、可私有化」的工程底子，但距「可签收、可对外承诺」的商业产品仍差一层**证据链**——八维度中 5 项达 B/C+，性能（D）与部署运维（C-）是硬短板，合规（C）是最大不确定性；同时**竞争分析基线存在结构性空白**，5 个指定对标产品中 2 个在项目文档中零记载、1 个仅一句定位声明，导致 PRD 的 AC-01「与大厂功能清单逐项对照」无法判定。

**三个最重要的判断**：

1. **最大风险不是技术债，是「演示态全绿」**。RAG 真实上传断裂、备份仅单库、支付中间态、PG 口径盲区四项，都会在客户现场首次暴露，且现有 mock 与单副本口径恰好把它们全部掩盖。
2. **性能与部署是「工作量问题」，合规是「决策问题」**。前者内部 2 周可产出证据；后者（Dify 许可、squid GPL 结论、生成式 AI 备案适用性）必须先有书面结论，否则 SaaS 上线时间表不可控。
3. **竞争分析目前不可用于决策**。文档只能支撑一个维度的差异判断（工具接入范式：预定义操作白名单 vs 通用工具调用 + MCP），其余五个维度（功能设计、UX、交互模式、适用场景、差异化定位）对竞品均无记载。差异化定位应改写为「能力整合与交付可控」，而非「功能更全」。

## 2.3 三个可以据文档成立的判断

### J-1 工具接入范式是唯一有证据的结构性差异

| 维度 | Moy | ClaudeCode / Codex |
|---|---|---|
| 工具来源 | 平台预定义操作白名单（六原语，`action_gateway.py:167-176` if/elif） | 通用工具调用 + MCP 生态 |
| 新增工具成本 | 至少改 3 处（YAML + connector + `_CONNECTOR_MODULES`） | 接一个 MCP server（文档：一个 client + 白名单/审批界面） |
| 长尾覆盖 | 弱（能力封闭集合） | 强（生态现成 server） |
| 可审计性 | 强（每个操作是命名原语，天然可审计、可授权） | 弱（通用调用，审计粒度取决于工具自身） |

**判断**：这不是"落后"，而是**用长尾覆盖换可审计可交付**。文档 M7 的"能力天花板远低于"是事实陈述，但结论应是"取舍需显式化"，而非"必须追平"。

**产品含义**：Moy 应把"六原语白名单"定位为**合规卖点**（办公场景下每个动作可授权、可审计、可回滚），同时把 MCP 作为**管理员审批后的扩展通道**（文档 `tech-path-review:52` 已给出方案），而不是替换主路径。这也回答了"为什么不直接做成通用 Agent"——通用 Agent 无法向企业交付"每个动作都可追责"。

### J-2 可嵌入性差异：它们可以被"接进来"，Moy 是"把别人接进来"

文档记载 DeerFlow 支持「Codex CLI / Claude Code 作为模型后端」（`research:117`）。这条事实的产品含义是：**ClaudeCode/Codex 存在"被集成"的产品形态**（CLI 后端），而 Moy 的产品形态是"集成方"（适配层 + 工具连接 + 插件宿主）。

**判断**：二者不必然构成正面竞争。对 Moy 的可执行结论是——与其在通用工具调用上追赶，不如评估"把 CLI 型 Agent 作为 V1.1 的一类执行后端"（与模型矩阵同层），从而借用其长尾能力，同时保留 Moy 的治理与审计外壳。

> 注：该结论基于文档对 DeerFlow 集成方式的记载推导，属**方案建议**而非竞品事实断言。

# 第三部分 综合结论与待拍板事项

## 3.1 四条结论

1. **就绪度**：八维度 5 项 B/C+、3 项 C 及以下、0 项 A。状态是"研发完成度高、签收证据度低"，差距主要在工作量与决策，不在技术能力。
2. **发布关键路径**：3 项内部修复（P0-1 提交、RAG multipart、取消竞态）→ 4 项外部协调（连接器账号、支付口径、目标平台、CI 额度）→ 证据生产（性能/渗透/部署六步/合规三件套）→ Gate 4 复审。内部 2 周、外部 2-6 周。
