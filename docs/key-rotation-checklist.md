# Moy（麦子）V1.0 密钥与凭证轮换清单

| 项 | 内容 |
| --- | --- |
| 适用版本 | V1.0 |
| 适用读者 | 客户运维工程师、DBA、安全负责人 |
| 使用方式 | 按第 1 章的周期表排期，逐项照第 2 章对应条目执行，每项执行后填第 9 章的记录表 |
| 铁律 | **任何轮换都必须在维护窗口内进行，且轮换前完成一次可用备份** |

## 1. 轮换周期建议

| # | 凭证 | 建议周期 | 强制触发条件 | 是否需重启 | 风险等级 |
| --- | --- | --- | --- | --- | --- |
| 1 | 身份服务客户端密钥（OIDC client secret） | 180 天 | 人员离岗、疑似泄露 | 是 | 高（影响全部登录） |
| 2 | 登录令牌签名密钥（JWT secret） | 180 天 | 人员离岗、疑似泄露 | 是 | **高（全站会话失效）** |
| 3 | 数据库超级用户口令 | 180 天 | 人员离岗、疑似泄露 | 是 | 高 |
| 4 | 数据库应用账号口令 | 180 天 | 人员离岗、疑似泄露 | 是 | 高 |
| 5 | 缓存口令 | 180 天 | 同上 | 是 | 中 |
| 6 | 身份服务管理员口令 | 90 天 | 同上 | 否（改库即生效） | 高 |
| 7 | 业务服务内部通信密钥（2 枚） | 180 天 | 同上 | 是 | 中 |
| 8 | 内容处理服务主密钥（Dify secret key） | 180 天 | 同上 | 是 | 中 |
| 9 | **凭据加密主密钥**（AES-256） | 365 天 | 疑似泄露立即 | 是 | **极高（影响全部工具授权）** |
| 10 | 对象存储访问密钥（全量版） | 180 天 | 同上 | 是 | 中 |
| 11 | 模型服务 API Key | 90–180 天 | 供应商要求、用量异常 | 否（下一次调用生效） | 中 |
| 12 | 邮箱 SMTP/IMAP 授权 | 90–180 天 | 邮箱服务商策略、异常登录 | 否 | 低 |
| 13 | 代码仓库（GitHub）授权 | 90 天 | 同上 | 否 | 中 |
| 14 | 企业微信应用凭证 | 90–180 天 | 同上 | 否 | 中 |
| 15 | 飞书应用凭证 | 90–180 天 | 同上 | 否 | 中 |
| 16 | 微信公众号凭证 | 90–180 天 | 同上 | 否 | 中 |
| 17 | 支付渠道密钥（微信支付 APIv3 等） | 365 天 | 支付服务商要求 | 是 | **极高（影响收款）** |
| 18 | 授权许可文件（License） | 按合同 | 席位/期限变更 | 是 | 中 |

> "是否需重启"的准确含义：配置类密钥改的是环境文件，**必须重建容器**才会被读取（`docker compose up -d` 会重建有变化的服务；`restart` 不会重读环境文件）。业务连接类凭证（第 11–16 项）存在数据库里，改完即时生效。

## 2. 逐项轮换步骤

### 2.0 通用前置（每一项都要做）

```bash
# ① 维护窗口声明（回滚/恢复脚本的误操作防护，见部署手册第 8 章）
export OA_MAINTENANCE=1

# ② 可用备份（轮换失败时的唯一退路）
bash deploy/backup.sh

# ③ 记录当前状态（便于对比"改完有没有变差"）
docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite ps > /tmp/ps.before.txt
cp deploy/.env.lite /tmp/env.before            # 含敏感信息，改完即删

# ④ 改完统一重建（不要用 restart）
docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite up -d
```

> 改环境文件的纪律：**先备份、再改、改完逐项 diff**。`cp` 出来的副本含明文口令，**用完立即 `shred -u` 或删除**。

### 2.1 身份服务客户端密钥（OIDC client secret）

| 项 | 内容 |
| --- | --- |
| 配置项 | `OA_KEYCLOAK_CLIENT_SECRET`（以及前端侧 `OA_WEB_OIDC_CLIENT_ID` 对应的客户端配置） |
| 影响面 | 业务适配层向身份服务换取令牌的客户端认证。**密钥错误 = 全站无法登录** |
| 是否需要重启 | **是**（业务适配层必须重建） |

**步骤**

1. 在身份服务管理端，为对应客户端重新生成客户端密钥（**先不要删旧值**，多数身份服务允许暂时并存，或允许回退）；
2. 更新 `deploy/.env.lite` 的 `OA_KEYCLOAK_CLIENT_SECRET`；
3. 重建业务适配层容器：
   ```bash
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite up -d adapter
   ```
4. 验证（三项，必须全过）：
   ```bash
   # ① 业务就绪
   curl -s http://127.0.0.1/api/v1/readyz
   # ② 真实登录一次（浏览器无痕窗口，避免旧会话掩盖问题）
   # ③ 登出后重新登录一次（确认新令牌签发链路完整）
   ```
5. 确认无误后，在身份服务端作废旧密钥。

**回滚**：把 `.env.lite` 恢复为 `/tmp/env.before` 中的值 → `up -d adapter` → 若身份服务端已作废旧密钥，需先在管理端恢复旧密钥。

### 2.2 登录令牌签名密钥（JWT secret）

| 项 | 内容 |
| --- | --- |
| 配置项 | `OA_JWT_SECRET`、`OA_JWT_ALGORITHM`（当前 HS256）、`OA_JWT_AUDIENCE`、`OA_JWT_ISSUER` |
| 影响面 | **所有已登录用户的会话立即失效**（需要重新登录）；产物下载令牌同样依赖该密钥，轮换瞬间已签发的下载链接会失效 |
| 是否需要重启 | **是** |

**步骤**

1. 生成新密钥（长度 ≥ 32 字符，URL 安全字符）：
   ```bash
   openssl rand -hex 32
   ```
2. 更新 `.env.lite` 的 `OA_JWT_SECRET`；
3. 重建业务适配层；
4. 验证：
   - 新登录可用；
   - 旧会话被要求重新登录（**这是预期行为**，提前通知用户）；
   - 重新生成一次产物下载链接可正常下载。

**回滚**：恢复旧值并重建。**注意**：回滚会再次让新旧会话全部失效一次。

**排期建议**：放在下班后或周末，并提前通知全员。

### 2.3 数据库超级用户口令

| 项 | 内容 |
| --- | --- |
| 配置项 | `OA_POSTGRES_USER`（账号名）、`OA_POSTGRES_PASSWORD` |
| 影响面 | 建库/初始化/迁移等需要高权限的动作；**日常业务不依赖它**（业务走应用账号） |
| 是否需要重启 | **是**（数据库容器需以新口令启动；迁移任务也读该变量） |

**步骤**

1. 先在数据库内改口令（容器内执行）：
   ```bash
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite \
     exec -T postgres psql -U officeai -d officeai \
     -c "ALTER ROLE officeai WITH PASSWORD '<新口令>';"
   ```
2. 更新 `.env.lite` 的 `OA_POSTGRES_PASSWORD`；
3. 重建依赖它的服务：
   ```bash
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite up -d postgres
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite up -d adapter dify-api dify-worker plugin_daemon
   ```
4. 验证：
   ```bash
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite ps   # 全 healthy
   curl -s http://127.0.0.1/api/v1/readyz
   bash deploy/backup.sh --out-dir /tmp/rotate-check    # 备份可用 = 连接串正确
   ```
5. **别忘了**：迁移任务（一次性 Job）也使用该变量，轮换后跑一次 `--check` 确认：
   ```bash
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite run --rm migrate
   ```

**回滚**：`ALTER ROLE` 改回旧口令 + 恢复环境文件 + 重建。

**风险提示**：口令含 `@ : / ?` 等字符时需要 URL 转义。**统一使用 `openssl rand -hex 24` 生成**（hex 字符集天然安全）。

### 2.4 数据库应用账号口令

| 项 | 内容 |
| --- | --- |
| 配置项 | `OA_DATABASE_URL`（形如 `postgresql+asyncpg://<账号>:<口令>@<主机>:<端口>/<库>`） |
| 影响面 | **全部业务请求**。口令错误 = 业务就绪探针永远不通过 |
| 是否需要重启 | **是** |

**步骤**

1. 生成新口令：`openssl rand -hex 24`；
2. 改数据库侧口令（用超级用户）：
   ```bash
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite \
     exec -T postgres psql -U officeai -d officeai \
     -c "ALTER ROLE officeai_app WITH PASSWORD '<新口令>';"
   ```
3. 更新 `.env.lite` 的 `OA_DATABASE_URL`（**整条连接串，注意只改口令段**）；
4. **用平台自带的对齐函数避免两侧不一致**：
   ```bash
   bash deploy/validate_lite_up.sh    # 内含"对齐应用角色口令"步骤，以环境文件的连接串为准
   ```
   或直接重建服务后由脚本对齐：
   ```bash
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite up -d adapter
   ```
5. 验证：`/api/v1/readyz` 返回 ready；跑一次对话；跑一次导出（读写都验证到）。

**回滚**：`ALTER ROLE` 改回 + 恢复连接串 + 重建。

**常见错误**：只改了一侧（数据库改了、连接串没改，或反之），表现为就绪探针长期不通过、日志里有认证失败。核对方法：
```bash
docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite logs --tail=50 adapter | grep -i "auth\|password\|role"
```

### 2.5 缓存口令

| 项 | 内容 |
| --- | --- |
| 配置项 | `OA_VALKEY_PASSWORD` |
| 影响面 | 幂等键与频率保护。口令错 = 重复提交保护与限流失效（业务仍可跑，但会退化） |
| 是否需要重启 | **是** |

**步骤**

1. 改缓存服务配置中的口令（编排里以环境变量注入）；
2. 更新 `.env.lite`；
3. 重建缓存服务与业务适配层：
   ```bash
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite up -d valkey adapter
   ```
4. 验证：连续两次提交同一个幂等键，第二次应返回"重复的请求已被忽略"；快速连点触发频率保护提示。

**回滚**：恢复环境文件并重建。**注意**：缓存数据在重建后可能丢失（幂等键与限流计数），这属正常且可接受。

### 2.6 身份服务管理员口令

| 项 | 内容 |
| --- | --- |
| 配置项 | `OA_KEYCLOAK_ADMIN`、`OA_KEYCLOAK_ADMIN_PASSWORD` |
| 影响面 | 仅在需要进身份服务管理端时使用；**不影响终端用户登录** |
| 是否需要重启 | 否（管理端改密即生效）；若通过环境变量首次创建管理员，则需重建 |

**步骤**

1. 登录身份服务管理端，在管理界面修改管理员口令（推荐，避免环境变量与库内不一致）；
2. 同步更新 `.env.lite` 的 `OA_KEYCLOAK_ADMIN_PASSWORD`（保持文档与环境一致，避免下次重建时被旧值覆盖）；
3. 验证：退出后用新口令登录管理端；终端用户登录不受影响。

**回滚**：管理端改回旧口令。

**风险提示**：若环境变量与库内口令不一致，重建身份服务容器时会以环境变量为准（可能覆盖）。这是最容易踩的坑——**改完必须同步环境文件**。

### 2.7 业务服务内部通信密钥（2 枚）

| 项 | 内容 |
| --- | --- |
| 配置项 | `OA_PLUGIN_DAEMON_KEY`、`OA_PLUGIN_INNER_API_KEY` |
| 影响面 | 业务适配层与插件运行服务之间的内部调用鉴权。密钥错 = 工具调用全失败（提示"工具暂时没有响应"） |
| 是否需要重启 | **是**（两侧都要重建，且必须同时） |

**步骤**

1. 生成新值（32 字节 base64）：
   ```bash
   openssl rand -base64 32
   ```
2. 同时更新 `.env.lite` 中两项；
3. **同一个窗口内**重建两侧（顺序错会出现短暂 401）：
   ```bash
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite up -d plugin_daemon adapter
   ```
4. 验证：在设置里点一次"测试连接"（或执行一次只读工具操作，如查看邮件列表）。

**回滚**：恢复旧值 + 同时重建两侧。

### 2.8 内容处理服务主密钥（Dify secret key）

| 项 | 内容 |
| --- | --- |
| 配置项 | `OA_DIFY_SECRET_KEY` |
| 影响面 | 业务适配层调用内容处理服务的签名凭据；**部分加密场景复用该密钥**，轮换后旧加密数据可能需要重建 |
| 是否需要重启 | **是** |

**步骤**

1. 生成新值（≥ 32 字符）：`openssl rand -hex 32`；
2. 更新 `.env.lite`；
3. 重建内容处理服务与业务适配层：
   ```bash
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite up -d dify-api dify-worker adapter
   ```
4. 验证：发一次对话、传一份文档提问（覆盖对话与资料两条链路）。

**回滚**：恢复旧值 + 重建。**若已用新密钥写入了新的加密数据，回滚前先确认这些数据可丢弃或可重建**（工具授权凭证不受影响，它用的是第 2.9 项的独立密钥）。

### 2.9 凭据加密主密钥（**最高风险项**）

| 项 | 内容 |
| --- | --- |
| 配置项 | `OA_CREDENTIAL_ENCRYPTION_KEY`（新主密钥）、`OA_CREDENTIAL_ENCRYPTION_KEYS_LEGACY`（轮换期旧密钥，格式 `1:base64,2:base64`） |
| 影响面 | **全部第三方工具授权凭证的解密**。密钥配错的后果不是"报错"，而是**所有已连接工具显示"该知识库暂时无法访问/授权失效"** |
| 是否需要重启 | **是** |
| 算法 | AES-256-GCM；每条密文自带密钥版本号 |

**轮换原理（务必理解再动手）**：解密时按密文自带的版本号挑选密钥，**加密永远用新主密钥**。主密钥版本号由系统按"旧密钥最大版本 + 1"推导。因此轮换分三步走，**不需要重新录入任何工具授权**：

**步骤**

1. 生成新主密钥：
   ```bash
   python -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())"
   ```
2. 把**当前**主密钥挪到"轮换期旧密钥"（沿用其原有版本号；首次轮换时版本号为 `1`）：
   ```
   OA_CREDENTIAL_ENCRYPTION_KEYS_LEGACY=1:<原主密钥>
   OA_CREDENTIAL_ENCRYPTION_KEY=<新主密钥>
   ```
3. 重建业务适配层：
   ```bash
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite up -d adapter
   ```
4. 验证（**这一步决定成败，不可跳过**）：
   - 打开「插件与工作台」→ 已连接的工具，逐个点"测试连接"，应全部成功；
   - 随便执行一次只读工具操作（查邮件列表/查仓库信息）；
   - 观察日志中是否出现凭据类错误码（应无）：
     ```bash
     docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite logs --tail=100 adapter | grep -i "11007\|credential"
     ```
5. **观察期（建议 7 天）后**：系统已经把所有**新写入**的密文换成新密钥；仍在用旧密钥解密的只有历史密文（未变更过的连接）。
   - 如需彻底清掉旧密钥：让相关工具连接**重新授权一次**（这会以新密钥重写密文），全部完成后再移除 `OA_CREDENTIAL_ENCRYPTION_KEYS_LEGACY` 并重建。

**回滚**：把两项换回原值（新密钥丢弃）并重建。因旧密文一直可解，**回滚是安全的**——这正是保留旧密钥配置的目的。

**绝对禁止**：
- 直接把 `OA_CREDENTIAL_ENCRYPTION_KEY` 换成新值而不保留旧密钥 → 历史密文全部解不开，工具连接全部失效且**不可恢复**（只能全部重新授权）；
- 在维护窗口外做这件事；
- 改动后不做第 4 步验证。

### 2.10 对象存储访问密钥（全量版）

| 项 | 内容 |
| --- | --- |
| 配置项 | `OA_OBJECT_STORE_ACCESS_KEY`、`OA_OBJECT_STORE_SECRET_KEY` |
| 影响面 | 产物与资料文件的读写（全量版）；轻量版用本地卷，**不适用** |
| 是否需要重启 | **是** |

**步骤**：在对象存储管理端新建密钥对并授予同一桶权限 → 更新环境文件 → 重建 `object-store` 与依赖服务 → 验证（上传一个文件能下载回来）→ 确认无误后删除旧密钥对。

**回滚**：旧密钥对在删除前一直可用，直接恢复环境文件并重建。

### 2.11 模型服务 API Key

| 项 | 内容 |
| --- | --- |
| 配置项 | `OA_DEEPSEEK_API_KEY`（或客户选择的服务提供方对应项）；服务侧应用密钥 `OA_DIFY_*_APP_KEY` 系列（默认/编程/长文档/深度推理/降级） |
| 影响面 | 对话与内容生成能力。Key 失效的表现是"智能助手繁忙，请稍后再试"（不会暴露上游错误细节） |
| 是否需要重启 | 否（多数场景下一次调用即生效）；**服务侧应用密钥改动后建议重建一次**，避免进程内缓存 |

**步骤**

1. 在服务提供方控制台新建 Key（**先不要删旧 Key**，保留回退窗口）；
2. 更新 `.env.lite` 中对应项；
3. 若改的是服务侧应用密钥，重建相关服务：
   ```bash
   docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite up -d dify-api dify-worker adapter
   ```
4. 验证：发一次对话；再分别用四种能力档位各发一次（确认四个档位都能用，不是只有一个能用）；
5. 观察 24 小时后删除旧 Key。

**回滚**：恢复环境文件并重建；旧 Key 在删除前一直有效。

**注意**：四个能力档位对应不同的应用密钥。**只改了其中一个**会造成"通用助手能用、编程助手报繁忙"——验证时必须逐档位验证。

### 2.12 邮箱 SMTP/IMAP 授权

| 项 | 内容 |
| --- | --- |
| 配置位置 | **产品内**：「插件与工作台」→ 已添加的邮箱工具 → 配置/重新授权（**不在环境文件里**） |
| 影响面 | 发邮件、看邮件类操作 |
| 是否需要重启 | 否 |

**步骤**

1. 在邮箱服务商侧生成新的授权码/应用专用密码（保留旧值直到验证通过）；
2. 产品内重新连接该邮箱账号（凭证以第 2.9 项的密钥加密后入库）；
3. 验证：发一封测试邮件到自己的另一个邮箱；查看一次收件箱列表；
4. 服务商侧作废旧授权码。

**回滚**：产品内重新用旧授权码连接（旧码在作废前有效）。

### 2.13 代码仓库（GitHub）授权

| 影响面 | 研发工作台的"提交代码/创建合并请求"步骤 |

**步骤**

**回滚**：重新用旧令牌授权（吊销前有效）。

### 2.17 支付渠道密钥（如启用）

| 项 | 内容 |
| --- | --- |
| 配置项 | `OA_PAY_CHANNEL`、`OA_PAY_MCH_ID`、`OA_PAY_API_V3_KEY`、`OA_PAY_CERT_SERIAL`、`OA_PAY_PRIVATE_KEY_PATH`、`OA_PAY_NOTIFY_URL` |
| 影响面 | **收款**。私钥或 APIv3 密钥错误 = 下单失败或回调验签失败（表现为"支付结果未确认"） |
| 是否需要重启 | **是** |

**步骤**

1. 在支付服务商商户平台申请新证书/新 APIv3 密钥（保留旧证书直至验证通过）；
2. 更新环境文件与证书文件路径（证书文件权限收紧为仅运行用户可读）；
3. 重建下单相关服务；
4. 验证：**先小额真实下单一次**（如最低价套餐）→ 确认支付成功 → 确认订阅状态自动刷新 → 确认账单生成；
5. 商户平台停用旧证书/旧密钥。

**回滚**：恢复旧证书与密钥并重建（旧证书停用前有效）。**这一类轮换必须有支付渠道对账人员在场**。

## 3. 轮换后的统一验证（每次都做这 6 项）

| # | 检查 | 命令/操作 | 期望 |
| --- | --- | --- | --- |
| 1 | 服务状态 | `docker compose -f deploy/docker-compose.lite.yml --env-file deploy/.env.lite ps` | 9 个常驻服务全部 healthy |
| 2 | 入口健康 | `curl -s http://127.0.0.1/healthz` | `ok` |
| 3 | 业务就绪 | `curl -s http://127.0.0.1/api/v1/readyz` | `ready` |
| 4 | 登录 | 浏览器无痕窗口登录 | 成功，能看到工作区 |
| 5 | 对话 + 资料 | 发一句话；对一份已处理文档提问 | 有回答；引用可点开 |
| 6 | 工具 | 逐个"测试连接"已连接的工具 | 全部成功 |

任一项失败 → 按对应条目的"回滚"执行，**不要在生产上边试边改**。

## 4. 轮换期的三条禁令

1. **禁止在同一个维护窗口轮换 3 项以上**。出问题时无法区分是哪一项造成的。
2. **禁止"先删旧凭证再验证新凭证"**。除明确"重置即失效"的平台（企微/飞书部分应用类型/支付证书）外，一律保留旧值到验证通过。
3. **禁止把凭证写进工单、聊天记录、截图的文本里**。改完 `cp` 出来的环境文件副本必须立即删除。

## 7. 泄露应急处置（与常规轮换的区别）

若怀疑某凭证已泄露，**不要按周期流程慢慢走**，按下列顺序：

| 顺序 | 动作 | 时限 |
| --- | --- | --- |
| 1 | **先在源头吊销/重置**（不等验证） | 立即 |
| 2 | 停入口，阻断正在进行的滥用 | 立即 |
| 3 | 按对应条目更新配置并重建 | 30 分钟内 |
| 4 | 查操作记录，确认异常调用范围（按时间窗、操作者、IP 掩码） | 2 小时内 |
| 5 | 按《数据处理协议》第 8 条通知客户安全接口人 | 24 小时内 |
| 6 | 复盘并补充控制措施 | 15 个工作日内 |
