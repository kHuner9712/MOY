### 2.0 继承自 B19 的 PG 路径缺陷（本批实测，非 B20 引入）

用静态扫描（同一脚本分别对三个取证点）核到：

| 取证点 | `INSERT INTO {TASK_TABLE}` 列/值 | 含 `queue_position` | 结论 |
| --- | --- | --- | --- |
| `b6effcf`（**B19 交付提交**） | **25 / 24** | **是** | **引入点** |
| **`HEAD`（已提交）** | **25 / 24** | **是** | **缺陷仍在** |
| 工作区（`M`，未提交） | 23 / 23 | 否 | 修复**未落库** |

**后果**：PG 模式下 `create_task()` 会因列数不匹配 + 引用不存在的列而 **100% 失败**；内存实现全绿，因此 B19/B20 的骨架与门禁都发现不了。

**为什么必须在 B20 报告里出现**：它解释了两件事——
1. **为什么 B19 判 PASS 却仍产出不可用的 PG 路径**：`create_task` 的 PG 分支不在任何测试里（`task_repo` 分支覆盖仅 25.00%）；
2. **为什么"覆盖率挂账"不是数字游戏**：正是这段未覆盖路径，藏着一条 100% 失败的生产代码。

> **复盘应落在判据、不落在人**：B19 判 PASS 的判据里**缺一条「PG 分支必须被执行」**——当时的签收集合（骨架红数 / 门禁 / 覆盖率）没有一项要求"仓储的 PG 实现走过一次"，所以缺陷不是被漏看，而是**没有判据能看见它**。
>
> **故立为门禁（B21 起）**：**仓储类模块的签收必须包含「PG 实现至少执行过一次」的存在性证据行**——**不是覆盖率数字，是「这条路径被执行过」的存在性证据**。
> 理由：覆盖率是**程度**（87% / 74%），「执行过没有」是**存在性**；B19 的问题不是覆盖率低，而是**这条路径一次都没跑**。**存在性判据比程度判据更容易做到、也更难造假。**

> 建议台账记 **`P3-B19-04`**（**P0**，`due_batch=B21`，`due_action=修复提交落库 + PG create_task 用例走通（写后读回全字段）`）。（编号由 team-lead 定：`P3-B19-01` 已被「推进未执行」占用。）
> **闭合条件是"已提交 + 用例走通"**，不能只看工作区——本轮"工作区改了但 HEAD 没改"是最典型的"看起来修好了"。

**分支点规模（决定"百分比"是否可用的前提）**：

| 模块 | 分支点 | 未覆盖分支 | 分支覆盖 | 单分支权重 | 声明 ≥60% 需覆盖 | **生效阈值**（`ceil(0.60×N)/N`） | 偏差 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `task_repo.py` | **88** | 66 | 25.00% | 1.14pp | 52.8 → **53** | **60.23%** | +0.23pp |
| `plugin_repo.py` | 72 | 34 | 52.78% | 1.39pp | 43.2 → **44** | **61.11%** | +1.11pp |
| `artifact_repo.py` | **24** | 18 | 25.00% | **4.17pp** | 14.4 → **15** | **62.50%** | **+2.50pp** |

> **声明阈值 ≠ 生效阈值（离散化自动收紧）**：`≥` 类离散指标的真实要求是 `ceil(阈值×分母)/分母`。
> `artifact_repo` 只有 24 个分支点 → **实际被要求 62.5%，而非 60%**（多 2.5pp），而报告上写的是 60%。
> **这与"取整向下＝悄悄放水"是同一枚硬币的两面**：放水会被怀疑，**而"可达性自动向上取整"没人会怀疑，因为它看起来正好是 60%**。
>
> **规则**：**偏差 > 2pp 必须在报告里显式写出生效阈值**（本例仅 `artifact_repo` 触发）。
> 语句侧同样存在但极小（85.22% / 85.14% / 85.06%，+0.06~0.22pp）；全局合并分母大（N=9453），偏差仅 +0.004pp。

**两条实现层判据（否则"读数与判定不一致"）**：

1. **判定式必须用整数比较，不要比浮点百分比**：
```python
ok = covered * 100 >= threshold_pp * total      # ✅ 整数比较
# ok = covered / total >= threshold_pp / 100    # ❌ 浮点：87.9999999 显示 88.0 却判 <88
```
> 这类错的可怕之处：**它只在恰好落在边界浮点时出现**，而报告上显示的是 `88.0`——**"显示达标、判定不达标"，永远查不出来**。

2. **偏差上限 = 1/分母 = 单分支权重**（表中"单分支权重"与"偏差上限"是同一个数）：
| 分母 | 1 单位 = | 是否必须披露 |
| --- | --- | --- |
| 9453（全局） | 0.011pp | 不必 |
| 88 / 72 | 1.14pp / 1.39pp | 看情况 |
| **24** | **4.17pp** | **必须** |

> **所以"要不要写生效阈值"不看阈值高低，看分母大小**——全局偏差只有 +0.004pp，正是因为分母太大，离散化几乎不存在。

**三条报告级硬要求（数字必须可当场复核）**：
1. **每个百分比必须能由报告内给出的 `(covered, total)` 当场算回**——算不回的数字不得出现（把复算从"重跑一遍"降为"同页做除法"）；
2. **同一判定链的分子分母必须来自同一次 `coverage run` 的同一文件**——"分子来自 A 次、分母来自 B 次"是本轮最难查的一类错；
3. **本项目当前依赖 `--cov-fail-under` 与 `coverage report` 输出，无自算百分比**；**若将来引入脚本判定，必须用整数比较**（`covered*100 >= th*ceil` 形式）——"没触发 ≠ 不需要写"，下一个写脚本的人不会翻这轮对话。

三者均 ≥20 个分支点，**按百分比判是可行的**；但 `artifact_repo`（24）已接近小分母边界——**单分支权重 4.17pp，少测一个分支掉 4 个点**。

> **补一条判据（适用于将来新增模块）**：**分支点 < 20 的模块，用「未覆盖分支数 ≤ 1」判，不用百分比**。
> 理由：**百分比在小分母上不是"程度"，而是"单点"**——2~5 个分支的模块，错 1 个就是 50~80%，直接不达标；
> 而小分母模块常常恰是**关键开关点**（一个 `if` 决定降级与否）。
> 这与"聚合指标掩盖单点塌陷"是**同一枚硬币的两面**：**聚合会掩盖，小分母会放大**，两者都要换判据，而不是调阈值。

**覆盖率进判定前必须"平账"（2026-10-23 定）**：
> `covered_branches + missing_branches == num_branches`（`partial` 归入 `missing`，**不得二次扣减**）；
> 语句侧同理 `covered_lines + missing_lines == num_statements`。**不能平账的百分比，不管多好看，都是算错了。**

本报告的四个数即可自证：`2170 + 670 = 2840`、`69 + 29 = 98`、`12542 + 1272 = 13814`、`320 + 46 = 366`。

**平账只保证"内部一致"，不保证"范围正确"**——`omit`/`source` 配错会漏掉整个文件，**分母缩水，等式照样平**。故必须同时给范围元数据：
```
source=["app"] | omit=["*/tests/*","*/__main__.py"] | 覆盖文件数 117 | 总语句 13814 | 总分支 2840
```
> **平账防"算错"，`source/omit` 防"算漏"——两种不同的错，不能互相替代。**

**"最小过线"必须标为脆弱点，且余量必须用整数单位表达**：
```
需覆盖 = ceil(76.6% × 2840) = ceil(2175.44) = 2176
补后 covered = 2176
余量 = 2176 − 2176 = 0 个分支      ← 不是"0.02pp"，是"零"
```
> **"0.02pp"会让人以为还有一点点余量；"0 个分支"才是真实：一个分支都不能掉。**
> 百分比是派生值，**余量也必须是派生的整数**——与"判定用整数比较、不用百分比"同一条：
> `covered >= ceil(threshold × total)`；`余量 = covered − ceil(threshold × total)`（单位：个分支/条语句）。
**余量必须"每档一个"**（四档各有自己的 `need`，只给一个会让人误以为其它档也零余量）：

| 档位 | covered | total | 门槛 | need = ceil(门槛×total) | **余量（整数）** |
| --- | --- | --- | --- | --- | --- |
| 总 `app/*`（合并） | 14712 | 16654 | 88% | 14656 | **+56** |
| `business+db`（合并） | 8417 | 9512 | 86% | 8181 | **+236** |
| **分支底线** | 2170 | 2840 | 76.6% | 2176 | **−6** ❌ |
| `task_repo` 语句 / 分支 | 320 / 69 | 366 / 98 | 85% / 60% | 312 / 59 | **+8 / +10** |
| `artifact_repo` 语句 / 分支 | 149 / 18 | 155 / 24 | 85% / 60% | 132 / 15 | **+17 / +3** ⚠ |
| `plugin_repo` 语句 / 分支 | 390 / 65 | 397 / 72 | 85% / 60% | 338 / 44 | **+52 / +21** |

> **符号约定**：**余量 ≥ 0 达标、余量 < 0 未达标**（写成负数，一眼看出差多少）；**不用"pp"、"几乎达标"这类词**——**余量是整数，负号就是红线**。
> 注意 **`artifact_repo` 分支只有 +3**（24 个分支点、单分支权重 4.17pp）：**它和分支底线一样属薄余量档**，只是还没翻红。

**薄余量的机制（为什么它一定会恶化）**：
```
新增 k 个未覆盖分支 → total' = total + k（covered 不变）
need' = ceil(th × total')   ↑ 变大
余量' = covered − need'     ↓ 变小
```
> **"多写代码"本身就会吃掉余量**——而写代码是开发常态，不是异常。
> `artifact_repo`：`18/24`、`need 15`、余量 **+3**；**再加 4 个未覆盖分支 → need 17、余量 +1**。
> **它不是"现在很危险"，是"下一次重构就会危险"——而它现在是绿的，所以没人看。**

**两条机械化规则**：
| 规则 | 内容 |
| --- | --- |
| **观察项** | **余量 ≤ 3（整数单位）→ 列观察项**，报告单列并挂 `due_batch` 补余量 |
| **趋势** | **余量记入 append-only 序列**（每批一个整数），看是否**单调下降**——`+3 → +2 → +1` 比单点 `+3` 早两批预警 |

> **单批 +3 不可怕，"每批掉一点"才可怕，而它永远不会触发阈值**——这是"温水"型退化：**阈值抓不到，趋势抓得到**。
> 与 `red` 的"append-only + 单调不增"是同一个手法：**给会缓慢恶化的量一条序列，而不是一个点。**

**`omit` 的校验位 = 文件数**（不是装饰）：
```
文件数=117（源=117，差 0）    ← 实测：find app -name "*.py" = 117，app/ 下无 __main__.py
```
> **覆盖文件数 ≠ 源文件数 → 分母被 `omit` 悄悄改过**；把差写出来（差 0 才叫干净），`omit` 这条"错了不显形"才有抓手。

**报告行模板（三个"不写就等于没验"的字段必须同现）**：
```
coverage[档位] covered=C | total=T | partial=P | 门槛=th% | need=ceil(th×T) | 余量=±k（整数，单位：分支/语句）
src=["app"] | omit=["*/tests/*","*/__main__.py"] | 文件数=117 | SHA=<冻结点> | 运行状态=passed/failed/killed
```
> `SHA`（哪棵树）、`余量`（够不够）、`omit`（分母对不对）**三者缺一，此行不可被别人复算**；`omit` 不写时分母错了也看不出来。
> **`killed` 单列**：跑挂是"**没结论**"，既不是 failed 也不是 passed，不得混入 failed 计数。

> **任何无关改动（删一条断言、加一个分支）都会让它在下一批回落**；且"刚好过线"在报告里与"有余量"看起来一模一样——
> **数字不携带"余量"这件事，除非报告模板强制一列「余量（整数）」**：把"要记得写"变成"字段必填"，才是根治。
> 处置：**先过线，但必须在报告里写明"本次为最小过线，属已知脆弱点"并挂 `due_batch` 补余量**；
> 否则下一批看到 76.62% 会以为这是稳定水位，继续"差多少补多少"——**门禁退化为算术游戏，优化的是指标不是行为。**
> **`partial` 的归属是这套账里最容易错的一格**：本轮 `-2-2` 把 partial 当"已覆盖"二次扣减，

> **第 6 条为何比"`git log <sha> -- <path>` 非空"更强**：后者只证明**某个**提交碰过该文件（可能是个更早的无关提交），

## 8. `P3-B21-01`（P2，测试缺陷）：日志捕获的顺序依赖

**症状**：`test_pg_error_surfacing` **单跑绿、全量红**（`assert []`：一条日志都没抓到）。

**真因**（`app/core/logging.py:131-136`）：`structlog.configure(..., cache_logger_on_first_use=True)`。
`error_handler` 的 `logger` 是**模块级对象**，一旦首次使用就把处理器链**缓存**；
`capture_logs()` 靠 `structlog.configure(processors=[LogCapture()])` 生效，**对已缓存的 logger 无效**。

| 场景 | 结果 | 原因 |
| --- | --- | --- |
| 单跑 | 绿 | 首次使用，恰好绑在捕获配置上 |
| 全量 | 红 | 前面的用例已让该 logger 缓存了处理器链 |

**修法**：**spy 模块级 logger**（`monkeypatch.setattr(error_handler_module, "logger", spy)`），断言
"处理器交给了 logger 什么"（`exception_type` / `sqlstate` / `exc_info`），而不是"日志框架最终输出了什么"——
与 `c5`（spy 包住 `sanitize` 断是否被调用）同一种做法，与 structlog 的缓存/配置彻底解耦。

**计数方法分级（`[grep]` vs `[run]`）**：
> `[grep]` **只能产出布尔值（在 / 不在），不能产出计数**——**不是精度低，是类型不同**。
> 所以 `[grep]` 仅可用于"整组是否存在"的初筛；**任何"组内缺几条"的结论必须是 `[run]`**。
> 否则会出现"用 grep 的数去填 36/42 这种计数位"——**数看着有，方法不支持。**

**两版教训**：
1. 第一版改成"先 `TestClient` 再 `capture_logs`"，**单跑 + 879 合跑都绿，但全量仍红**；
2. 所以：**根因假设也必须用"改完能否复现绿"来验证**——只凭"解释得通"就宣布根因，
   与"看起来绿了就算过"是同一类错。**局部绿当全绿，是这轮被反复点出的毛病，这次犯在我自己的用例上。**

## 10. 三条跨批可复用的判据（2026-10-23）

**10.1 先归类、再计数**：样本计数**不能按字符串全局检索**——同一个字符串在不同组里语义不同
（`EMP1234` 在⑤是"被剥离"，在⑧是"顺序"；`PO2024001` 属⑤，`PO2024001-2025001` 才属⑧）。
> 本轮 `36 → 34` 的错就是"全局 grep 计数"：把 ⑤ 的样本重复计入 ⑧。**通则：先按组归类，再在组内计数；计数必须 `[run]`，`[grep]` 只出布尔。**

**10.2 表头必须写单位**：
```
识别层  用例数=44  passed=44   |   样本数=42  在库=34  缺口=8
```
> `44` 与 `34` **都真但单位不同**（用例 vs 样本）；**单位进表头，不靠正文解释**——否则会重演"36 vs 34"。

**10.3 "最不利位置法"**：把被测用例放到**最会污染其前置状态的位置**再跑。
| 场景 | 最不利位置 |
| --- | --- |
| 日志 / spy 类 | 排在大量触发日志的用例**之后** |
| 缓存 / 单例类 | 排在会**污染全局状态**的用例之后 |
| 时间 / 随机类 | 排在使用**假时钟 / 固定种子**的用例之后 |

> `0 failed` 只证明"**这一次**顺序没问题"；**"最不利位置仍绿"才证明"不依赖顺序"**。
> 与"改坏即红"是同一层证明强度：一个证明"能红"，一个证明"不靠运气"。

**平账自证**：`covered_branches 2176 + missing_branches 664 = 2840 = num_branches` ✅
（`num_partial_branches = 436` **是"该行有分支未走通"的行数，`⊆ missing`，不得从 total 减**。）

> **`partial` 归属错误本轮出现 3 次，同一根因**：

| # | 错法 | 数学形态 |
| --- | --- | --- |
| 1 | `(total − missing) − partial`（`-2-2` 92.9%） | partial **被减两次** |
| 2 | `(total − partial)`（lead 84.65%） | partial **被当已覆盖** |
| 3 | ⑤ 组字符串算进 ⑧（本文样本 36/42） | 同一元素**计两次** |

> **三种形态、一个根因：没有先声明"集合从属关系"就做加减**——**「子集重复排除 / 重复计入」**。
> 这也解释了为什么"四元组一算就露"：**四元组把 `partial ⊆ missing` 显式写进了等式**。
> **通则：凡计数类结论，先验恒等式，再谈数值**（`covered + missing == total`、`在库 + 缺 == 应有`）。
> **两条都是纯加法、10 秒可做；它们能同时挡住三个人犯的三种错——这正是机械检查相对"仔细核对"的价值：不依赖谁认真。**
>
> **为什么平账比重算更强**：**它不检查"算得对不对"，只检查"算完还在不在全集里"**——
> **重算会重复同一个错误假设，而平账不会。**（本轮 `-2-2`、lead、本文作者三人在不同地方犯同一个错，
> 却都能被一眼看出，正因为三个错**都不满足平账**，而平账不问你用的是哪个算法。）

**观察项（必须被看见）**：**分支余量 = 0** → `due_batch=阶段四首周`、`due_action=分支余量补到 ≥50 条`。
> **0 不是红，但它意味着"删掉任何一个用例就会掉回红"**；按"余量 ≤3 入观察项"的规则，它是最高优先级的观察项。

> **每份判定必须写明冻结树**；否则同一项目会因"换棵树"得出两个相反的结论。


**10.4 三类错误与对策（本轮全部踩过，按发生顺序）**：
| # | 形态 | 对策 |
| --- | --- | --- |
| 1 | **取数端**：把工作区当树 / 把命令行当配置 / 把全文当列清单 | **载体三问**（哪棵树·哪个文件·哪一层）+ 读数**带时间戳** |
| 2 | **计数端**：先算后归类（36/42 把⑤算进⑧；清单把"机制"算进"口径"） | **先归类再计数** + **平账**（`在库 + 缺 == 应有`） |
| 3 | **引用端**：引用"我刚才看到的那版"（台账已改、文档已更新） | **引用具体行前先 `git log -1 -- <file>` / `sed -n` 现读一次**，不引用记忆中的版本 |

> **第 3 条是"引用"这个动作本身的缺陷**，不是谁不认真：**任何转发都会把"某一刻的读数"变成"当前事实"**。
> 这也是"出处双向规则"（取数者附 SHA、引用者要出处）能成立的原因——**它给引用端也装了一个校验位**。

**引用端的落地形态：`引用即抄录`**——凡引用具体行，**必须把该行内容（或关键片段）抄进自己的句子，并附 `文件:行`**：
- ❌ "台账里写的是 84.65%"
- ✅ "台账 `expected_xfail.py:101` 现文为「`covered_branches 2176 / num_branches 2840 = 76.62%`」"

> **抄录这个动作强制你打开文件**：要贴那行字就必须读当前版本，**读完就发现它已经变了**；
> 而"引用一下结论"不需要打开任何文件，**所以它永远不会发现版本变了**。

**它顺手解决了单位丢失——两者其实是同一个动作**：抄「**44 个用例 / 34 个样本**」时，**单位没法和数字分离**；
而写"44 passed"就是**把单位丢掉的过程**。**所以"单位丢失"与"版本失配"同源：都是"转述而不抄录"。**

| 端 | 校验位 |
| --- | --- |
| 取数端 | 附 **SHA + 分母 + 时刻** |
| **引用端** | **抄录原行 + `文件:行`**（抄录即重读） |
