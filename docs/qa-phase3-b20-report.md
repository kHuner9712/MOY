### 2.0 继承自 B19 的 PG 路径缺陷（本批实测，非 B20 引入）

用静态扫描（同一脚本分别对三个取证点）核到：

| 取证点 | `INSERT INTO {TASK_TABLE}` 列/值 | 含 `queue_position` | 结论 |
| --- | --- | --- | --- |
| `b6effcf`（**B19 交付提交**） | **25 / 24** | **是** | **引入点** |
| **`HEAD`（已提交）** | **25 / 24** | **是** | **缺陷仍在** |
| 工作区（`M`，未提交） | 23 / 23 | 否 | 修复**未落库** |

**后果**：PG 模式下 `create_task()` 会因列数不匹配 + 引用不存在的列而 **100% 失败**；内存实现全绿，因此 B19/B20 的骨架与门禁都发现不了。

**为什么必须在 B20 报告里出现**：它解释了两件事——
1. **为什么 B19 判 PASS 却仍产出不可用的 PG 路径**：`create_task` 的 PG 分支不在任何测试里（`task_repo` 分支覆盖仅 25.00%）；
2. **为什么"覆盖率挂账"不是数字游戏**：正是这段未覆盖路径，藏着一条 100% 失败的生产代码。

> **复盘应落在判据、不落在人**：B19 判 PASS 的判据里**缺一条「PG 分支必须被执行」**——当时的签收集合（骨架红数 / 门禁 / 覆盖率）没有一项要求"仓储的 PG 实现走过一次"，所以缺陷不是被漏看，而是**没有判据能看见它**。
>
> **故立为门禁（B21 起）**：**仓储类模块的签收必须包含「PG 实现至少执行过一次」的存在性证据行**——**不是覆盖率数字，是「这条路径被执行过」的存在性证据**。
> 理由：覆盖率是**程度**（87% / 74%），「执行过没有」是**存在性**；B19 的问题不是覆盖率低，而是**这条路径一次都没跑**。**存在性判据比程度判据更容易做到、也更难造假。**

> 建议台账记 **`P3-B19-04`**（**P0**，`due_batch=B21`，`due_action=修复提交落库 + PG create_task 用例走通（写后读回全字段）`）。（编号由 team-lead 定：`P3-B19-01` 已被「推进未执行」占用。）
> **闭合条件是"已提交 + 用例走通"**，不能只看工作区——本轮"工作区改了但 HEAD 没改"是最典型的"看起来修好了"。

### 2.1 定性结论（必须与"功能面全绿"一起读）
- 未覆盖集中在 **`task_repo` / `plugin_repo` / `artifact_repo` 三个 PG 实现**（合计 329 条，占总缺口 **33%**）；
- 且这些未覆盖是**整段方法**（如 `task_repo` 的 `586-612`、`645-656`、`685-708`、`724-750`、`839-871`），**不是零散异常分支**；
- **因此："功能面全绿"的准确表述是 —— in-memory 实现全绿；PG（生产）实现路径覆盖率 `task_repo 47.81% / artifact_repo 60.67% / plugin_repo 67.80%`。**

> **风险**：两条实现并存时，**只验一条的绿不构成通过**（与 B21 要求的"迁移双路径、两条都要能红"同源）。

**分支覆盖是更硬的短板**：三个 PG repo 的分支覆盖分别是 **25.00% / 25.00% / 52.78%** ——
**错误分支与决策路径基本未被走过**，这比"少写几个断言"严重，也解释了为什么"SQL 列数不匹配"这类缺陷能在内存全绿的情况下存活到 PG 侧才暴露。
