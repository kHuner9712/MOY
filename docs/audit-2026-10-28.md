## 一、整体评估

**结论：工程质量明显高于同类项目平均水准，架构红线被真实执行而非口头约定；但存在 1 个上线阻断级资源泄漏和一批「半成品接线」问题，接入真实流量前必须先清 P0/P1。**

做得好的（有真实实现与测试背书）：

1. **架构纪律**：`httpx` 仅存在于 `app/clients/`，`services/*` 只经 `DifyClient` 调底座，全仓确认无第二出口；前端 fetch 仅在 `api-client.ts`（2 处）与 `oidc.ts`（可注入），黑盒化禁词只出现在被豁免的注释里。
2. **安全设计**：错误码注册制 + fail-closed 判权 + RLS 双保险（事务级 `set_config` + BYPASSRLS 启动自检）；前端 PKCE/S256 + state 校验 + 开放重定向防御实现严谨。
3. **工程化**：7 个前端门禁脚本带自检；迁移有台账 + checksum 漂移检测 + 双路径实跑门禁；CI 权限最小化、超时/并发取消齐备；compose 密钥全部 `${VAR:?}` 缺失即拒启，`.env.example` 无真实凭证，Dockerfile 非 root。
4. **注释文化**：大量「审计编号 → 根因 → 修复」留痕，可追溯性强。

三大短板（本次审计主线发现）：

1. **资源生命周期失控**（P0-1、P1-2）：连接池/流式响应无人关闭，真实流量下必然耗尽句柄。
2. **「已造好但没接线」的半成品**：Redis 幂等/限流后端、U4/U5 权限点、前端会话列表、SaaS 沙箱接线——配置与实现互相撒谎。
3. **多路径漂移缺乏机械防线**：三份 compose（private/saas/lite）复制粘贴漂移，G-34 门禁只比两份且判据太窄，本次多个部署问题均为它的漏网形态。

## 二、问题清单

### P0（上线阻断，1 项）

**[P0-1] model_service 每请求泄漏一个 httpx 连接池**
- 位置：`apps/adapter/app/services/model_service.py:536-559` + `apps/adapter/app/clients/dify_client.py:87-92`
- 问题：`_dify_for()` 每次调用 `DifyClient.for_app_key()`，后者构造函数里 `client is None` 时新建 `httpx.AsyncClient`（`_owns_client=True`，上限 100 连接/20 keepalive）。`generate()` 与 `generate_stream()` 每请求各创建一个且从不 `aclose()`（全仓只有 `memory_extractor.py:280` 主动关闭）。
- 影响：`OA_DOWNSTREAM_ENABLED=true` 后按 QPS 耗尽 fd/端口，最终整站不可用。现有单测全部 monkeypatch `for_app_key`，恰好绕开了这条泄漏路径，测试全绿掩盖了它。
- 建议：按 app_key 缓存客户端实例（`dict[str, DifyClient]`）；或改用 `dify_client.py:162` 已原生支持的「单例客户端 + 每请求 effective_key 覆盖」模式（与 rag_service 一致）。

**后端**

- **[P1-1] U4/U5 无权限点校验**：`app/services/identity_service.py:285-327, 356-393`。`invite_member`/`upsert_role` 函数体只有 org_id 非空与席位校验，无 `require_point`；而权限矩阵定义了 `team:member:invite` / `team:role:manage`（`app/core/builtin_roles.py:48,51`），member 角色不含这两点——即任意普通成员可邀请成员、创建角色。对比同文件 U6（417 行）与新路径 `business/member_service.py:241`、`role_service.py:118` 均有校验。修复：服务入口补 `guard_permission`，并加权限矩阵负向测试（`tests/integration/test_endpoints.py:640-685` 目前只有 happy path）。
- **[P1-2] 流式响应无 try/finally，消费者中途退出即泄漏**：`app/clients/dify_client.py:450-452`。`async for ... yield` 后才 `aclose()`，客户端断开/GeneratorExit 时永远走不到。修复：`try: async for ... finally: await response.aclose()`。

## 三、架构与规范一致性专项

| 规范 | 结论 |
| --- | --- |
| 适配层唯一原则（禁直连底座） | ✅ 通过。httpx 仅在 clients/ |
| 统一响应 {code,message,data} + 错误码注册制 | ✅ 通过，有门禁；唯一瑕疵是 STATUS_MAP 不分域（P2-6） |
| Bearer + X-Tenant-Id | ✅ 基本通过（逐端点核对 Depends）；例外：/metrics 免鉴权（P2-1） |
| Idempotency-Key + ULID | ✅ 通过；但 Redis 后端未接线（P1-4） |
| OA_ 前缀 + structlog JSON | ✅ 通过；OA_DIFY_MEMORY_APP_KEY 缺登记（P2-22） |
| 前端黑盒化 | ✅ 通过（可执行代码层面）；OpenAPI tags 与注释残留术语（P3） |
| 统一组件库 | ⚠️ 3 处裸 input（P2-13） |
| 双路径（saas/private）一致性 | ❌ 未通过：sandbox 接线、beat、etcd、healthcheck、maxmemory 等多处漂移（P1-10 等），且 G-34 门禁不含 lite、判据不足 |
