## 一、审计范围、方法与局限

**方法（全程只读）**：代码与配置静态审读；`git ls-files` / `git log` 溯源；AST 自写脚本做「孤儿模块 + 文件级循环依赖」检测；`wc` + AST 统计「总行 / docstring 行 / 有效代码行」；把 5 个仓库自带门禁**实跑**（`validate_import_directions.py`、`validate_images.py`、`validate_openapi.py --strict`、`validate_deps.py` + `--self-test`、`validate_gate_wiring.py`、`export_plugin_contract.py --check`、`check-plugin-contract.mjs --generated`）；`uv lock --check`（只读校验）；在**临时目录**复现 web 镜像 `deps` 阶段的 `npm ci`（不改动仓库，`git status` 全程干净）。

**局限（明确声明）**：

1. 未安装任何依赖、未执行 `uv sync` / `npm ci` 于仓库内、**未启动或重建任何容器**、未做全栈冒烟（仅用 `docker image inspect` / `docker ps` 做只读查询）——镜像内行为属**静态推断 + 最小复现**，涉及运行时结论处已逐条标注证据形态。
2. Python 三方包许可证未能逐项机读（`uv.lock` 不含 license 元数据，`pip-licenses` 需联网安装）——凡未取证的判定标「待验证」。
3. CI 本月未实跑（用户侧已知），因此「CI 会红 / 不会红」类结论属**据规则推演**，非实测；本轮把这类推演都落到了可复核的正则与退出码上。

**已闭环（有命令证据）**：`uv.lock` 入库且 `uv lock --check` 通过（58 包）；CI `uv sync --frozen` + SCA `uv export --frozen` 同源；`npm` 侧根 `package-lock.json`（lockfileVersion 3，631 条）与 workspace `package.json` 一致（从仓库根 `npm ci` 实测 `added 630 packages`）；`images.lock` 19 条**每条都登记了 digest**，且 `validate_images.py` 把 Dockerfile `FROM` 也纳入了扫描（「精确 tag」这一层打了折扣，见下）；`install.sh` 的 `verify_images_by_digest` 是全仓库最严格的一环；镜像内无 GPL 族（squid GPL-2.0 以 `distribution: independent-container` 显式豁免，SeaweedFS/Valkey/Milvus/Keycloak/Prometheus 全白名单）。

**开环（三个洞，按严重度）**：

1. **生产镜像不消费锁**（R2-ARC-02）：CI 验的是 lock 树，交付的是「构建当天解析」的树。这是第一轮 H-2 的核心诉求，**只修了测试侧**。
2. **web 镜像三套编排全部构建不出来，且失败阶段不同**（R2-ARC-01）：全量栈死在 `npm ci`（peer 冲突），**lite / saas 死在解析 `COPY --from=lockroot`**（named context 未声明，比 npm ci 更早更硬）。H-3 的修复只补了一套编排的 context——**「改一套漏两套」正是这个仓库自己记录过的事故形态**（`validate_deploy.py` 文档头：「改一处不等于改完：两份编排是各自维护的」），而这条新增约束恰好落在门禁盲区（R2-ARC-12）。CI 零镜像构建使其全静默。
3. **LGPL 混入前端生产树 + 白名单声明失真**（R2-ARC-03）：`sharp → @img/sharp-libvips-*`（10 条 `LGPL-3.0-or-later`），而 `next/image` 全仓零使用——这是一个**用一行 `--omit=optional` 就能消掉**的合规敞口，却因为「没人构建过前端镜像」而没人看见。

**版本口径**：Dify 1.17.1 / Keycloak 26.8.1 / pgvector:pg18（PG 18.6，与基线一致）/ Valkey **9.2** / Milvus v3.0.3 / etcd v3.7.2 / SeaweedFS **4.48** / Prometheus v3.15.0 / squid 6.13 —— 与基线记忆一致，**唯一冲突在文档侧**：`architecture-v1.0.md` 仍写 Valkey 7.2 / SeaweedFS 3.80（R2-ARC-04）。

**标签精度（三条线索的结论）**：`images.lock` 的 19 条**每条都带 digest**，这一层是合格的；但「精确标签」策略**只写在锁文件注释里，`validate_images.py:347` 只拦 `latest/main/master`** —— 于是 `pgvector:pg18`（PG 18.x 滚动）、`nginx:1.29-alpine`（奇数 = mainline 分支，非 stable）都能过门禁（R2-ARC-14）；再叠加「三套编排 0 处 `@sha256`，digest 仅在 `install.sh` 生效」（R2-ARC-08），就形成「锁文件记的是某一刻、`compose up` 拉到的是当刻」的记录-实物错位。**`dify-plugin-daemon:0.6.10-local` 经核实不是问题**：`-local` 是上游官方变体（有实测 RepoDigest + 2.28GB 体积佐证，见 `docs/lite-container-baseline.md:33`），只差在锁文件里补一句「为何是 `-local`」（R2-ARC-16）。**`ubuntu/squid:6.13-25.04_beta` 是这三条里最实的一条**（R2-ARC-15）：beta 标签 + Ubuntu interim 底座（25.04，标准支持约 9 个月，**待验证**是否仍有 backport），而它承载 Dify 全家（api/sandbox/plugin_daemon）的出站口；且该问题 2026-10-22 的审计（`docs/audit-repo-2026-10-22.md:199 P2-7`）就已登记、要求「评估换非 beta 稳定标签」，**至今 tag 未变、无评估记录** —— 属旧账未闭环，不是本轮新发现。

**上游生命周期风险（待验证项集中处）**：`python-jose 3.5.0` —— 存在**上游不修复**的 PYSEC-2026-4298，全靠调用侧 `algorithms=[...]` 一行约束兜底（见 §2.4，建议给出到期判据）；`ecdsa 0.19.2` —— Minerva 侧信道上游明确不修（本项目仅验签，风险可接受）；`ubuntu/squid:6.13-25.04_beta` 的底座（R2-ARC-15）；`librt` / `ast-serialize`（mypy 的新型依赖，dev-only，维护者与许可**待验证**，不进运行时镜像）；前端 `tailwindcss@3.4` / `zustand@4.5` / `date-fns@3.6` 落后 1 个大版本（与 infra「紧跟最新稳定版」策略不同源，属可接受的前端稳定性取舍，仅登记）。 **另有一条"升级债"的形态值得单独记一笔**（R2-ARC-17）：`starlette` 已在告警「`httpx` 将被 `httpx2` 取代」，但仓库既无 tripwire、也无升级台账；而 `pyproject.toml:184` 唯一一行 `filterwarnings` 经实测**空转**（过滤前后输出逐字相同），且它真正会起作用的那天恰好是「未来 httpx 源告警出现时把它静默吞掉」——`no-op 配置 + 暗示已处理` 比没有配置更糟。更关键的是：`deploy/images.lock:16` 引用的「月度巡检（架构文档 9.6）」在 9.6 里**并不存在**，仓库也没有 dependabot/renovate —— **「升级」这条线目前只有"扫描"（发现漏洞），没有"巡检+到期判据"（决定何时升）**，本报告涉及的 4 条债务（starlette-httpx2 / python-jose / ecdsa / 前端大版本）都挂在这个缺口上，建议合并成一个 `docs/dependency-upgrade-watchlist.md` 一次性解决。

## 五、优先修复建议

> **方法论（本轮实证得出，建议上升为团队验收通则）：配置改动的完成定义不是「diff 落地」，而是「产物时间戳更新」。**
> 硬证据：H-3 / H-2 的修复提交时间是 2026-10-28 15:51–17:53，而 `officeai/web:1.0.0`（`Created=2026-10-22T14:52:13Z`）与 `officeai/adapter:1.0.0`（`Created=2026-10-22T14:50:54Z`）**一次都没重建过**，
> 4 个运行容器 `oa-web`/`oa-adapter`/`oal-web`/`oal-adapter` 全部 `Up 26 hours` —— 也就是说 **29 条修复批次从未在任何容器里运行过**。
> 由此提出两条通用关闭条件：**①** 凡触碰 Dockerfile / compose / 依赖锁的修复，必须附 `docker image inspect --format "{{.Created}}" <tag>` 输出，且**晚于提交时间**；

> 「我改完了」不是完成，「产物换过了」才是完成——本次两条高危（R2-ARC-01/02）恰恰都是"改完了但产物没换"。
