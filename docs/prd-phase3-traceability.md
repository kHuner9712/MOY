## 0. 使用说明

1. **用例编号规则**：`TC-P3-xx` 与 P0 编号 1:1 对应（`P0-P3-01` → `TC-P3-01`）。单条 P0 的断言用 `a/b/c/d/e` 后缀，可直接落成一个用例的多个 assert（或拆成同编号多个用例，**编号不得跳号**）。
2. **断言写法约定**：每条断言必须是「动作 → 可观测结果 → 期望值」三段式，禁止出现「体验良好」「提示合理」这类不可判定表述。可观测对象只有五类：HTTP 响应字段、页面 DOM 文案/属性、仓库或第三方回执、导出文件内容、扫描脚本退出码。
3. **三档标记**（每条断言末尾标注）：
   - `A` = 可自动化（脚本/接口断言/静态扫描，建议进 CI）；
   - `M` = 需人工执行（跨系统核对、文件打开、走查）；
   - `A+M` = 接口断言可自动化 + 结果物需人工抽验。
4. **前置数据约定**：凡涉及真实第三方的断言，前置条件统一为「沙箱环境 + 契约桩」（见第 5 章表四），无法提供的必须标 `M` 并留证。
5. **本文所有体积类数字均标口径**（2026-10-23 补，源于「同一数字四种结果」事故）：行数 = `wc -l` 口径；断言数 = **各 TC 行「最大圈码编号」之和**（跳号不计、重复引用不计）——**按「圈码出现次数」统计会得到不同数字**（同一文件：TC 行内出现 128 次、全文出现 164 次），三个数都能算出来，差别只在口径，**不可混比**；端点数 = 附录 A.1 表格行口径；P0 条数 = PRD §3.1 表格行口径。**引用时不写口径的数字不要用**——604/603/606/607 四种结果没有一个是错的，全差在文末换行。另：**行数还依赖读取时刻**，跨文档对表时建议标采样点（如 `606 行 @ v1.2 封版后`），否则两个都对的核算（如架构 1495 与 1502）会被误判为不一致。
6. 本文件**不含错误码数值**：错误码由架构统一分配后回填，QA 写用例时用「语义名」占位（如 `E-4 未授权`），码值落地后由架构提供映射表一次性替换。

### 3.4 Offer 金额扫描三规则（QA 直接抄）
> **本小节是金额规则的唯一真源**；其他文档（PRD、QA 方案）只能引用本小节，**不得反向被本小节引用**（引用方向单向：外部 → §3.4）。

- **R1（带单位金额）**：`(?<!\d)(?:(?:[1-9]\d{0,2}(?:,\d{3})+|\d{3,})(?:\.\d{1,2})?\s*(?:元|万元?|亿元?|k|K|/月|每月|/年|年薪)|\d{1,2}(?:\.\d{1,2})?\s*(?:[kK]|万元?|亿元?))`
  - **扩容依据（2026-10-23 裁定）**：原式要求 **≥3 位数字**，导致 `15k`、`1.2万` 这类**最常见的薪资写法反而不被判违规**——而模型最可能输出的正是它们。尾部新增分支专门覆盖「1-2 位数字 + k/K/万/万元」。
  - **正样本（必须判失败，但需注明由哪条规则命中——否则会误判规则失效）**：
    - **R1 命中**：`15k`、`1.2万`、`1.2万元`、`8000每月`（**带单位**，无需上下文）；
    - **R2 命中**：`8000`、`8,000`（**裸数字**，须落在 `薪|工资|待遇|补贴|奖金…` **±20 字符窗口**内才算命中，R1 不负责它们）；
    - 任一样本未被其**对应规则**命中即视为该规则未生效，报告不得表述为「金额三规则已覆盖」。
  - **单位集含「亿/亿元」**（2026-10-23 补）：`3 亿元`、`1200 亿`、`0.5 亿` 均命中；不加则股权/总包类表述会漏检。
  - **⚠ R1 是「形状匹配」，不区分「金额」与「业务量」**：实测 `服务 2000 万用户`、`覆盖 500 万家企业`、`累计 1200 万次调用` **全部命中**——它们与「年薪 2000 万」形状相同。**因此作用域（只扫 `output_key=offer`）是唯一防线**；若日后要扫公文全篇，必须改为「上下文限定」式（如单位前 `±20` 字符内须出现 `薪|薪酬|工资|待遇|奖金|股权|期权|年薪|月薪|总包`），否则必然大面积假红——而**假红比漏检更伤**：它会让执行方开始「绕门禁」。
- **R2（金额上下文内的裸数字）**：在 `薪|工资|待遇|补贴|奖金|年终|期权|股权|月收入|总包` 前后 **±20 字符**窗口内，按**先区间、后单值**顺序匹配：
  - **R2-a 区间优先**（2026-10-23 主理人批准；**执行顺序固定为：① 日期/编号豁免先行剔除 → ② R2-a → ③ R2-b**，顺序不得颠倒）：`(?<![\d-])\d{3,7}\s*[-–—~～至]\s*\d{3,7}(?![\d-])`
    - **必须命中**：`8000-10000`、`8000–10000`（en dash）、`8000~10000`、`8000至10000`；
    - **不得命中**：`2026-11-01`（日期）、`-5~-3`（负数区间）、**`PO2024001-2025001`（编号区间）**；
    - **`PO2024001-2025001` 是唯一的「顺序可验证」样本**：它与金额区间**形状完全相同**（两侧各 ≥3 位数字 + 连字符），**只有「先剥编号前缀」才不会误报**——实测：不剥离 → **命中**（误报）；剥离后 → 剩 `-2025001` → **不命中**。`2026-11-01` 抓不住顺序问题（它靠位数保护，顺序反了也不命中），**所以「顺序不得颠倒」这条若无此样本就是不可验证的要求**；
    - 注：`2026-11-01` 即使不先剔除日期，也因**第二段仅 2 位 < 3 位**而不被 R2-a 抓——顺序是**防御性要求**（防未来出现 3 位段日期如 `2026-100`）；`-5~-3` 由 lookbehind 的 `-` 挡住。
  - **R2-b 单值**：`(?<![\d-])\d{3,7}(?:\.\d{1,2})?(?![\d-])`
  - **R2-b 千分位形态（2026-10-23 主理人批准）**：`8,000` / `1,500` / `12,345,678` **必须整段命中**（否则脱敏只遮尾段 `8,***`，形同未遮）；
  - **R2-a 两侧支持千分位**：`8,000-10,000` / `12,000-15,000` **必须整段命中**（与 R2-b 千分位形态对称；**只补 R2-b 不补 R2-a，千分位区间的「整段」判据仍然落空**）；
  - **为什么要补 R2-a**：R2-b 的 `(?<![\d-])` 为排除日期/编号而禁止**连字符两侧**，R1 又要求带单位——于是 `月薪 8000-10000`（无单位 + ASCII 连字符，中文 Offer 最常见的薪资区间写法）落在两条规则的**空隙里，双双漏检**。
  - **正样本**：`月薪 8000-10000` 必须命中（由 R2-a）；**同时** `2026-11-01`（日期）、`EMP-1234`（编号）、`第 3-5 章`、`比例 20-30%` 必须**不**命中——**两条并列才算证明「区间被抓、日期没被抓」**；只测前者会诱使实现「放开连字符」，把日期也吃进来。
  - **工号样本也必须两种写法各一条**：`EMP-1234`（靠 lookbehind 的 `-` 挡住）与 **`EMP1234`（只能靠豁免剥离挡住）**——只测前者时，实现**删掉豁免**仍能通过；只测后者时，实现**放开连字符**仍能通过。**两条并列才同时锁住两个独立机制**。
  - **通用做法**：单一正样本总会指向一个「能过但错」的实现——**先假想最省事的错实现，再为它准备一条样本**。
  - **放宽豁免必须配「反向守卫样本」**：每加一条豁免，同时加一条**仍应命中**的样本——`RMB8000` / `K8000` / `¥8000` / `CNY 8000` / `8000元` / `月薪 8000`（实测均被 R2-b 命中，豁免不得剥掉它们）。**理由：放宽豁免是在移动边界——只测「误报消失」只验了一半，另一半是「原本该抓的还抓得到」。**

**两条门禁口径（2026-10-23 由 B16 实跑暴露后补，架构已落 §10/§11）**

1. **隔离复跑必须显式定位被测树**：扫描类门禁（`validate_plugins.py` / `validate_plugin_actions.py` / `validate_capability_usage.py`）**不带 `--dir` 时会扫"已安装包路径"而非脚本所在树**，导致"隔离复跑"实为验错树。故：B16 起每批复跑一律带 `--dir <git archive 归档目录>`，并在批次报告固定记录「**扫描绝对路径 + 归档 sha**」两列，**缺两列则该批门禁结论无效**；**覆盖率/门槛类判据以「批次检查单」为唯一真源，本表不载阈值**；配套只记一条设计原则——**门槛组合必须能算出总体可达**（用当期实测值验算，算不出则调整门槛）；**不得以「子集门槛不得高于总体」作约束**：总体是加权平均，子集可高于总体（例：插件域新模块 ≥90% vs 总 ≥85%）。**任何「下限」类判据的值必须 ≥ 该指标的历史实测值**（超时/配额/并发数同用）；若确需下调，**必须显式写「下调 X pp + 理由 + 批准人」**——**禁止的是「悄悄下调」，不是下调本身**。**下限取整时只可向上取整**（实测 86.09% → 门槛 86%，不得取 85%；76.60% → 76.6%，不得取 76%），否则那 1pp 就是「看起来没退的退」（避免第二份门禁真源）；本表只记配套的取证纪律——
   > **A 档阈值快照（2026-10-23 终裁；**真源仍为检查单行 `380`**，本处仅供核对，冲突以检查单为准）**：总 `app/*` 合并 **≥88%**（实测 88.06%）｜`business+db` 合并 **≥86%**（实测 86.09%）｜分支 **≥76.6%**（实测 76.60%）｜核心三 repo 语句 **≥85%** + 分支 **≥60%**（**首设、无历史基线**）。四档锚在复算值、**零松弛**；**取整方向必须使门槛不降低**（≥ 向上取、≤ 向下取）；合并值仅展示、不作门禁。
   > **⚠ 「门槛已定」≠「批次已过」**：`P3-B19-04`（P0）与 `P3-B20-01`（P0）的关闭，取决于**工程侧提交 + QA 在冻结点复测**；本表不因阈值定稿而认定任何批次通过。
**引用任何事实前，先答三问：哪棵树（工作区/HEAD/导出树）· 哪个文件（路径）· 哪一层（CLI/配置文件/默认值）**——三问都答得出才算取证完成（本轮三例：只看工作区/只看命令行/只 grep 根目录，各错一次）。**工作区读数还必须附时间戳、不得跨小时沿用**——工作区只能证明「有人在改」，**不能证明「改成什么样」**（实例：`task_repo` INSERT 列数一小时前 23、现在 24，两次读数都真、都被下一分钟推翻）——本轮实例：曾误判「CI 未开分支覆盖」，实为 grep 了**不存在的根 `pyproject.toml`**，真配置在 `apps/adapter/pyproject.toml`（`branch = true`）。**「已修复」只认已提交树（HEAD）或冻结点导出树，工作区改动不计**——工作区改了但没提交，任何人看工作区都会以为修好了；本轮实例：PG `create_task` 列不匹配在**已提交 HEAD 仍在**（引入 `b6effcf`），仅工作区已改。**主工作区存在在途改动（WIP）时，不得从主树取任何证据**——主树上的红可能是 WIP 中间态（如未定义符号），不能记为批次缺陷；一律在 `git archive <sha>` 导出树上跑；若门禁做 `manifest_sha256` 比对，**必须复用加载器的唯一入口 `manifest_digest()`**：对**解析后的声明对象**做规范 JSON（`sort_keys=True` + 紧凑分隔 + `ensure_ascii=False`）再取 sha256，**不基于原始字节**——这样 CRLF / BOM / 尾随空白 / 键序都不进摘要。**禁止另写一个「归一化原始字节」的等价实现**：两套等价但不同实现的规则会算出两个不同的 sha，那才是真正的周期性误红（会让人以为声明被篡改）。
**「清单类」数字必须能「逐条编号」验证**：`grep -c "^[0-9]\+\. "` 与文档自称的条数一致；**不一致时以逐条编号为准，不以任何人的总结为准**（本轮实例：撤回清单实为 **7 条**，曾被按印象记为 9 条）。**清单条数最易被"我以为有 N 条"污染，又最易被下游引用进报告。**
2. **门禁自证三原则**（架构 L1300-1310）：① 目标必须显式，且**两件事分别断言**：「解析后的目录」==「期望归档根」，**且确实发生了遍历**（命中文件数 > 0）——只断路径相等时，「路径对但 0 个文件」仍会绿；② 日志必须自证 sha；③ **判据不得窄于契约允许的实现集合**（多合法实现时用集合包含，不用单一等值）。
   > 元规则：**门禁必须能证明「它验的对象」就是「它声称验的对象」**。G-24 空跑（输入=0 条用例）、G-17 词表漂移（输入=空词表）、本次假隔离（输入=错误的树）是同一类——**只约束了输出，没约束输入**。

**批次 xfail / red 口径（2026-10-23 主理人裁定，阶段三硬规则）**：
1. **三个桶**：`xfail`（已写断言、实现未到，**已知并接受**）/ `landed`（已转绿并验收）/ `red`（已写断言、当前失败，**已知但不接受**）；正常模式允许 `xfailed == EXPECTED_XFAIL`、**不允许 `skipped`**（`skipped` 恒 0；自检用例正常模式不收集，机制自选：文件名不带 `test_` 首选 / `collect_ignore`）。
2. **「只降不升」按合成计数判定**：`xfailed + red`（= **`EXPECTED_OPEN_CASES`**，断言层）单调不增，**不能只看 `xfailed`**——否则把 `xfail` 改成 `red` 就能清空待办，实测可让 `xfailed` 从 6 直接降到 0 而交付零增长。**「不许涨」的对象是两个桶之和，不是单个桶；`red` 单项允许随交付上升**（新代码暴露新缺陷是正常轨迹，禁它等于逼人少写断言）。
3. **每个 `red` 必须挂缺陷编号 + 归属批次**，且编号须与该批**缺陷台账**双向相等、唯一（否则编号被编造或复用，字段沦为填字）；**批次完成时该批归属的 `red` 必须为 0**——否则可以带着红缺陷签收，而计数显示已完成。
4. **断言失败只允许两条路**：转 `red`（带编号）或修到绿；**不得转 `xfail` 顶替**——那是从后门把断言换成「预期失败」。
5. **唯一真源** `tests/expected_xfail.py`（`EXPECTED_XFAIL` / `EXPECTED_RED` / **`EXPECTED_OPEN_CASES`** / **`OPEN_CASES_HISTORY`** / `DEFECT_LEDGER`），骨架与门禁一律 import，不本地另写；三个常量须自洽（`OPEN == XFAIL + RED`），单改一个必红。
6. `xfail` 与 `skip` 的区别不是形式：前者是**带编号与到期批次的待办**，后者是没有到期日的黑洞。
