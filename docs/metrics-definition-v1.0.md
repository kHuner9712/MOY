## 0. 为什么需要这份文档

总纲 §十四 明确：Moy 不以「接入了多少模型、安装了多少插件」为成功标准，而以**真实工作成果**为衡量标准。
当前实现（`apps/web/src/app/(main)/ops/metrics/page.tsx:46-56`）只有 5 项用量类指标
（区间活跃企业 / 活跃成员 / 对话次数 / 文档处理 / 用量合计），**总纲 8 项核心指标 0 项落地**。

本文件的作用是：在写代码之前，把「每个指标到底怎么算」定死，避免埋点做完才发现口径不一致（返工成本最高的一种）。

**三条纪律**

1. **定义先于埋点**：口径未定的指标不上线、不进看板、不对外披露。
2. **不编造数字**：阈值、目标值一律留空待拍板；历史数据不足时标注「样本期不足」，不给趋势结论（总纲 §十四末段）。
3. **可复算**：每个指标给出 SQL 口径或等价伪代码，任何人可用同一批数据复算出同一结果。

### 1.5 数据域约定（必读，否则指标会被误读）

**本文件所有指标默认只覆盖「工作流任务域」（`plugin_task` / `plugin_task_step` / `plugin_artifact`）。**
纯对话与文档问答（`conversation` / `message` / `usage_event.capability ∈ {chat, doc_qa, doc_process}`）**不在** M1/M3/M4/M6 的分母内。

| 数据域 | 覆盖对象 | 适用指标 | 现有看板口径 |
| --- | --- | --- | --- |
| 工作流任务域 | 插件任务（3 工作台 + 3 轻量插件） | M1、M2、M3、M4（工作流部分）、M6 | **此前无对应看板**，本文件首次定义 |
| 对话与文档域 | 会话、文档问答、文档处理 | M4（对话部分）、M5 | `/model/usage`、看板「对话次数/文档处理」 |
| 组织与商业域 | 租户、席位、订阅、订单 | M7、M8 | 运营看板企业数/套餐分布 |

> **两个域的完成率不可混算**：把对话次数当"任务"计算完成率，会得到一个漂亮但没有意义的数字。
> 若需平台级视图，应分域展示（"工作流任务完成率 / 对话有效完成率"），不合并为单一百分比。
> 指标标题在对外表述时须带数据域限定词（例："工作流任务完成率"），不得简写为"任务完成率"。

## 2. 八项核心指标定义

> 每项格式：定义 → 计算公式 → 数据来源 → 采集点 → 看板归属 → 当前可得性。
> 可得性三档：**可算**（现有表即可，SQL 可出）｜**需埋点**（需前端事件或新增表）｜**需外部数据**（问卷/工时/客户反馈）。

### M1 工作流任务完成率

- **数据域**：工作流任务域（`plugin_task`）。不含对话/文档。
- **定义**：统计周期内，**用户主动发起的任务**中达到明确完成标准（`status = 'completed'`）的比例。
  这是总纲「用户是否取得可用成果」的最直接代理指标。
- **计算公式**
  ```
  任务完成率 = COUNT(status='completed') / COUNT(分母)
  分母 = status ∈ {completed, failed, cancelled} 的任务（已终态）
        + 统计周期结束时仍处于 running/queued/waiting_confirm 的任务按「未完成」计入分母
        − 用户主动取消（cancelled 且 cancel_requested=true）
  ```
- **口径细则（必须遵守，否则数字会失真）**
  1. **`cancelled` 需拆分**：用户主动取消（`cancel_requested = true`）不计入分母；系统取消/超时取消计入分母。
  2. **`waiting_confirm` 不得算作失败**：它是「等待人工确认」的中间态，统计期末按未完成计入，但在看板上单列「待确认」数量。
  3. **`retry_of` 不计为新任务**：重试任务与其原任务合并为一条「任务实例」，只计一次分母；详见 M6。
  4. 对话类任务（无 `plugin_task`）不纳入本指标，单独用「对话完成率（有后续追问/无报错）」观察，暂不进主看板。
- **数据来源**：`plugin_task`（`status`、`cancel_requested`、`started_at`）。
- **采集点**：无需新增埋点，状态机已在 `business/task_service.py` 落库。
- **看板归属**：运营看板（R4）主卡片；团队看板（R2）按本团队过滤；私有化交付报告（客户级）。
- **当前可得性**：**可算**（W1 出 SQL 视图与端点即可）。

### M2 成果采纳率

- **数据域**：工作流任务域（`plugin_artifact`）。不含对话类产物（知识库回答不产生 artifact）。
- **定义**：**完成满 7 天**的工作流产物中，出现「下载 / 复制 / 编辑后保存」任一类采用行为（可叠加）的比例。
  采用强度分三档，便于区分「拿来就用」与「改改再用」。
- **计算公式**
  ```
  纳入统计的产物 = 所属任务 status='completed' 且 task.finished_at <= now() - interval '7 days' 的 artifact
                  （type ∈ {text, file, table}；排除 link —— 外链无法判定采用）
  已采纳产物     = 上述产物中，在 artifact_adoption 里存在事件的 artifact（按 artifact_id 去重）
  成果采纳率     = COUNT(DISTINCT 已采纳产物) / COUNT(纳入统计的产物)
  直接采用占比   = 仅有 download/copy 事件的产物数 / 纳入统计的产物
  修改后采用占比 = 有 edit_save 事件的产物数 / 纳入统计的产物
  未采纳占比     = 1 − 成果采纳率（**查询期算出，不落库**）
  ```
- **关键设计（否决了「补记 none」方案，2026-10-23 与架构师对齐）**
  1. **不写「未采纳」事件**：`artifact_adoption` 是 append-only 事件表，写入"未发生"违背事件语义，
     会污染将来的漏斗分析。
  2. **不需要清理/补记任务**：改用**查询期时间窗口过滤**（`finished_at <= now() - 7 days`），
     口径等价、零调度面、零脏数据、零新告警。
  3. **7 天为观察窗**：不满 7 天的产物不计入分母，避免"刚生成还没用"被判为未采纳（这会系统性低估）。
- **「采用」的操作定义（三动作，由架构师复核后合并）**
  | 动作 | 触发点 | 判定 |
  | --- | --- | --- |
  | `download` | 产物下载路由 `GET /files/artifacts/{token}`（`artifact_files.py:35`）；**「导出」在实现上走同一下载路径，合并为本动作，不重复埋点** | 直接采用 |
  | `copy` | 前端「复制」动作（纯前端触发，需新端点接收事件） | 直接采用 |
  | `edit_save` | 产物编辑 `PUT /agent/tasks/{id}/artifacts/{artifact_id}`（`agent.py:415`）保存成功 | 修改后采用 |
- **数据来源**：`plugin_artifact`（分母）+ `plugin_task.finished_at`（窗口过滤）+ `artifact_adoption`（分子）。
- **采集点**：下载路由与编辑路由在后端直接写事件（最可靠，不受前端改动影响）；`copy` 由前端调用新端点。
  **不设 7 天补记任务**。
- **看板归属**：运营看板（R4）三档分列；个人中心（R1）仅展示本人产物的采用状态（业务语言）。
- **当前可得性**：**需埋点**（W1：迁移 `0012_artifact_adoption` + 事件写入 + `copy` 端点 + 看板卡片）。

### M3 工作流任务完成时间

- **数据域**：工作流任务域（`plugin_task`）。
- **定义**：任务从发起到终态的真实耗时，**按任务类型（`plugin_id`）分组**统计，用 P50 / P95 而非均值（均值会被长尾拉偏）。
- **计算公式**
  ```
  单任务耗时 = finished_at − started_at − 人工等待时长
  P50 / P95 = 按 plugin_id 分组后的分位数
  ```
- **口径细则**
  1. **必须扣除人工等待**：`waiting_confirm` 停留时长单列为「等待人工」时长，不计入执行耗时（否则「系统慢」与「人没空点确认」混为一谈）。
  2. 只统计 `completed` 任务；失败任务耗时进 M6。
  3. 「相较用户原有方法是否节省时间」需基线数据，V1.0 **不做自评**，仅在客户可提供基线时按项目单列（避免编造）。
- **数据来源**：`plugin_task`（`started_at`、`finished_at`）+ `plugin_task_step`（`waiting_confirm` 区间）。
- **采集点**：无需新增埋点。
- **看板归属**：运营看板（按插件维度）；团队看板。
- **当前可得性**：**可算**（执行耗时）；「节省时间」部分**需外部数据**。

### M4 重复使用率

- **数据域**：双域分别统计——工作流任务域（`plugin_task`）与对话域（`conversation` / `usage_event`）。
  **两个域的数值不可相加**；对外只报工作流域（与 M1/M3 同域可比）。
- **定义**：同一用户在同一能力/插件上，30 天窗口内**再次发起**同类任务的比例。它是留存的产品化表达，比 DAU 更贴近「愿不愿意把工作交给 Moy」。
- **计算公式**
  ```
  重复使用率 = 窗口期内发起 ≥2 次同类任务的用户数 / 窗口期内发起 ≥1 次该类任务的用户数
  同类 = 同一 plugin_id（工作流类）或同一 capability（对话/文档类）
  ```
- **口径细则**
  1. 首次使用的新用户与老用户**分开看**（新用户重复率天然更低，混在一起会掩盖问题）。
  2. 排除 `retry`（重试不是重复使用）。
- **数据来源**：`plugin_task`（`initiator_id`、`plugin_id`、`trigger_type`、`started_at`）；对话类用 `conversation` / `usage_event`。
- **采集点**：无需新增埋点。
- **看板归属**：运营看板（R4）；产品迭代复盘。
- **当前可得性**：**可算**。

### M5 单位成功任务成本

- **数据域**：工作流任务域（分母）+ 全平台用量（分子 `usage_event`）。
- **定义**：每一个**成功交付**的任务平均消耗多少资源与运营成本。用于回答「这个功能到底赚不赚钱」，是总纲 §9.5 商业决策原则的直接输入。
- **计算公式**
  ```
  单位成功任务成本 = 统计期资源总成本 / 统计期成功任务数
  资源总成本 = Σ(模型调用成本) + Σ(第三方服务成本) + Σ(基础设施分摊)
  当前近似：资源总成本 ≈ Σ(usage_event.units) × 单位成本系数
  ```
- **口径细则（当前最大缺口）**
  1. **`units` 是「字数折算」，不是 token，也不是金额**（见 `usage_service.py`）。用它算成本只能得到「相对成本指数」，**不能对外称「每个任务 X 元」**。
  2. **`units` 的折算口径一旦变更，历史成本指数不可比**：口径版本必须与图表一同展示（例：`指数口径 v1（字数折算）`），跨版本不做连线对比。否则折算规则一调，曲线会"默默变形"且无人察觉。
  3. 分母与 M1 的 `completed` 严格一致（同一口径），否则「成本下降」可能只是任务变少。
  4. 基础设施分摊（K8s / 存储 / 向量库）V1.0 采用「按租户用量比例分摊」的近似，需在报表脚注声明。
- **数据来源**：`usage_event`（`units`、`capability`）+ `usage_monthly`；成本系数表（**需新增**，建议配置化 `cost_price_catalog`）。
- **采集点**：`business/usage_service.py` 计量链路已有；成本系数需配置项。
- **看板归属**：运营看板（R4）+ 内部经营报表（不对外）。
- **当前可得性**：**部分可算**（可出相对成本指数）｜**需外部数据**（真实单价、账单）。

### M6 故障恢复能力

- **数据域**：工作流任务域（`plugin_task` / `plugin_task_step`）。
- **定义**：任务失败之后，系统能否**正确报告 → 恢复或引导人工处理**。用三个子指标刻画，避免单一数字掩盖问题。
- **计算公式**
  ```
  ① 可恢复失败占比   = 标记 retryable=true 的失败任务 / 全部失败任务
  ② 重试成功率       = 重试后 completed 的任务数 / 重试任务数（按 retry_of 归并）
  ③ 失败可见性       = 有业务语言 error_message 且给出 operator_action 的失败任务 / 全部失败任务
  （辅助）平均恢复时长 = 重试成功任务的 finished_at − 原任务 failed 时间
  ```
- **口径细则**：失败任务合并入 M1 分母（计为未完成），**但不得从 M1 分母中删除**——否则「失败越多完成率越高」。
- **数据来源**：`plugin_task`（`status`、`error_message`、`retry_of`、`trigger_type`）、`plugin_task_step`、`audit_log`（人工介入）。
- **采集点**：无需新增埋点（状态机与失败动作链路已具备，见 `failure-actions`、`retryable`）。
- **看板归属**：运营看板（R4）；QA 回归看板。
- **当前可得性**：**可算**（①②③）；「人工介入成本」**需外部数据**。

### M7 用户满意度与付费意愿

- **数据域**：组织与商业域（`billing_subscription` / `billing_order` / `tenant`）+ 应用内评分（需新增）。
- **定义**：拆成两个可分别取证的子项，**不合并成一个模糊的「满意度」**。
  - **付费意愿**：试用 → 付费的转化、续费、席位扩张（客观数据）。
  - **满意度**：任务完成后的主观评价（问卷 / 应用内评分）。
- **计算公式**
  ```
  试用转付费率 = 统计期首次付费租户数 / 统计期产生过有效使用的租户数
  续费率       = 到期续费租户数 / 到期租户数
  席位扩张率   = (期末席位数 − 期初席位数) / 期初席位数
  满意度       = 应用内评分均值（1-5），仅统计评分样本量 ≥ N 的周期（N 待定，建议 ≥30）
  ```
- **口径细则**：样本量不足时**只报样本数、不报均值**（避免 3 个评分算出「4.7 分」）。
- **数据来源**：`billing_subscription`、`billing_order`、`tenant`（客观）；**应用内评分需新增**（可复用 `plugin_review` 的评分模型，或新增 `task_feedback`）。
- **采集点**：任务完成后一次性轻量评分（不打断流程，可跳过）。
- **看板归属**：经营报表（不对外）；满意度进产品复盘。
- **当前可得性**：付费侧 **需外部数据**（支付未真实联调，当前无真实付费样本）｜满意度 **需埋点**。

### M8 能力维护效率

- **数据域**：研发过程域（git log / 缺陷台账 / 阶段验收报告），不进产品看板。
- **定义**：新增 / 升级 / 替换一项能力，需要多少时间与维护成本。它决定「模块化复用」到底是资产还是负债。
- **计算公式**
  ```
  新能力接入工时   = 从立项到 L3（集成已验证）的人日
  能力缺陷密度     = 该能力上线后 30 天内缺陷数 / 该能力端点数
  升级/替换影响面  = 一次升级改动的文件数（或跨层改动数，配合分层门禁统计）
  ```
- **口径细则**：以 `git` 提交与缺陷台账（`tests/expected_xfail.py`）为事实源，**不靠回忆估算**。
- **数据来源**：git log、`expected_xfail.py`、阶段验收报告；**需人工归集**（建议每阶段末由 PM 汇总一次）。
- **采集点**：阶段收口时人工统计（S 级工作量）。
- **看板归属**：不进产品看板；进「阶段复盘 / 架构健康度」报告。
- **当前可得性**：**需外部数据**（人工统计）。

## 4. 看板归属与呈现原则

| 看板 | 受众 | 指标 | 呈现原则 |
| --- | --- | --- | --- |
| 运营看板 `/ops/metrics` | R4 平台运营 | M1、M2、M3、M4、M6（+ 现有 5 项用量） | 每个卡片必须标注：统计期、样本量、口径版本号；无样本时显示「样本不足」而非 0 |

## 7. 已知风险与陷阱

| 风险 | 表现 | 缓解 |
| --- | --- | --- |
| 口径漂移 | 不同报表对「完成率」算法不同，月环比不可比 | 本文为唯一口径源；看板标注口径版本号（v1.0） |
| 分母裁剪 | 为提高完成率而剔除失败/取消任务 | M1 细则固定分母构成；代码评审 + 数据校验用例 |
| 单位误读 | 把 `units` 当 token 或金额对外披露 | M5 只有「相对成本指数」；对外一律不报绝对金额 |
| 小样本噪声 | 3 条任务算出「完成率 33%」 | 样本量 < N 时只显示样本数（N 建议 30，随指标定） |
| 埋点污染 | 用户误点下载导致采纳率虚高 | 采纳率同时报「直接/修改后/未采用」三项，异常结构易识别 |
| 指标变成 KPI 表演 | 团队优化数字而非优化成果 | 指标只用于资源分配判断（总纲原则七），不与个人绩效挂钩 |
| 数据域混算 | 把对话次数并入「任务完成率」，得到高而无意义的数字 | §1.5 数据域约定；指标标题必须带数据域限定词 |
| 事件表记录"未发生" | 补记 `none` 事件污染漏斗，且需常驻清理任务 | 已否决补记方案，改查询期 7 天窗口过滤（见 M2） |
