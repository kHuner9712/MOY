# 技术路径评估与替代方案（决策备忘）

**日期**：2026-10-23
**评估对象**：`main` @ `fc3df7b`（适配层 117 个 .py / 55,103 行；前端 19,234 行；18 个容器；84 端点；34 张表）
**结论一句话**：**工程正确性 8/10，产品正确性 4/10。** 路径不是错的，是"重"错了地方——80% 的产能花在"把底座包得更严实"，20% 花在"用户为什么要用你"。不需要推翻重来，需要**三次降级 + 一次聚焦**。

---

## 一、路径中真正做对的四件事（不要动）

1. **适配层隔离底座，是对的**。真正的价值不是"将来能换 Dify"，而是**同一套代码同时交付 SaaS 与私有化**——这是定价权与交付形态的自由。执行力也罕见：全仓含 `dify` 字样仅 110 处 / 11 文件，且 `dify_base_url` 已收口到 `core/config.py` + `clients/dify_client.py`。
2. **多租户用 PG RLS 双保险，是对的**。比手写 tenant 过滤可靠一个量级，`/readyz` 自检 `BYPASSRLS` 更是老手才会想到的细节。
3. **插件"不含可执行代码"，是对的**。没有沙箱的前提下，允许第三方代码执行是安全黑洞，小团队扛不住。这个取舍要保留。
4. **先做私有化交付，是对的**。对国内有付费意愿的企业客户，"能装在自己机房"是真实决策因素，也是大厂 SaaS 打不进来的缝隙。

## 二、三个该改判的选择

### 判断 1｜Dify 该当"产品底座"吗？——不该，应降为"provider 之一"

**现在的事实**：4 个能力档位（通用/编程/长文档/深度推理）映射到 4 个 **Dify 应用**，不是 4 个模型；RAG 走 Dify datasets；Agent 走 Dify workflow；换模型要在 Dify 控制台改应用编排。

**问题在于借错了东西**：
- Dify 最强的是**可视化编排**——而你的插件是 JSON 声明、界面自己写，这部分能力你一点没用上。
- Dify 最弱的是**会话持久化、上下文、多副本、精细成本计量**——恰恰是你要的全部自己补（上一份报告 S2/S4/M1 已逐条证实）。
- 你实际只借到三件事：**模型接入、RAG 索引、流式输出**。为这三件事，你付出的是 7 个容器 + 一整套协议转换 + 跟着 Dify 版本升级做兼容（1.17 控制台改 Cookie+CSRF 就是一次隐性成本）。

**更优方案**：把 Dify 从"底座"降为"可选编排器"。
- **模型网关**：直接对接 **OpenAI 兼容协议**（通义/豆包/DeepSeek/自建 vLLM 全部兼容）。可用 LiteLLM（MIT）或自研 200 行 httpx 适配器。收益是立刻拿到 token 级计量、重试、fallback、按档位定价——这正是你现在缺的 S3/S4。
- **检索**：规模不大时直接用 **pgvector**（已经在 PG 里，零新增组件）；超过百万级再上 Milvus。
- **Dify 保留**：作为"需要可视化编排的客户"的增值模块，装不装可选。
- **收益**：少 7 个容器（dify-api/worker/beat/web/sandbox/plugin-daemon/ssrf_proxy）、少一层协议转换、token 计量变精确、换模型变改配置。**这一条能同时解掉上一份报告里的 S3、S4、M1、M3、M9 五个问题。**

> 风险提示：这不是"重写"。`services/` 层的协议转换逻辑大部分可复用，只是把"调 Dify 应用"换成"调 OpenAI 兼容端点"。工作量约 1-2 周，且可灰度并存（新老两条路各跑一个档位做对比）。

### 判断 2｜84 端点 / 34 表 / 1573 测试，是成熟的信号吗？——是过度建设的信号

二十周做出 84 个端点、34 张表、5.5 万行后端 + 1.9 万行前端，同时还要兼顾商业化——这个比例说明产能在往"完备性"堆，而不是往"验证需求"堆。

最刺眼的证据：**计费域有 10 个端点（套餐/订阅/订单/发票/支付回调/用量/运营后台），而模型提供方密钥还没拿到、微信支付未真实联调、5 个工具连接器全是桩。** 钱的路由修好了，货还没进来。

**更优方案**：V1 砍到三个域。
- 保留：**对话（含会话与记忆）+ 知识库 + 1 个标杆工作台**。
- 降级：计费改为"额度表 + 人工开单"，不做订阅/发票/回调全链路（这 6 个端点冻结，不删不改）。
- 省下的两周，全部投到"打通 1 个真实客户的真实流程"。

### 判断 3｜插件体系算"积木式整合"吗？——不算，它是"声明式 SOP 引擎"

你的原话是"整合全球开源与独立开发者的现有成果"。但现状是：插件 = 一份 JSON，能力封闭 6 项、原语封闭 6 项、UI 只有一种、不能带依赖/前端/代码。**外部开发者只能在你预置的 6 个原语里排列组合**——这不是整合生态，是整合你自己的 6 个原语。

真正在做"积木"的项目走的是另一条路：**MCP（Model Context Protocol）**。Claude Code、Codex、Cursor 都靠它接工具，生态里已有大量现成 server（GitHub、文件系统、浏览器、数据库等）。接 MCP 的边际成本极低：**一个 client（几百行）+ 一个 server 白名单/审批界面**，就能瞬间拥有几十个工具，而别人的工具你一行不用写。

**更优方案：双轨，不是二选一。**
- **对内轨道**：保留 JSON 声明式工作台，服务你自己交付的 3 个标杆场景——它稳定、可审、适合私有化交付。这是你的"确定性"。
- **对外轨道**：接 **MCP 作为工具总线**，生态靠社区；再开放一个"轻量插件包"格式（manifest + iframe/Web Component 前端 + 声明式权限），允许第三方带 UI 但不带后端代码。
- **取舍原则**：**声明式保证安全，MCP 保证生态。** 两者不冲突，前者是交付形态，后者是能力来源。

## 三、断档处：记忆与上下文——这是唯一真正的护城河

上一份报告已证：34 张表没有 `conversation` / `message` / `user_memory`，上下文全部托管给 Dify 的 `conversation_id`，前端刷新即失忆。

这不是"还没做"，而是**路径里没有给它留位置**。将来要做记忆（事实抽取、向量召回、遗忘曲线）时，你连原始消息都没有——**没有原料，谈何加工**。

**为什么它优先级最高**：Dify / Coze / 大厂 SaaS 都不会给你真正的跨会话记忆（它们只给会话级上下文）。这是少数**只有自建才有**的能力，而且一旦建立，用户迁移成本极高——这才叫"数据重力"。相比之下，多接 3 个模型、多 20 个端点，都不构成壁垒。

**最小可行形态（两周可落地）**：
1. 四张表：`conversation` / `message`（append-only，先落库再调模型）/ `memory_fact`（LLM 结构化抽取）/ `memory_embedding`（pgvector）。
2. 写入：每 N 轮抽一次事实（谁、偏好、约束、项目背景），去重合并。
3. 读取：top-k 事实 + 最近窗口拼进 system prompt。
4. 管理：个人中心"记忆"页可看/可删/可关——**这既是合规要求，也是销售话术**。

## 四、部署形态：先把"重交付"变"可复制交付"

18 个容器、无资源限制、无 K8s（`deploy/k8s/` 只有一个 README）、Prometheus 抓的 4 个目标里 3 个不存在。目标客户是"有真实工作流刚需、愿意付费的职场用户"——这类客户多数没有 IT 部门，也不会为十几个容器买单。

**两档交付**：
- **轻量版（主推）**：4 个容器 = app + PG（含 pgvector）+ Valkey + 反向代理。`docker compose up` 三分钟起，单机 8G 内存可跑。向量规模百万级以下完全够用。
- **标准版**：现在的全家桶，卖给有 IT 部门的中大型客户。

这一步的价值不在技术，在**服务半径**——独立开发者能同时服务的客户数，取决于交付有多轻。

## 五、质量投入的错配

17 道门禁、1598 个测试、90% 覆盖率——但绝大多数是**契约/桩级**（因为模型密钥没拿到、支付没联调、工具是桩）。也就是说：**你在用极高的确定性，验证一个还没被真实使用过的系统。**

**建议**：门禁从 17 道收敛到 6 道（ruff / mypy / pytest 关键路径 / tsc / eslint / 一条真跑 e2e），省下的时间做三件事：
1. 用真实密钥跑通 M1/M2，量出真实首字延迟与单次成本——这是定价的基础。
2. 找 3 个真实用户跑端到端（哪怕手工建单）。
3. 建**金标任务集**：20 条真实工作流 + 人工评分标准，作为后续每次改动的回归基线。**这比 90% 覆盖率有用十倍**，因为它衡量的是"能不能把事做成"，不是"代码是否符合规范"。

## 八、需要你拍板的三个问题

1. **Dify 是"底座"还是"可选编排器"？** 这一条决定未来三个月的全部排期，也决定要不要动 `services/` 层。
2. **首个付费客户画像：中小企业私有化，还是个人 SaaS？** 决定"轻量版"和"全家桶"谁先打磨。
3. **能否接受 V1 砍掉计费全链路（订阅/发票/回调），改人工开单？** 这是最快释放产能的一刀，但需要你承担"看起来不完整"的心理成本。
