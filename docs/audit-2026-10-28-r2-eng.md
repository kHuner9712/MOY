### 2.1 H-1 逐条核对（重点）

**(1) 客户端按 app_key 缓存 — 通过**

```python
# app/services/model_service.py:565-569
client = self._dify_clients.get(key)
if client is None:
    client = DifyClient.for_app_key(key, self._settings)
    self._dify_clients[key] = client
return client
```
- 缓存字典在 `__init__` 初始化（`:343`），`ModelService` 是进程单例（`:1597-1606`），因此缓存真的跨请求复用。
- **临界区无 `await` 的论证成立**：`resolve_app_key`（`:525-538`）是同步方法，`dict` 读改写之间不会让出事件循环，单事件循环下无需加锁。该论证可复核。
- **上限**：缓存规模 = 配置中 app_key 个数（`app/registry/*.yaml` 档位路由，当前 4 档 + 其它域），**无 LRU 但天然有界**，不构成泄漏。`aclose()` 后 `clear()`（`:577-579`）语义正确。

**(2) `post_stream` 的 try/finally — 通过**

```python
# app/clients/dify_client.py:452-456
try:
    async for event in self._iter_sse(response):
        yield event
finally:
    await response.aclose()
```
- **正常结束**：`aclose` 必达。
- **GeneratorExit（客户端断开 → Starlette 关生成器 → `agen.aclose()`）**：`finally` 必达，且此处不再 `yield`，不会触发 `RuntimeError: async generator ignored GeneratorExit`。
- **CancelledError**：⚠️ **待验证**。`finally` 内的 `await` 本身也是可被取消的挂起点；若任务已被取消且期间发生第二次取消/事件循环已在关停，`response.aclose()` 可能未跑完。加固方式：`asyncio.shield(response.aclose())` 或外包 `contextlib.suppress(Exception)`。**本项不改判 H-1 为未修好**（主路径已闭环），仅登记为残余风险。
- `>=400` 分支（`:443-448`）先 `aclose` 再抛错，正确。

**(3) lifespan 统一关闭 — 通过，但有次生问题**

```python
# app/main.py:357-360
await get_model_service().aclose()
await dispose_engine()
```
顺序正确（先停底座、再释放业务库）。**次生问题见 R2-ENG-17**：`get_model_service()` 是惰性构造，若进程从未有业务流量，关停时会**现场构造**整个服务图（含新建 httpx 连接池）；且该 await 未包 try/except，一旦构造或 `aclose` 抛错，`dispose_engine()` 与 `adapter_stopping` 日志都不会执行。

**(4) 并发安全 — 通过**

共享 `httpx.AsyncClient` 跨请求复用是 httpx 的既定用法（`httpx.AsyncClient` 文档明确线程/协程安全）；`max_connections=100 / max_keepalive_connections=20`（`dify_client.py:91`）为每 app_key 独立池，7 档位上限 700 连接，对底座是可接受量级。

**(5) 回归测试 — 存在且覆盖三条路径**

`tests/unit/test_model_service_client_cache.py`：同 key 同实例、异 key 异实例、`aclose()` 后重建（`:125-132`）、GeneratorExit 后 `response.aclose_calls == 1`（`:150-192`）。与方案要求一致。

**(6) 同类泄漏面 — 已闭环**

其它 `DifyClient` 创建点均为**单例持有**，不存在「每请求新建」：
`agent_service.py:166`（AgentService 单例 `:733`）、`memory_extractor.py:238`（由 `memory_service.py:167` 单例持有）、`rag_service.py:216` / `model_service.py:339`（取 `get_dify_client()` 全局单例）。

**R2-ENG-02（支付回调）**
```python
# payment_gateway.py:120-134  待签串只有 4 项，notify_id 恒为空
def signing_payload(*, out_trade_no, transaction_id, amount_total, notify_id="") -> str:
    return f"{out_trade_no}\n{transaction_id}\n{int(amount_total)}\n{notify_id}"

# payment_gateway.py:293-308  验签只覆盖 (order, txn, amount)

                   transaction_id=txn_id, amount_total=amount_cents), sha256).hexdigest()
...
trade_state=str(payload.get("trade_state") or TRADE_STATE_UNKNOWN)   # ← 未参与签名
```
而 `order_service.py:568-570` 用 `notification.is_success`（即 `trade_state in {"SUCCESS"}`，`payment_gateway.py:115-117`）决定**是否把订单置为已支付并开通服务**。
→ 「是否已付款」由**签名之外**的字段驱动。任何拿到过一次合法签名三元组 `(out_trade_no, transaction_id, amount_total)` 的人，都能把它与 `trade_state=SUCCESS` 组合重放（失败回调同样带签名，`_record_rejection` 不占幂等键，`order_service.py:469-476` 自述）。

### ② 潜在安全漏洞

**结论：攻击面收敛得比多数同规模项目好（无注入面、无 SSRF 暴露面、租户隔离三道防线完整），但有 1 条「防线是配置幻觉」+ 5 条中等（原 1 高已按 §八 裁决为中）。**

- **认证与授权 — 通过**：`_decode_token` 强制 `algorithms=[conf.jwt_algorithm]`（`security.py:158`），`audience`/`issuer` 均显式传入；`validate_auth_startup`（`:853-940`）在非 dev/test 环境下把「stub 鉴权 / 空 jwt_secret / `tenant_membership_check=off` 未放行」全部转成启动失败，并带 deadline 时效——这是 fail-closed 的**启动期**闭环，不是只打日志。`uv.lock` 解析到 `python-jose 3.5.0`（`uv.lock:1442-1443`），已越过 3.4.0 的算法混淆/JWT-bomb 修复线。`jwt_algorithm` 仍是自由字符串（`config.py:71`），未做白名单校验 —— 属「需运维先配错才能利用」的加固项，未单列条目。
- **多租户隔离 — 通过（这是我原本最担心的项）**：
  - `set_config('app.tenant_id', :tenant_id, **TRUE**)`（`db/session.py:42`）——`is_local=TRUE` 意味着**事务级**作用域，事务结束自动复位，**连接归还池时不会带着上个租户的上下文**，消除了「连接复用串租户」这一最典型形态。
  - 进入即设租户变量，失败即 `rollback()+close()`（`session.py:159-169`），池不泄漏。
  - `X-Tenant-Id` 伪造有 `assert_tenant_membership`（`security.py:461-509`）+ `__platform__` 哨兵**查库之前**拒绝（`:591-599`）+ `is_platform_scope` 双要素判定（`:761-788`）。三层都在。
  - `BYPASSRLS` 双保险：连接串黑名单用户名（`engine.py:39`）+ 启动/就绪自检 `pg_roles.rolbypassrls`（`:45-48,227-257`）+ CI 断言 `bypassrls=f`（`ci-adapter.yml:163-164`）。
  - 唯一设计权衡：`tenant_membership_check=auto` 只在 `deploy_mode=saas` 且非 stub 时校验（`security.py:532-543`）——私有化下生效租户被强制 `default`，无跨租户语义，可接受。
- **注入面 — 干净**：无 `f"SELECT ... {用户输入}"`（所有 f-string 拼的都是**模块级常量表名**，如 `{JOB_TABLE}`，值一律走绑定参数）；`ILIKE` 全部用 `:keyword` 参数化；`ORDER BY` 动态列名取自白名单函数（`document_repo.py:756-763` 自述「列名与方向均取自白名单常量」）；`tenant_data_service` 的表名经 `_identifier()` 校验；`migrate.py` 只执行**仓库内** SQL 文件。
- **文件 / 路径 — 干净**：上传无落盘路径拼接（分块写 `TemporaryFile`），导出文件名经 `safe_filename`（`renderer.py:278-292`：`[\/:*?"<>|\s]`→`_` 且 `strip("._")`，`..` 与分隔符均不可存活）。
- **主要风险按优先级**：
  1. **R2-ENG-01（中，原判高，见 §八）** 幂等/限流 redis 后端不存在 —— 本轮唯一「安全控制宣称已生效但实际未生效」的条目，且在部署默认值上已经切到 redis。
  2. **R2-ENG-02（中）** 支付回调把「是否付款成功」放在签名之外。
  3. **R2-ENG-03（中）** 出站白名单未实现 —— 当前无用户可控 URL 暴露面，所以是**未来功能的定时炸弹**，不是当下可打。
  4. **R2-ENG-05（中）** 判权双入口 + 19 个调用点不写拒绝审计。
  5. **R2-ENG-04（中）** 日志脱敏是安慰剂。
  6. **R2-ENG-06（中）** 无 CSP/HSTS，与已接受的 localStorage token 权衡叠加。
  7. **R2-ENG-11（中）** adapter 端口 + `/metrics` 免鉴权。
- **正面清单（用于校准风险判断，避免只报坏消息）**：`dangerouslySetInnerHTML` 0 处；PKCE S256 + 一次性 state 存 sessionStorage（`login/page.tsx:31`）；OIDC 回跳页 `Referrer-Policy: no-referrer` 落**响应头**且注释解释了为何 `<meta>` 不够（`next.config.js:44-56`）；支付回调「校验先于领幂等键」的顺序被显式设计并被测试钉住（`order_service.py:469-476`）；回调载荷只落 SHA-256 摘要不落原文（`payment_gateway.py:137-145`）；容器均非 root（`adapter/Dockerfile:61`、`web/Dockerfile:72`），无 `privileged` / 无 `docker.sock` 挂载，`${VAR:?}` 强制变量分别 35/23/29 处。

### ③ 性能隐患

**结论：连接池/超时/索引这些「教科书要点」全部到位，真正的隐患在三处「热路径上做重活」。**

- **异步正确性 — 基本干净，1 处明确缺陷**：全仓 `requests` / `time.sleep` / `os.system` = 0，同步 DB 驱动 = 0。唯一在事件循环上跑同步重活的是**文件渲染**（R2-ENG-07，docx/zip），另有上传路径的 `tmp.write/tmp.read`（50MB 同步读，随 R2-ENG-12 一并处理）。`migrate.py:830` 的 `subprocess.run` 虽在 async 函数内，但只走 CLI 路径（`_run_cli`），不污染服务进程。
- **N+1 — 只有 1 处真 N+1**（`ops_service._tenant_names`，R2-ENG-18，且 N 被 200 上限兜住）。启发式扫全仓 `for ... await` 共 20 处，逐处核对后其余均为「批量写 upsert / 重试循环 / 单例清理」，不是 N+1。分页、`COUNT`、聚合都有正确实现（`billing/postgres.py:251-267` 是被审计点名的正确示范）。
- **连接池与超时 — 通过**：
  - DB：`pool_size=10 / max_overflow=5 / pool_timeout=5s / pool_pre_ping / pool_recycle=1800`（`engine.py:154-162`），并写明容量公式「副本数 ×(pool_size+max_overflow) ≤ PG max_connections × 0.6」（`config.py:172`）。
  - httpx：普通请求有 connect/read 超时（`dify_client.py:127-136`），流式单独设 `read=dify_stream_first_byte_timeout`（`:431-435`），**且流式禁用重试**（正确）。
  - **缺口**：Redis **无任何超时**。`credential_service.py:214` `redis_asyncio.from_url(url, decode_responses=True)` 未传 `socket_timeout` / `socket_connect_timeout` → redis-py 默认**永久阻塞**。Valkey 一旦 hang（网络分区/内存打满/OOM），凭据解析的 `await` 会无限期挂住，同时占住一个 DB 连接与一个事件循环任务。**建议**：`socket_timeout=1.0, socket_connect_timeout=1.0, health_check_interval=30`，并给调用点包 `asyncio.wait_for`。（此条并入 R2-ENG-01 的整改范围——装配 redis 后端时一并把客户端参数建对。）
- **缓存有效性**：Redis 侧 key 均带 TTL（幂等 24h、限流 60s、凭据按配置），无雪崩风险；进程内两处缓存无上限（R2-ENG-09），权限快照 TTL 5s（`config.py` 的 `permission_cache_ttl_seconds`）设计合理。前端 react-query：全局 `staleTime=30s / retry=1 / refetchOnWindowFocus=false / gcTime=5min`（`lib/query-client.tsx:18-45`），只有记忆页单独调 5s —— 策略一致，无「每个页面各写一套」。
- **流式与背压 — 通过**：`generate_stream` 的 `try/except/finally` 在中断时仍会结算用量（`estimate_interrupted_units`）并把助手消息落为 `aborted + truncated=true`（`model_service.py:1313-1361`），客户端断开不会留下「永远正在输入」的行；SSE 不做半句切分（整帧丢弃 + `cap_reached`），避免多字节字符与引用标记被切断；nginx 已配 `X-Accel-Buffering no` 与 `proxy_read_timeout 300s`（`lite.conf:69`、`nginx.conf:53`）。
- **任务队列 — 1 处并发缺陷**（R2-ENG-10：batch 串行 × 60s 超时 > 120s 租约 → 可能重复执行）。轮询间隔 1s 固定、无忙等（`_loop` 里有 `await asyncio.sleep`）、认领用 `FOR UPDATE SKIP LOCKED` + 部分索引 `idx_job_due (run_after) WHERE status IN ('queued','running')`（`init-schema-phase4.sql:232-233`）——这些都做得对，问题只在「租约粒度 vs 执行粒度」不匹配。
- **前端性能**：25/25 页面 `'use client'`，即 ARC-06 现状（本机已裁定暂缓，不计入缺陷），但它同时是 R2-ENG-08/09 之外唯一会显著影响首屏的因素；`optimizePackageImports` 已对 `lucide-react`/`date-fns` 生效（`next.config.js:11-13`）；无大列表虚拟化（会话/文档列表未用 `virtualizer`），文档数上千前不构成问题。
