## 0. 先定义什么叫"持平"

"横向持平"不能按功能点数量对齐（那会永远追不完），按**任务闭环**判定。三层判据：

| 层 | 判据 | 验收方式 |
|---|---|---|
| **L0 闭环** | 6 类典型办公任务，每类 3 条，从一句话下达到拿到可用成果物，全程无人工拼接 | 18 条场景用例全绿 |
| **L1 能力面** | 五产品的**公共能力集**（下表 §2 的 P0 项）无缺项 | 矩阵打勾率 100% |
| **L2 体验** | 任务状态可见、可中断、可续跑、产物可预览可下载可再编辑 | 走查 + 用例 |

**明确不追求**：ClaudeCode / Codex 的 coding 专项能力（见 §3.4）。原因不是做不到，是**做了也不是 Moy 的战场**——它们的用户是工程师，Moy 的用户是职场岗位。强行对齐会让产品失焦，且永远落后一个版本。

## 1. 五个产品的功能基线（公开资料）

### 1.1 WorkBuddy —— 桌面工作台，成果物导向

| 维度 | 事实 |
|---|---|
| 形态 | Windows / macOS 桌面应用 |
| 核心交互 | 一句话下达 → 自主拆解规划 → 执行 → 右侧结果区交付 |
| 关键能力 | ① **成果物交付**：文档、表格、PPT、数据分析；② **本地文件操作**（授权文件夹，批量整理/重命名/转格式）；③ **人机双写**：直接在 Word/Excel/PPT/腾讯文档里改，用户同时编辑；④ 多任务并行（任务列表按文件夹分组）；⑤ 结果区（产物/全部文件/变更/预览）；⑥ 连接器 + MCP 接入外部服务；⑦ 专家 / 技能 / 连接器 / 资料库四类扩展；⑧ 模型切换、Skills 技能包、高危指令拦截 |
| 场景 | 文档生成、数据分析、PPT/报告、深度研究、邮件周报、批量文件处理、代码开发、设计创意 |
| 交互要点 | "不用把工作搬到 AI 面前，让 AI 进入你正在用的文件" |

### 1.2 AccioWork —— 本地优先桌面 Agent 平台（电商垂直）

| 维度 | 事实 |
|---|---|
| 形态 | Electron 桌面（macOS / Windows），本地编排，LLM 请求走自有代理 |
| 核心交互 | Agent Hub 选 agent → 对话/自动化触发 → 工具执行 → 交付 |
| 关键能力 | ① **Agent Hub**（自定义角色/指令/能力集，每 agent 可切 Gemini/GPT-4o/Claude/Qwen）；② **Automations**（cron 定时，本地执行，漏跑重启补偿）；③ **Browser**（CDP 控制真实浏览器，遇登录墙即停、禁自动登录）；④ **Connectors**（Gmail/Drive/Slack/Notion）；⑤ **Skills**（内置/市场/自建，支持 MCP）；⑥ **Channels**（Telegram/Discord/钉钉/飞书/微信）；⑦ **Teams (Beta)**（Team Lead + 成员 agent，委派子任务、群聊协作）；⑧ **四层权限**（auto-approve / ask every time / remember / always deny），每会话显式能力集（文件路径、终端、浏览器、连接器）；⑨ 沙箱（目录白名单 + symlink 逃逸检测 + 跨团队 vault 隔离）；⑩ 本地优先 + 审计 |
| 场景 | 电商全链路（选品/采购议价/建店/平台运营/SEO/客服），8 个专业 agent、2,696 用例 |

### 1.3 Muse（MuseWork / Muse 个人 Agent）—— 全场景工作伙伴

| 维度 | 事实 |
|---|---|
| 形态 | Web + 桌面 + 移动（MuseWork）；个人 Agent 形态（Muse） |
| 核心交互 | 对话为主 + 任务队列 + 状态可见 |
| 关键能力 | ① **Skills 三段式**（官方技能 / 我的技能 / 技能市场）；② **任务队列**（多任务按序处理）；③ **实时工作状态**（live status，避免"要不要重发"的焦虑）；④ **长期记忆 + 动态画像**（越用越贴合）；⑤ **Artifacts**（PDF/文档/交互式仪表板）；⑥ **Goals**（长链路目标 + 进度追踪）；⑦ **Ideas**（主动建议）；⑧ 多平台连接（有 API 用 API，无 API 用浏览器模拟）；⑨ 多模态输入输出；⑩ 安全 VM + 独立审查 agent（对外发送内容先审） |

## 3. 差距分级与取舍

### 3.1 P0（13 项，缺了不叫工作台）

| # | 能力 | 为什么是 P0 |
|---|---|---|
| 1 | 计划生成与确认（A-2/A-3） | 五产品全部有；没有它，"一句话"就退化成"一条指令" |
| 2 | 补齐 xlsx / pptx / pdf 渲染（B-2/B-3/B-4） | **分水岭**：WorkBuddy 全部卖点是"交付可验收的文件"；docx 已有，表格与 PPT 是办公最高频 |
| 3 | 产物预览（B-5 补预览） | 现在只能下载（且有版本管理），不能"先看后拿"，体验断层 |
| 4 | 上传解析（B-6） | 办公任务的输入一定是文件 |
| 5 | MCP 客户端（C-2） | 扩展性的唯一低成本路径（tech-path-review 已论证） |
| 6 | 技能自建 + 市场（C-3/4/5） | 插件体系已有雏形，差"用户能自己加" |
| 7 | 连接器 OAuth 一键授权（C-8） | 手填密钥是把企业客户挡在门外 |
| 8 | 定时任务（D-3） | 周报/日报/巡检是办公最高频场景 |
| 9 | 项目空间（E-1） | 没有项目概念，记忆和资料无处附着 |
| 10 | 会话能力集 + 四层授权（F-1/F-2） | AccioWork/ClaudeCode 的标配，也是私有化客户必问 |
| 11 | 任务队列（A-5） | 多任务并行是"工作台 vs 聊天框"的体感差异 |
| 12 | 可续跑（A-4 补齐） | 长任务失败即从头，用户会直接放弃 |
| 13 | 能力档位选择 UI（G-1） | 不暴露模型名，但要让用户能选"快/准/长文本" |

### 3.2 P1（8 项，竞争力）

多 Agent 团队（D-1/D-2）、浏览器自动化（C-6）、代码执行沙箱（C-7）、IM 渠道（D-5）、长期记忆（E-2）、记忆白盒（E-3）、任务入口聚合（G-2）、PDF/网页/仪表板产物（B-4）。

### 3.3 P2（7 项，择机）

人机双写（B-7）、事件触发（D-4）、主动建议（D-6）、用户画像（E-4）、内容审查（F-5）、移动端（G-3）、桌面端（G-4）、多模态输入（G-5）。

### 3.4 明确不做（4 项，附理由）

| 不做 | 理由 |
|---|---|
| 通用 coding agent（对标 ClaudeCode/Codex 的代码库级重构） | 用户群不同：它们服务工程师，Moy 服务岗位。做了也追不上，且会破坏"办公工作台"的定位。Moy 只保留"办公场景的代码辅助"（片段生成/解释/审查） |
| 自建技能市场的大规模运营（对标 33 万 skills） | 生态规模无法追赶，改做**兼容层**：能装 Claude Skills / MCP server 即可 |
| 模型名直选 | 与"技术黑盒化"红线冲突。用能力档位（general/code/long_context/reasoning）替代，既满足选择感又不暴露技术细节 |
| 消费级个人 Agent（日历/订票/砍价） | 与 B 端定位冲突，且涉及支付与个人数据，风险收益比不划算 |

## 4. 八大模块实现方案

> 原则：**不改 30 个冻结端点**，新能力全部挂 `/api/v1` 新域（第五批基线），复用现有 A1-A6 任务引擎与插件运行时。

### 4.1 补齐 xlsx / pptx / pdf 渲染（最高优先，8 人日）

**先纠正一个误判**：Moy **已有**完整产物体系，不是从零开始——

| 已有能力 | 落点 |
|---|---|
| docx / md / csv 平台渲染（封闭集合） | `app/plugins/renderer.py`（`RENDER_FORMATS`，D-20 规定 docx 只由平台生成） |
| 产物版本化（只增不删，历史上限 20） | `artifact_repo.py`（`MAX_VERSION_HISTORY`） |
| 内容摘要 + MIME 归一化 + 降级不伪造 | `resolve_content_type()`；依赖缺失如实降级 md |
| 短时下载令牌 + 平台代理下载（不暴露存储地址） | `core/artifact_token.py`、`api/v1/artifact_files.py` |
| 产物编辑 + 重新导出（WF2） | `PUT /agent/tasks/{id}/artifacts/{artifact_id}` |
| 二进制双后端落库（内存 / PG BYTEA） | 迁移 `0005` |

**真实差距三条**：
1. **格式封闭集只有 docx/md/csv** → 办公最高频的**表格（xlsx）**与**演示（pptx）**缺失，PDF 也无；
2. **无预览**：只能下载，"先看后拿"断层；
3. **无产物中心**：产物只能从任务详情看，不能跨任务/项目汇总检索。

**方案（扩展现有渲染器，不新建体系）**：
```python
# app/plugins/renderer.py
RENDER_FORMATS = ("docx", "xlsx", "pptx", "pdf", "md", "csv")  # 原 3 种
```
```
新增端点（挂现有 /api/v1，不破坏 30 冻结基线）
  GET  /api/v1/agent/artifacts                    # 产物中心：按项目/任务/时间列产物
  GET  /api/v1/agent/artifacts/{id}/preview       # 预览：首页图/结构化渲染（不返回二进制）
  POST /api/v1/agent/tasks/{id}/artifacts/{aid}:reexport  # 换格式重导出（如 docx→pdf）
```

**技术选型（重点：私有化镜像不能变重）**：

| 格式 | 库 | 理由 |
|---|---|---|
| xlsx | `openpyxl` | 纯 Python，公式/图表/条件格式齐全，无系统依赖 |
| pptx | `python-pptx` | 纯 Python，母版复用，无系统依赖 |
| pdf | `reportlab`（首选）或前端打印 | **不用 weasyprint**：它依赖 cairo/pango，私有化镜像要加系统库，与"最小镜像"冲突 |

**三条必须守住的设计原则**（延续既有决策，不因扩格式而放弃）：
1. **平台唯一渲染落点**（D-20）：插件不得自行产出 docx/xlsx/pptx，一律调平台渲染器；
2. **缺依赖如实降级**：`openpyxl` 未安装时降级为 csv 并在响应里标注 `degraded=true`，**绝不伪造一个打不开的 xlsx**；
3. **内容与排版分离**：LLM 只产出 `{title, sections[], tables[], charts[]}` 结构化 JSON，渲染由确定性代码完成。

**依赖准入**：`openpyxl` / `python-pptx` / `reportlab` 均为 MIT/BSD，但需按现有流程补 `deploy/validate_deps.py` 白名单条目 + 引入审核记录（新增 3 个平台依赖，风险等级低、无 C 扩展）。

**验收**：9 个产物（3 场景 × 3 格式）全部可下载、可用 Office/WPS 打开、样式不崩；缺依赖场景降级为 csv 且响应标注 `degraded=true`。

### 4.2 计划生成与确认（6 人日）

```
POST /api/v1/agent/plans              # 入参: goal + context → 出参: steps[] + 预估 + 所需能力
POST /api/v1/agent/plans/{id}:confirm # 确认后转 A1 创建任务
POST /api/v1/agent/plans/{id}:revise  # 用户改计划（删/并/换步骤）
```
- 计划结构：`{step_id, intent, tool, inputs, depends_on, risk_level}`。
- `risk_level=high` 的步骤在执行前触发二次确认（复用四层授权）。
- 计划落库，任务执行时按 `depends_on` 编排；失败可定位到具体步骤。

**验收**：同一 goal 连续 3 次生成计划，步骤数差异 ≤20%；用户删掉一步后执行仍成功。

### 4.3 任务队列与续跑（5 人日）

- 队列：`priority + created_at` 排序，单租户并发上限可配（默认 3）。
- 续跑：每步完成写 checkpoint（步骤 ID + 中间产物引用），失败重试从最近 checkpoint 起。
- 状态流：现有 A6 SSE 扩展 `queued / planning / running / waiting_approval / paused / completed`。

**验收**：提交 10 个任务，队列按序执行；杀掉 worker 后重启，任务从断点续跑。

### 4.4 MCP 客户端 + 技能体系（10 人日）

**MCP 客户端**（参考 tech-path-review 的"一个 client 几百行"判断）：
```
POST /api/v1/tools/mcp/servers          # 注册 server（stdio / http+sse）
GET  /api/v1/tools/mcp/servers          # 列表 + 连通状态
POST /api/v1/tools/mcp/servers/{id}:probe  # 探活 + 拉 tools/list
```
- 工具命名空间隔离：`mcp:{server}:{tool}`，避免与内置工具冲突。
- 所有 MCP 调用经统一出站代理（复用现有 squid），默认拒绝私网。
- 首次注册需管理员审批（对齐 AccioWork 的"敏感能力显式授权"）。

**技能体系**（复用现有插件 manifest，加 `skills` 段）：
- 三段式：内置 / 我的 / 市场（对齐 Muse）。
- 技能 = 声明（YAML）+ 可选脚本（受限执行）+ 依赖声明（工具/MCP）。
- 兼容 Claude Skills 目录格式，降低迁移成本。

**验收**：装一个官方 MCP server（如 filesystem）→ 在对话里被调用 → 出结果；用户自建 1 个技能并跑通。

### 4.5 Agent 团队（8 人日，P1）

```
POST /api/v1/agent/teams               # 创建团队: lead + members(岗位插件)
POST /api/v1/agent/teams/{id}/dispatch # 派发任务，lead 拆解并分派
```
- 复用现有插件作为"成员"（每个岗位插件即一个 member）。
- Lead 只做两件事：拆解 + 汇总；不做具体执行（避免单点）。
- 协作记录进任务 steps，可视化呈现"谁做了什么"。

**验收**：一个"周报团队"（数据插件 + 写作插件 + 审核插件）产出一份带数据的周报。

### 4.6 定时任务（5 人日）

```
POST /api/v1/agent/schedules           # cron + goal + 能力档位 + 通知渠道
GET/PATCH/DELETE /api/v1/agent/schedules/{id}
```
- 调度器用 APScheduler（进程内）或 Valkey 延迟队列（多副本）——V1.0 单副本先用 APScheduler。
- 漏跑补偿：启动时扫描 `next_run_at < now` 的任务补跑一次（对齐 AccioWork）。
- 执行结果落任务引擎，产物走 artifacts。

**验收**：配置"每周一 9:00 生成上周数据周报"，连续两周准点产出，产物可下载。

### 4.7 权限与能力集（6 人日）

| 层 | 现有 | 要补 |
|---|---|---|
| 角色权限 | ✅ RBAC | — |
| 会话能力集 | ❌ | 任务创建时签发 `capability_set`：可访问路径前缀、可调用工具白名单、可写操作上限 |
| 四层授权 | ⚠ 仅高危拦截 | `auto / ask_every / remember / deny` 四档，按工具 × 租户配置 |
| 沙箱 | ⚠ Dify sandbox | 文件路径白名单 + symlink 解析后校验（对齐 AccioWork） |

**验收**：同一用户，任务 A 允许发邮件、任务 B 不允许；越权调用返回 14003 且审计留痕。

### 4.8 记忆与项目空间（8 人日，P1）

- **项目空间**：`POST /api/v1/projects`，任务/资料/产物/记忆按项目归属（复用现有 tenant 隔离，加一层 project）。
- **记忆三层**：事实（结构化 KV）/ 经验（反思条目）/ 画像（偏好），全部可查可删。
- **白盒**：`GET /api/v1/memory?project_id=`、`DELETE /api/v1/memory/{id}`、`GET /api/v1/memory/export`。

**验收**：用户能看到"AI 记住了我什么"，删除后不再召回。
