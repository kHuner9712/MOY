## 1. 数字的来源纪律（读本文前必须先读这节）

### 1.1 三档证据等级

本文出现的每一个数字都属于且仅属于以下三档之一，**标注必须与数字同时出现**：

| 等级 | 含义 | 标注方式 | 能否作为容量承诺 |
| --- | --- | --- | --- |
| **A 级：实测产物** | 由仓库内脚本跑出、产物文件可打开核对 | 标注 `来源：<文件路径>` + 测试口径 | 可以，但仅限该口径 |
| **B 级：非正式观测** | 小样本、单机、非受控环境下的观测值 | 标注 `观测值，非基准` + 样本量 | **不可以** |
| **C 级：待压测** | 尚未测量 | 标注 `待压测` | 不可以 |

### 1.2 三条硬规则

1. **禁止手填数字。** 任何结果表中的数字必须来自 `results/` 目录下的实测产物文件，且文件名与测试批次可对应。手填即视为缺陷。
2. **禁止跨形态引用。** SaaS 形态与私有化形态的基准**不同**，数字不可互相引用（见第 7 章）。
3. **禁止只抄数字不抄口径。** 每个数字必须带：测试对象、测试环境、负载模型、样本量、统计方式。缺任一项即不可引用。

### 1.3 为什么定这么严

历史教训：曾出现"覆盖率 90.78%"未说明是否包含数据库用例，导致该数字在三个场合被三种方式解读。性能数字的误导成本更高——**客户会拿它做采购决策和扩容预算**。

## 2. 指标定义（口径统一，避免各说各话）

### 2.1 延迟类

| 指标 | 定义 | 统计方式 | 说明 |
| --- | --- | --- | --- |
| **P50** | 中位延迟：50% 的请求快于该值 | 单次压测窗口内的全部成功请求 | 代表"typical 体验" |
| **P95** | 95% 的请求快于该值 | 同上 | **对外的容量承诺应当用 P95，不用平均值** |
| **P99** | 99% 的请求快于该值 | 同上 | 反映尾部（卡顿）体验 |
| **平均值** | 算术平均 | 同上 | **仅作参考**：平均值会被少数极快请求拉低，掩盖长尾。本文不以平均值做任何承诺 |
| **首字延迟** | 从发出请求到**第一个字出现在界面上**的时间 | 单请求测量，取 P50/P95 | 流式场景的核心体感指标 |
| **首屏 LCP** | 页面最大内容元素完成绘制的时间 | 浏览器性能接口，5 次中位数 | 口径固定为：Chrome 最新版 + 本地网络（无 CDN）+ **冷缓存** |

### 2.2 吞吐与并发类

| 指标 | 定义 |
| --- | --- |
| **RPS** | 每秒完成的请求数（只统计成功响应） |
| **并发数** | 同时在途的请求数（阶梯加压的档位：100 / 200 / 500） |
| **错误率** | 非成功响应占比。**分类统计**：超时 / 5xx / 业务拒绝（额度用尽、频率保护）——三类必须分开，混在一起会得出错误结论 |
| **内存峰值** | 压测窗口内各服务工作集峰值之和（Docker 统计口径） |

### 2.3 稳定性类

| 指标 | 定义 | 口径 |
| --- | --- | --- |
| **起服务时间** | 从执行启动命令到业务就绪探针返回 ready 的墙钟时间 | 8 GiB 空机、冷启动（无镜像缓存预热） |
| **会话恢复时间** | 打开一个已有会话并拉取最近 30 条消息的耗时 P95 | 含数据库查询 |
| **记忆召回时间** | 生成回答前完成偏好记忆检索的耗时 P95 | 每人 200 条记忆规模；超时按降级策略处理（不阻塞回答） |

## 3. 测试方法

### 3.1 压测脚本位置

| 脚本 | 覆盖场景 | 主要参数 |
| --- | --- | --- |
| `scripts/bench/bench_chat.py` | S1 对话首字（`--mode chat`）、S5 会话恢复（`--mode session`） | `--upstream mock/real/unspecified`、`--profile`、`--concurrency`、`--requests`、`--out` |
| `scripts/bench/bench_kb.py` | S2 知识库检索（`--mode search`）、S3 文档解析（`--mode parse`） | `--base-id`、`--doc-count`、`--concurrency`、`--out` |
| `scripts/bench/bench_plugin.py` | S4 插件任务端到端 | `--plugin-id`、`--inputs`、`--auto-confirm`、`--max-wait`、`--out` |
| `scripts/bench/_common.py` | 公共统计（分位计算、原始数据落盘、披露标签校验） | 被上面三个脚本引用 |
| `scripts/bench/lite-probe/probe.py` | 容器启动耗时与内存峰值探针 | 产物见 `scripts/bench/lite-probe/out/` |
| `results/<日期>/` | 每次压测的产物目录（原始数据 + 汇总表） | 约定：**结果表的唯一取数来源** |

三个场景脚本共用一套纪律，对本文章节 1 的规则做了工程化约束：

| 机制 | 作用 |
| --- | --- |
| `--upstream mock/real/unspecified` | **强制披露上游类型**。填 `unspecified`（未标注）的结果**不允许直接对外披露** |
| `--min-samples` | 样本不足时直接拒绝出结论，避免"3 个请求算出的 P99" |
| 退出码 `3`（`blocked` 未执行） | 环境不具备条件时**明确报"没测"**，而不是跑出半份数据 |
| 退出码 `4`（数据不足） | 采到的样本不够，拒绝给分位数 |

### 3.2 执行与复算

```bash
# 示例：对话首字，桩上游（不含上游延迟），100 并发
python scripts/bench/bench_chat.py --mode chat --upstream mock \
  --concurrency 100 --requests 500 --out results/<日期>/s1_mock.json

# 示例：会话恢复（30 条消息）
python scripts/bench/bench_chat.py --mode session --limit 30 \
  --requests 200 --out results/<日期>/s5_session.json

# 示例：知识库检索 / 文档解析
python scripts/bench/bench_kb.py --mode search --base-id <知识库标识> --query "<固定问题>" \
  --concurrency 100 --out results/<日期>/s2_search.json
python scripts/bench/bench_kb.py --mode parse --base-id <知识库标识> --doc-count 20 \
  --out results/<日期>/s3_parse.json

# 示例：插件任务端到端（允许自动确认，否则人工确认点会被记为未完成）
python scripts/bench/bench_plugin.py --plugin-id plg_content_ops --inputs inputs.json \
  --auto-confirm --requests 20 --out results/<日期>/s4_plugin.json
```

> 复算能力是硬要求：**客户必须能拿着我们给的原始数据自己算出同样的 P95**，而不是只接受一个结论。分位计算与原始数据落盘由 `scripts/bench/_common.py` 统一实现，任何脚本都不得自算一套。

### 3.3 标准环境（每次压测必须记录）

| 项 | 记录内容 |
| --- | --- |
| 硬件 | CPU 核数 / 内存 / 磁盘类型（SSD/HDD） |
| 软件 | Docker 版本、Compose 版本、镜像指纹（`deploy/images.lock` 中的 digest） |
| 编排 | 轻量版（9 服务）或全量版（21 服务，常驻 20） |
| 数据库 | 是否与业务同机、连接池配置、批处理开关是否开启 |
| 网络 | 客户端与服务是否同机、是否经过网关、是否经过 TLS 终止 |
| 上游 | 是否为 mock 上游（标注"不含上游延迟"）或真实服务（标注服务与网络） |

**未记录上述任一项的压测结果，按 C 级处理（不可引用）。**

## 5. 已完成的实测（A 级：产物可核对）

> 本节数字**全部来自仓库内实测产物**，不是估算、不是推算。若客户在自己的环境复测得到不同数字，**以自己的环境为准**。

### 5.1 起服务时间与容器就绪顺序

| 项 | 值 | 口径说明 |
| --- | --- | --- |
| 全部就绪（all ready） | **100.9 秒** | 冷启动、8 GiB 类环境、轻量版 9 服务；来源 `scripts/bench/lite-probe/out/cold.json` 的 `all_ready_s` |
| 另一轮冷启动记录 | **95.7 秒** | 来源 `docs/lite-container-baseline.md` 第 1 节结论行；与上行为不同轮次，**取较大值做规划** |
| 各服务就绪时刻（相对起栈） | 缓存 7.3s / 内容处理工作进程 19.0s / 插件运行 19.4s / 数据库 19.5s / 身份服务 48.1s / 内容处理 API 84.4s / 业务适配层 87.8s / 前端 94.5s / 入口网关 100.9s | 来源同上 `cold.json` 的 `ready_at_s` |

**用途**：部署手册把健康检查轮询上限设为 **180 秒**，即"最慢服务 100.9s × 1.78 倍余量"。**这是"装得上"的判据，不是性能指标。**

### 5.2 空载内存（轻量版）

| 项 | 值 | 口径说明 |
| --- | --- | --- |
| 空载稳态合计 | **1927.2 MiB**（Docker 工作集口径） | 来源 `docs/lite-container-baseline.md` 第 2.3 节；起栈后静置 40 秒、18 次采样取窗口峰值 |
| 空载稳态合计（cgroup 上界口径） | **2293.5 MiB** | 同上；两个口径都披露，因为不同工具的读数不同 |
| 冷启动峰值合计（工作集口径） | **1835.5 MiB** | 来源 `scripts/bench/lite-probe/out/cold.json` 的 `sum_peak_mib` |
| 单次完整链路的额外内存 | **< 10 MiB** | 来源 `docs/lite-container-baseline.md` 第 2.4 节（链路前 1150.1 → 链路峰值 1160.1） |

**结论（可作为容量规划依据，但仅限轻量版）**：轻量版内存由"进程基线"决定，**不由请求量决定**（在本量级下）。8 GiB 机器的余量 ≥ 5.6 GiB，可覆盖短时峰值与系统缓存。

### 5.3 一个必须披露的反例（配置错误的代价）

同一套编排，只去掉身份服务的堆内存上限，空载就会出现：单服务 **2166.8 MiB**、整机合计 **3304.5 MiB**（cgroup 上限口径 3667.9 MiB）——**比设置上限高 72%**。

来源：`docs/lite-container-baseline.md` 第 2.5 节。

**这条写进本文的原因**：客户若自行改编排（例如为了"让身份服务更快"去掉内存上限），**第 5.2 节的结论立即作废**。改动编排后必须重新测量。

### 5.4 非正式观测（B 级，**不可作为容量承诺**）

| 项 | 观测值 | 为什么只能算 B 级 |
| --- | --- | --- |
| 单次对话完整链路延迟 | 1.20 / 1.79 / 1.37 / 1.78 / 2.09 秒（5 次，全部成功） | 样本仅 5 次、单机、**含真实上游延迟**、未做并发、未做受控环境；来源 `docs/lite-container-baseline.md` 第 2.4 节 |

**结论**：这组数字只说明"链路是通的、量级在秒级"，**不能用来回答"100 人同时用会不会卡"**。后者属于第 6 章的压测范围，当前"待压测"。

## 6. 压测方案（待执行）

### 6.1 场景划分（4 个）

| 场景 | 测什么 | 为什么单列 |
| --- | --- | --- |
| **S1 对话首字** | 从请求发出到首字出现 | 体感核心指标；与回答长度无关，可稳定比较 |
| **S2 知识库检索** | 提问到检索完成并组装出答案的开头 | 资料量增长后最先劣化的环节 |
| **S3 文档解析** | 上传一份文档到"处理完成" | 与文件大小相关，需按大小分档（小/中/大） |
| **S4 插件任务** | 工作台任务的单步执行耗时与整体完成时间 | 含外部平台调用，受第三方延迟影响最大，**必须单独披露** |

### 6.2 每个场景的负载模型

| 场景 | 负载模型 | 加压方式 | 观测项 | 备注 |
| --- | --- | --- | --- | --- |
| S1 对话首字 | 固定输入长度、固定输出长度上限；同一会话单轮；不同用户会话隔离 | 100 / 200 / 500 并发，每档 5 分钟 | 首字 P50/P95/P99、RPS、错误分类、内存峰值 | 必须分两组：**mock 上游**（标注"不含上游延迟"）与**真实上游**（标注服务与网络） |
| S2 知识库检索 | 每库 500 份文档、每份 ≤ 20 页；问题集合固定（50 条，覆盖"能答/不能答"两类） | 100 / 200 并发，每档 5 分钟 | 检索 P95、引用命中率、无答案时的耗时 | "不能答"的问题不能比"能答"的快一个数量级——否则说明检索被跳过 |
| S3 文档解析 | 三档文件：1 MB / 10 MB / 40 MB（接近 50 MB 上限） | 串行 20 次 + 并发 10/20 | 解析完成时间 P50/P95、失败率、内存峰值 | 40 MB 档必须测：这是最容易触发内存与超时问题的区间 |
| S4 插件任务 | 三个场景工作台各跑 20 个任务；外部平台用**桩服务**与**真实平台**各一轮 | 并发 10 / 20 | 单步耗时、整体完成时间、失败分类 | **真实平台那一轮必须披露第三方延迟**，不得混入产品能力结论 |

## 7. SaaS 与私有化：两种形态的基准**不可混用**

| 维度 | 私有化（单机轻量版） | SaaS（多租户） |
| --- | --- | --- |
| 服务规模 | 9 个常驻服务，共用数据库与缓存 | 21 个服务（常驻 20），独立检索服务与对象存储 |
| 隔离开销 | 单租户，隔离判定命中率高、无跨租户竞争 | 多租户，隔离策略与租户竞争同时存在 |
| 数据规模 | 客户自身规模，可控 | 平台总规模，邻居效应存在 |
| 网络路径 | 客户内网，延迟可控 | 公网 + 平台内网，路径更长 |
| **能否互相引用** | **不能** | **不能** |

**对外表述纪律**：

- 引用私有化数字时，必须写明"私有化单机版 / 9 服务 / 该客户配置"；
- 引用 SaaS 数字时，必须写明"SaaS / 该区域 / 当时的平台负载区间"；
- **禁止**用 SaaS 的压测结果回答私有化客户的容量问题（反之亦然）。

## 8. 影响性能的配置项（客户调参前必看）

| 配置项 | 默认值 | 调大的影响 | 调小的影响 |
| --- | --- | --- | --- |
| `OA_DB_POOL_SIZE` | 10 | 并发能力上升，数据库连接压力上升 | 并发受限，易出现排队 |
| `OA_DB_MAX_OVERFLOW` | 5 | 短时突增容忍度上升 | 高并发下更容易超时 |
| `OA_DB_POOL_TIMEOUT_SECONDS` | 5 | 排队等待更久（延迟上升、错误下降） | 快速失败（错误上升、延迟下降） |
| `OA_MAX_UPLOAD_BYTES` | 50 MB | 需**同步**调大网关上限，否则用户拿到纯文本 413 | 大文件无法上传 |
| `OA_CREDENTIAL_CACHE_TTL_SECONDS` | 300 | 减少解密次数，凭证变更生效变慢 | 变更生效快，解密开销上升 |
| `OA_VALKEY_MAXMEMORY` | 2 GB | 缓存命中率上升，内存上升 | 命中率下降，淘汰更频繁 |
| `OA_MEMORY_EXTRACT_EVERY_TURNS` | 10 | 记忆抽取更稀疏（开销低） | 抽取更频繁（开销高） |
| `OA_MEMORY_EMBEDDING_ENABLED` | 关闭 | 打开会引入外部语义检索调用，**冷启动与召回延迟均上升** | 关闭时召回按类别+时间+置信度，语义精度下降但更快 |
| `OA_RATELIMIT_DEFAULT_PER_MINUTE` | 120 | 容忍更密集的调用 | 更早触发频率保护（表现为"当前使用人数较多"） |
| 身份服务堆上限 | `-Xmx384m` | **不设上限会让整机内存高 72%**（见 5.3） | 设得过小会导致登录变慢甚至失败 |

> 这些配置**改动后必须重新测量**。本文第 5 章的结论只对"默认配置 + 默认编排"成立。
