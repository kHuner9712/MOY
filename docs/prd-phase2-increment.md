**P2-KB-01 知识库设置与生命周期闭环**

- **用户价值**：知识库能被改名、改可见范围、改内容切分精细度、能删除；这是「商用级」的最低门槛，当前无编辑与删除入口。
- **功能描述**：
  1. 知识库详情页可编辑：名称（1-128 字）、描述（≤1024 字）、内容切分精细度（两档：「标准」「精细」）。
  2. 内容切分精细度在**知识库级**持久化，作为该库后续所有文档的默认处理方式；上传时可选单次覆盖（覆盖不改变库级设置）。
  3. 修改切分精细度时给出明确提示：仅对**之后上传的文档**生效，已处理文档需在文档行点「按新设置重新处理」。
  4. 删除知识库需二次确认，确认框须展示「该库下 N 个文档将一并删除，删除后不可恢复」；删除为软删除，列表内立即不可见，审计记录保留。
  5. 边界条件：无 `knowledge:base:update` 权限时按钮置灰并提示原因文案；库被删除后所有其下文档接口返回 `11001`；正在被引用（活跃会话）时允许删除但给出「已有对话引用该库，历史回答中的引用将无法定位」提示。
- **涉及端点**：
  - `[扩展]` `POST /api/v1/knowledge/bases`（R1）：请求新增可选 `chunk_policy`（`default`｜`fine`，缺省 `default`）；响应新增 `chunk_policy`。
  - `[扩展]` `GET /api/v1/knowledge/bases`（R2）：`KnowledgeBaseItem` 新增 `chunk_policy`、`my_role`（当前用户对该库的角色：`owner`｜`editor`｜`viewer`）、`updated_at`；`visibility` 枚举新增 `restricted`（指定成员可见）。
  - `[新增]` `PATCH /api/v1/knowledge/bases/{base_id}`
    - 请求：`{ "name"?: string, "description"?: string, "chunk_policy"?: "default"|"fine", "visibility"?: "organization"|"private"|"restricted" }`（至少一项）
    - 响应 `data`：`{ "base_id", "name", "description", "chunk_policy", "visibility", "updated_at" }`
    - 错误：`11001` 库不存在；`20003` 无权限；`20001` 参数非法
  - `[新增]` `DELETE /api/v1/knowledge/bases/{base_id}`
    - 响应 `data`：`{ "base_id", "deleted": true, "deleted_document_count": 12 }`
    - 错误：`11001`；`20003`（仅 `owner`/`org_admin` 可删）；`20005` 并发冲突
- **业务化文案要求**：`chunk_policy` → 「内容切分精细度」；选项文案「标准 · 处理更快，适合手册与说明文档」「精细 · 条款定位更准，适合制度与合同」；**禁止出现**「分块 / chunk / 切片 / 向量 / 索引」。
- **验收标准（可执行断言）**：
  1. 新建库 `chunk_policy=fine` → `GET /knowledge/bases` 该库返回 `fine`；上传文档不带 `chunk_policy` 时按 `fine` 处理，响应可查。
  2. `PATCH` 改名为空字符串返回 `20001`，界面提示「知识库名称不能为空」。
  3. 无权限账号调用 `PATCH`/`DELETE` 返回 `20003`，前端按钮置灰且 hover 有原因文案。
  4. `DELETE` 后 `GET /knowledge/bases` 不再返回该库；`GET /knowledge/bases/{id}/documents` 返回 `11001`；操作记录中可见「删除知识库」条目。
  5. 全流程界面无一处出现禁用词（第 7 章清单扫描 0 命中）。

**P2-KB-02 知识库文档清单与处理进度细化**

- **用户价值**：当前只有单文档进度查询，没有文档清单，用户无法知道「我传了哪些文档、哪些能用、哪些卡住了」。这是知识库详情页的主区块。
- **功能描述**：
  1. 知识库详情页文档区：分页列表，列包含 文档名称、上传人、上传时间、处理阶段、进度、文档大小、操作（重新处理 / 删除 / 查看来源）。
  2. 处理阶段对用户展示为 5 个业务环节：`uploaded`「已上传」→ `parsing`「正在读取内容」→ `preparing`「正在准备内容」→ `completed`「可使用」/ `failed`「处理未成功」。保留原三态 `index_status` 作为**兼容字段**（`processing`/`completed`/`failed`），新字段 `stage` 提供细化阶段；两者必须同时返回且语义一致（`completed` ⟺ `stage=completed`）。
  3. 处理中展示预估剩余时间（`estimated_remaining_seconds`，无法预估时返回 `null` 且前端只显示「处理中」文案，不显示进度条数值）。
  4. 失败展示业务语言原因 `error_message` + 「重新处理」按钮（复用 R5）。
  5. 支持按 名称关键字 / 处理阶段 筛选；支持按上传时间排序。
  6. 边界条件：单库文档 > 5000 时分页必须稳定（禁止全量返回）；删除处理中的文档需先取消处理，返回 `11006` 并提示「文档正在处理，请稍后再删除」。
- **涉及端点**：
  - `[新增]` `GET /api/v1/knowledge/bases/{base_id}/documents?page=1&page_size=20&keyword=&stage=&sort=uploaded_at:desc`
    - 响应 `data`：`{ "items": [{ "document_id", "file_name", "file_size", "uploader_name", "uploaded_at", "index_status", "stage", "progress", "estimated_remaining_seconds", "segment_count", "error_message" }], "meta": { "page", "page_size", "total", "total_pages" } }`
    - 错误：`11001`
  - `[扩展]` `GET /api/v1/knowledge/bases/{base_id}/documents/{doc_id}`（R4）：新增 `stage`、`estimated_remaining_seconds`、`file_size`、`uploaded_at`
  - `[复用]` `POST .../documents/{doc_id}/reindex`（R5）、`DELETE .../documents/{doc_id}`（R6）
- **业务化文案要求**：`index_status`/`stage` 一律映射为上述中文；`segment_count` → 「内容片段数」（仅在文档详情展开区显示，列表不显示）；**禁止出现**「索引 / 向量化 / 分块 / 任务 ID」。
- **验收标准**：
  1. 上传后 1s 内进入列表，阶段依次流转至「可使用」，进度单调不减。
  2. 构造解析失败文档：列表显示「处理未成功」+ 业务语言原因 + 「重新处理」按钮，点击后阶段回到「正在读取内容」。
  3. 筛选 `stage=failed` 仅返回失败文档；关键字筛选大小写不敏感。
  4. 5000 条文档下第 250 页返回正确且响应体 < 200KB（不允许全量返回）。
  5. 处理中删除返回 `11006`，文案为「文档正在处理，请稍后再删除」。

**P2-KB-03 知识库可见范围与成员授权**

- **用户价值**：敏感资料（薪酬、合同、客户清单）必须按人按部门授权，这是企业采购的硬门槛。
- **功能描述**：
  1. 可见范围三档：「全企业可见」（`organization`）、「指定成员可见」（`restricted`）、「仅自己可见」（`private`）。
  2. 「指定成员可见」下维护授权清单，授权对象支持三类：单个成员、部门（含子部门）、角色。同一对象重复授权以最新为准（幂等）。
  3. 授权记录含授权人、授权时间、对象类型、对象名称、该对象权限级别（`viewer` 仅问答/`editor` 可上传与管理文档）。
  4. 知识库「所有者」自动拥有最高权限且不可被撤销；撤销授权立即生效，被撤销成员下一次请求返回 `20003`，且该库从其列表消失。
  5. 列表/检索/问答三处必须**同一套判定**（权限隔离红线）：未授权成员在知识库列表看不到该库、`R7` 检索返回 `20003`、对话中携带未授权 `knowledge_base_ids` 时该库被静默跳过（不报错、不在引用中出现）。
  6. 边界条件：授权对象为部门时，成员后续加入/离开该部门权限自动随之变化；`guest` 角色不可被授予 `editor`；不允许把知识库授权给自己所在部门的上级部门以外的空对象。
- **涉及端点**：
  - `[扩展]` R1/R2 的 `visibility` 枚举新增 `restricted`（见 P2-KB-01）
  - `[新增]` `GET /api/v1/knowledge/bases/{base_id}/grants?page=&page_size=`
    - 响应：`{ "items": [{ "grant_id": "grnt_...", "subject_type": "user"|"department"|"role", "subject_id", "subject_name", "permission": "viewer"|"editor", "granted_by_name", "granted_at" }], "meta": {...} }`
  - `[新增]` `POST /api/v1/knowledge/bases/{base_id}/grants`
    - 请求：`{ "subject_type": "user"|"department"|"role", "subject_ids": ["usr_..."], "permission": "viewer"|"editor" }`（批量，≤50）
    - 响应：`{ "created_count": 3, "skipped_count": 1 }`（重复授权计入 skipped，不报错）
  - `[新增]` `DELETE /api/v1/knowledge/bases/{base_id}/grants/{grant_id}` → `{ "grant_id", "deleted": true }`
  - 内部判权统一走 `[复用]` `POST /api/v1/identity/verify`（U1），`permission=knowledge:base:read` + `resource={type:"knowledge_base",id}`
- **业务化文案要求**：「可见范围」「谁可以看」「添加成员 / 添加部门 / 添加角色」「可提问」「可上传与管理」；**禁止出现**「ACL / 权限位 / 主体 / 资源标识」。
- **验收标准**：
  1. 库设为 `restricted` 且仅授权成员 A：成员 B 的库列表不含该库；B 直接调 `GET /bases/{id}/documents` 返回 `20003`；B 调 `R7` 检索返回 `20003`。
  2. 授权给部门 D：D 内成员可访问；把该成员移出 D 后立即不可访问（≤ 5s 内生效，缓存 TTL 上限 5s）。
  3. 同一 `subject_id` 连续授权两次：第二次 `skipped_count=1`，不产生重复条目。
  4. 撤销授权后，被撤销账号刷新页面库消失且无二次报错。
  5. `guest` 角色授予 `editor` 返回 `20001` 且文案为「访客只能查看，不能上传或管理文档」。
  6. 授权操作写入操作记录，字段含 操作人、对象、时间。

**P2-KB-04 引用溯源回链与片段定位**

- **用户价值**：AI 答案要能核对。用户点引用必须能跳到原文那一段，而不是只看到一个文件名。
- **功能描述**：
  1. 对话回答中的引用条（含流式 `citation` 事件）携带可定位信息：所属知识库、文档、片段 ID、位置（页码/段落）。
  2. 点击引用 → 右侧抽屉展示：文档名 + 所属知识库 + 该片段完整内容 + 上下文（前后各 1 段）+ 位置（`第 12 页 · 第 3 段`）+ 「查看文档详情」。
  3. 「在文档中定位」：跳转知识库详情页并展开该文档，高亮对应位置；无位置信息（如纯文本文件无页码）时降级为展示片段内容并提示「该文档没有页码信息，已定位到相关片段」。
  4. 片段在上传者重新处理后 ID 可能失效：定位失败时不能报错，展示「该引用来自旧版本内容，原文已更新」并提供文档入口。
  5. 边界条件：引用所属知识库已被删除或用户已无权限 → 抽屉展示「该引用已不可查看」并隐藏定位入口（不返回技术错误码）；一次回答引用 > 20 条时抽屉分组折叠展示。
- **涉及端点**：
  - `[扩展]` `POST /api/v1/model/generate`（M1）与 `POST /api/v1/model/generate/stream`（M2）的 `citation` 事件：新增 `base_id`、`base_name`、`segment_id`、`document_id`、`position`（`{page|null, paragraph|null}`）；旧字段 `document_name`/`segment_content` 保留不变。
  - `[扩展]` `POST /api/v1/knowledge/search`（R7）：`segments[]` 新增 `base_id`、`base_name`、`segment_id`（`position` 已存在）
  - `[新增]` `GET /api/v1/knowledge/bases/{base_id}/documents/{doc_id}/segments/{segment_id}?with_context=true`
    - 响应 `data`：`{ "segment_id", "document_id", "document_name", "base_id", "base_name", "content", "context_before", "context_after", "position": {"page": 12, "paragraph": 3}, "status": "valid"|"stale" }`
    - 错误：`11001` 库不存在；`11004` 文档未处理完；`20003` 无权限；`status=stale` 时返回 200 而非错误
- **业务化文案要求**：「引用来源」「原文位置」「第 X 页 · 第 Y 段」「该引用来自旧版本内容，原文已更新」「该引用已不可查看」；**禁止出现**「segment / chunk / score / 相似度 / 召回」。
- **验收标准**：
  1. 对含 PDF 的知识库提问并命中，回答引用条可点击，抽屉展示片段全文与前后文，位置显示为 `第 N 页 · 第 M 段`。

  4. 删除该知识库后点击旧引用：显示「该引用已不可查看」。
  5. 流式回答过程中 `citation` 事件到达即可点击（不要求等 `done`）。

**P2-KB-05 知识库级独立访问凭据（阶段一遗留 C-2，内部能力）**

- **用户价值**：企业内部不同知识库分属不同系统、不同密钥额度；单一全局凭据会导致串用、限流互相影响、密钥轮换停全站。**该能力对终端用户完全不可见**。
- **功能描述**：
  1. 每个知识库可绑定独立的底座侧访问凭据（数据源凭据）；未绑定时回落到平台全局凭据（行为与现状一致，保证向后兼容）。
  2. 凭据由运维在配置中登记、以加密形式存储；**任何接口响应、日志、前端页面均不得返回凭据明文或可逆信息**。
  3. 凭据轮换：换绑后新请求立即使用新凭据，进行中的上传/处理任务失败时按 `11005` 返回并允许重试；轮换全程无需重启服务。
  4. 凭据失效（401/403）时对用户展示 `11005`「知识库服务暂时不可用，请稍后重试」，不得暴露凭据错误。
  5. 边界条件：凭据读取失败时不得降级到全局凭据（防止跨库数据串用）；一个凭据可被多个库引用，删除引用前需校验。
- **涉及端点**：
  - `[内部变更]` R1-R7 全部端点的服务端实现改为按 `base_id` 解析凭据；**对外契约零改动**（无新增字段、无新增错误码）
  - `[新增-内部]` `PUT /api/v1/knowledge/bases/{base_id}/credential-binding`（仅运维角色 token 可调用，前端不调用）
    - 请求：`{ "credential_ref": "cred_xxxx" }`（引用标识，非明文）
    - 响应：`{ "base_id", "binding_status": "bound"|"fallback", "updated_at" }`
- **业务化文案要求**：终端用户界面 **0 处**出现该能力（无任何设置项、无任何提示）；`11005` 文案保持「知识库服务暂时不可用，请稍后重试」。
- **验收标准**：
  1. 库 A 绑定凭据 c1、库 B 未绑定：对两库分别上传与检索，均在各自凭据下成功，日志中可区分凭据引用（非明文）。
  2. 库 A 凭据置为无效：库 A 的 R3/R7 返回 `11005`，库 B 仍正常（故障不扩散）。
  3. 库 A 凭据失效时**不得**回落到全局凭据（检查下游调用凭据标识为 c1）。
  4. 轮换凭据后不重启服务，下一请求即生效；进行中任务失败返回 `11005` 可重试成功。
  5. 全站接口响应与前端源码禁词扫描（含 `credential`、`api_key`、`dify`）0 命中。

- **业务化文案要求**：「组织架构」「部门」「上级部门」「部门负责人」「成员数」；错误文案见上；**禁止出现**「group / LDAP / realm / 层级 ID」。

**P2-ID-02 权限点目录与角色权限配置**

- **用户价值**：管理员不需要懂权限模型就能配出「谁能看账、谁能拉人」。
- **功能描述**：
  1. 权限点目录按资源分组展示（知识库 / 工具 / 插件 / 成员 / 账单 / 操作记录 六类，共 16 个权限点，见第 6 章），每项含业务名称、业务说明、所属分组。

  4. 修改角色权限后对**该角色下全部成员立即生效**（缓存 TTL ≤ 5s）。
  5. 边界条件：权限点标识对管理员不可见（只展示业务名称）；未注册权限点调用 U1 返回 `14004`；角色数量上限 50。

  - `[新增]` `DELETE /api/v1/identity/organizations/{org_id}/roles/{role_id}`
- **业务化文案要求**：「角色权限」「权限点」「勾选该角色可以做的事」；**禁止出现**「permission string / RBAC / scope / 权限位」。`display_name` 一律中文业务语言。

  1. 权限点目录返回 6 组、16 个权限点，全部含中文 `display_name`。

**P2-ID-03 成员角色变更与移除**

- **用户价值**：人员变动是最高频管理动作；当前只能邀请不能改不能删，团队管理不可用。
- **功能描述**：
  1. 成员列表支持按 部门 / 角色 / 状态（已加入 / 待接受 / 已停用） / 关键字 筛选，分页。
  2. 单个成员可：变更角色、调整所属部门（可多部门，主部门单选）、停用/启用、移出团队。
  3. 批量操作：勾选多个成员批量改角色 / 批量移出（单次 ≤ 100）。
  4. 保护规则：不能移除或降级企业所有者（返回 `14007`「不能移除企业所有者，请先转移所有权」）；不能移除自己；管理员不能修改与自己同级或更高角色的成员（返回 `14008`「你没有权限修改该成员」）。
  5. 移出成员时提示其数据处置：「该成员创建的知识库将转交给企业管理员，个人会话不移交」；移出后其个人工具连接失效。
  6. 变更立即生效（≤5s）；所有变更写入操作记录（含变更前后值）。
- **涉及端点**：
  - `[新增]` `PATCH /api/v1/identity/organizations/{org_id}/members/{member_id}` → 请求 `{ "role"?, "department_ids"?, "primary_department_id"?, "status"? }`，响应 `{ "member_id", "role", "department_ids", "status", "updated_at" }`

  - `[扩展]` U3 成员列表新增筛选参数 `department_id`、`status`
- **业务化文案要求**：「变更角色」「调整部门」「移出团队」「停用」；确认文案「移出后该成员将无法访问企业数据，其创建的知识库将转交由企业管理员管理」；**禁止出现**「删除用户 / 撤销 token / 会话失效」等实现语言。

  1. 把成员 A 从「成员」改为「组织管理员」：A 刷新后出现管理入口；知识库授权判定按新角色生效。

  3. 批量移出 100 人返回 `succeeded=100`；含 1 名所有者时该员进入 `failed` 且不影响其他成员。
  4. 移出后该成员访问任何企业资源返回 `20003`，登录后无企业数据。
  5. 操作记录中可查到「变更角色：成员 → 组织管理员」含前后值。

**P2-ID-04 操作记录查询**

- **用户价值**：合规与追溯。现在只有接口没有页面，管理员查不了。
- **功能描述**：

  5. 边界条件：查询跨度上限 90 天（超出返回 `20001`「查询时间范围最长 90 天，请缩小范围」）；运营后台不得查看客户租户的敏感对象名称（脱敏为「*」）；无 `audit:log:read` 权限不展示入口。
- **涉及端点**：

  - `[新增]` `GET /api/v1/identity/audit-logs/actions` → `{ "groups": [{ "group": "member", "group_name": "成员管理", "actions": [{ "action": "member.role_changed", "display_name": "变更成员角色" }] }] }`
- **业务化文案要求**：页面名「操作记录」；列名「时间 / 操作人 / 角色 / 操作类型 / 对象 / 结果 / 来源地址」；空态「所选时间范围内没有操作记录」；**禁止出现**「审计日志 / audit / 事件流 / trace id」。
- **验收标准**：
  1. 执行 P2-ID-03 的改角色动作后 5s 内在操作记录中可查到，`action_display_name` 为「变更成员角色」。
  2. 按操作人模糊 + 时间范围 + 结果组合筛选，返回结果集正确。
  3. 查询跨度 91 天返回 `20001` 且文案含「90 天」。
  4. IP 为掩码形式（如 `10.12.*.*`）。
  5. 无权限账号访问接口返回 `20003`，侧边栏不出现「操作记录」入口。

**P2-BL-02 订阅与席位管理**

- **用户价值**：企业管理员能自助开通、升级、加席位、到期续费，不用找销售。
- **功能描述**：
  1. 订阅状态：`trialing`「试用中」/ `active`「生效中」/ `past_due`「待续费」/ `cancelled`「已取消」/ `expired`「已到期」。展示当前套餐、生效时间、到期时间、席位数（已用/总量）、本周期额度。
  2. 操作：开通（免费版一键开通，付费版进入支付）、升级（立即生效，按剩余天数折算差价）、降级（当前周期结束后生效，期间提示「将在 X 月 X 日切换为 X 套餐」）、加/减席位（加席位立即生效，减席位下周期生效且不得低于已用席位）、取消自动续费。

  5. 边界条件：同一企业同一时刻只有一个有效订阅；`past_due` 状态保留 7 天宽限期（功能可用，顶部提示续费），逾期转 `expired`（保留数据，高消耗能力受限）。
- **涉及端点**：

  - `[新增]` `PATCH /api/v1/billing/subscription/seats` → 请求 `{ "seats": 25 }`，响应 `{ "seats_total", "seats_used", "effective_at", "order_id"|null }`；错误 `15003`（低于已用席位）
- **业务化文案要求**：「套餐」「席位」「生效中 / 待续费 / 已到期」「升级立即生效 / 降级将在 X 月 X 日生效」「增加席位」；**禁止出现**「subscription SKU / proration / 计费周期 ID」。

  1. 免费版开通后 `status=active`，`seats_total=3`。

  4. 席位用满时新增成员返回 `15003`，前端会员邀请按钮置灰且有提示。

**P2-BL-03 用量计量与额度查询**

- **用户价值**：让用户与企业管理员清楚「用了多少、还剩多少、谁用的」，也是运营对账基础。
- **功能描述**：
  1. 计量落库：每次对话、文档处理、自动化任务产生用量记录（业务化单位：字数额度），记录维度 企业 / 部门 / 成员 / 资源类型 / 时间。
  2. 个人视图（普通成员）：本周期已用、剩余、按日趋势（近 30 天）、按能力分布（对话 / 文档问答 / 文档处理 / 自动化任务，用业务名称）。
  3. 管理视图（企业管理员）：企业总量 + 按成员 Top 20 + 按部门汇总 + 导出（P1）。
  4. 口径一致性：个人视图继续复用 M4（字段不变），M4 内部改为读计量服务，`total_units`/`used_units` 单位即「字数额度」；管理视图走新端点。
  5. 边界条件：计量写入必须幂等（同一 `generation_id`/`document_id` 不重复计）；流式回答按结束时的 `usage` 结算，异常中断按已产出的部分内容折算；计量与适配层计数的对账偏差 ≤ 1%。
- **涉及端点**：
  - `[扩展]` `GET /api/v1/model/usage?period=month`（M4）：字段不变，新增 `quota_unit: "字数额度"`；数据源改为计量服务
  - `[新增]` `GET /api/v1/billing/usage?period=2026-11&group_by=member|department|capability`
    - 响应：`{ "period", "quota_units_total", "quota_units_used", "quota_units_remaining", "usage_percent": 63.2, "breakdown": [{ "key", "display_name", "units", "percent" }], "daily_trend": [{ "date", "units" }] }`
    - 错误：`20003`（管理视图需 `billing:subscription:read`）
- **业务化文案要求**：「字数额度」「本月已用 / 剩余」「按成员 / 按部门 / 按功能」；**严禁出现**「token / 消耗量 / 计费单元 / 计量表」。
- **验收标准**：
  1. 完成一次对话后 10s 内计量落库，`/billing/usage` 与 M4 的 `used_units` 差值 = 同一时刻快照，重复请求不重复累加。
  2. 同一 `generation_id` 重放（幂等键重复）不产生第二条计量记录。
  3. 流式中途断开：计量为已产出部分折算值（>0 且 < 完整值）。
  4. 按成员 breakdown 之和 = 企业总量（误差 0）。
  5. 对账任务：适配层计数 vs 计量表偏差 ≤ 1%（阶段验收必须实跑）。
  6. 页面无 `token` 字样。

**P2-BL-04 订单、账单与支付**

- **用户价值**：能下单、能付钱、能拿到账单去报销；没有这条链路，产品不能卖。
- **功能描述**：
  1. 下单：选择套餐与席位 → 展示应付金额与账期 → 创建订单 → 进入支付。
  2. 支付方式（首版必通）：① 在线支付（专业版：接入一个国内主流支付渠道，扫码/跳转）；② 对公转账（企业版：生成线下转账凭证信息，由平台运营在运营后台**人工核销**，核销后订阅生效）。
  3. 支付结果：成功后订阅立即生效并展示「支付成功，套餐已生效」；失败/超时展示业务语言原因 + 「重新支付」；订单在 30 分钟内未支付自动关闭（`status=closed`，文案「订单已超时关闭」）。
  4. 账单：账单列表（账期、金额、套餐、席位、状态、可下载账单文件）与订单详情（含支付流水号掩码）。
  5. 边界条件：同一企业同周期只允许一个待支付订单（重复下单复用原订单并返回 `20005` 语义提示）；支付回调必须验签且幂等（同一回调重复到达不重复开通）；金额以分为单位存储，展示保留两位小数。
- **涉及端点**：
  - `[新增]` `POST /api/v1/billing/orders` → 请求 `{ "plan_code", "seats", "order_type": "new"|"renew"|"upgrade"|"seats" , "payment_method": "online"|"offline_transfer" }`；响应 `{ "order_id": "ord_...", "amount_cents", "currency": "CNY", "status": "pending_payment", "payment_method", "pay_url"|null, "bank_info"|null, "expires_at" }`；错误 `15002`/`15004`/`20005`
  - `[新增]` `GET /api/v1/billing/orders?status=&page=` → 订单分页
  - `[新增]` `GET /api/v1/billing/orders/{order_id}` → 订单详情（含 `payment_no_masked`、`paid_at`、`invoice_status`）
  - `[新增]` `GET /api/v1/billing/invoices?period=` → `{ "items": [{ "invoice_id", "period", "amount_cents", "status": "issued"|"pending", "download_url" }] }`
  - `[新增-内部]` `POST /api/v1/billing/payments/callback`（支付渠道回调，**免 Bearer 鉴权但必须验签**，幂等）
- **业务化文案要求**：「订单」「应付金额」「在线支付 / 对公转账」「支付成功，套餐已生效」「订单已超时关闭，请重新下单」「账单」；**严禁出现**「回调 / webhook / 签名 / 商户号 / 交易流水」。
- **验收标准**：
  1. 在线支付全流程：下单 → 支付 → 回调 → 订阅生效，界面 3 步内完成且状态正确。
  2. 对公转账：下单后展示转账信息，运营后台核销后订阅生效、订单变「已支付」。
  3. 重复回调 3 次：订阅只生效一次，无重复账单。
  4. 30 分钟未支付订单自动关闭，页面显示「订单已超时关闭」。

#### 3.1.6 体验统一与兜底（P2-UX，1 条）

---

**P2-UX-01 全页面状态兜底（错误态 / 空态 / 加载态 / 重试）**

- **用户价值**：任何异常都不能白屏、不能出英文、不能出错误码，这是「首版即商用」的底线。
- **功能描述**：
  1. 统一状态组件：`LoadingState`（骨架屏，列表/表格/卡片三种形态）、`EmptyState`（图形 + 主文案 + 可选行动按钮）、`ErrorState`（业务文案 + 重试按钮 + 可选「联系管理员」）。
  2. 10 个页面 100% 覆盖三态；网络错误、超时、无权限、额度不足四类场景各有专属文案（见第 4 章逐页文案）。
  3. 全局兜底：未捕获异常、接口 5xx、流式中断 → 统一 toast + 可重试；**禁止**展示 `code`、堆栈、英文原文。
  4. 错误态重试：点击重试重新发起原请求（不刷新整页）；连续 3 次失败提示「多次尝试未成功，请稍后再试或联系管理员」。
  5. 边界条件：同一错误 3s 内多次出现只提示一次（防刷屏）；离线状态顶部固定提示条「网络连接已断开，请检查网络后重试」。
- **涉及端点**：无新增；依赖统一响应 `{code,message,data}` 与 `lib/business-errors.ts` 映射表（新增 14005-14008 / 15001-15008 映射，见附录 B）。
- **业务化文案要求**：错误态统一句式「<发生了什么>，<怎么办>」，如「知识库暂时无法加载，请重试」；**禁止出现**任何错误码、英文、技术名词。
- **验收标准**：
  1. 对 10 个页面逐一断网 / 注入 500 / 注入 20003：均展示 ErrorState 且含重试按钮，点击后恢复。
  2. 所有列表页在无数据与筛选无结果时文案不同。
  3. 全站文案扫描：错误码正则 `\b[1-3]\d{4}\b` 在 UI 文案中 0 命中；英文技术词 0 命中。
  4. 连续 3 次失败后展示「多次尝试未成功」提示。
  5. 首屏骨架屏与内容切换无布局抖动（CLS 可接受，无白屏 > 300ms）。

### 5.2 计量口径

- **唯一计量单位：字数额度**。所有能力折算为字数额度消耗（对话 = 输入 + 输出字数；文档处理 = 解析字数 × 精细度系数（标准 1.0 / 精细 1.2）；自动化任务 = 各步骤字数之和）。
- 计量维度：企业 / 部门 / 成员 / 能力 / 日期。写入幂等（按 `generation_id`、`document_id`、`task_id`）。
- 展示精度：以「万字」展示（`1,234,567` → `123.5 万字`），剩余额度不足 1 万时展示精确到字。
- **禁止**在用户界面出现 `token`、`units`、`消耗点数` 等原始字段名。

### 5.3 超限行为（软限制，不停服）

| 阈值 | 行为（用户可感知） |
| --- | --- |
| ≥ 80% | 顶部提示条「本月字数额度已使用 80%，剩余 X 万字」（黄）；管理员收到站内通知 |
| ≥ 100% | ① 对话继续可用，但进入「常规模式」：单次回答长度受限，界面提示「额度已用完，当前为常规模式，升级套餐可恢复完整能力」；② 文档上传暂停处理（已上传的保留，处理排队到额度恢复或升级后）；③ 自动化任务排队不启动；④ 管理员收到通知与升级入口 |
| 周期结束 | 额度重置为套餐额度；未用完不结转 |
| `past_due` 逾期 > 7 天 | 高消耗能力（文档处理、自动化任务）停用，对话保持「常规模式」，数据完整保留 |

> **红线**：任何情况下不得整体停服、不得白屏、不得出现「暂不支持」；额度限制必须在界面上有明确可执行出路（升级 / 加购 / 等额度重置）。

### 5.4 展示口径（业务语言）

- 个人中心：「本月字数额度 已用 123.5 万 / 共 300 万」。
- 企业账单：「本周期额度 6,000 万字，已用 2,341 万字，剩余 3,659 万字」。
- 运营后台：同上口径 + 折算金额（仅运营可见）。
- **任何角色的界面均不展示** 模型名、token、单价成本、供应商。

### 6.3 三层校验规则（权限隔离红线）

1. **租户层**：token 的 `tenant_id` 必须与资源 `tenant_id` 一致，否则 `20003`；运营角色例外但只能拿到聚合数据。
2. **组织层**：知识库「指定部门可见」、部门数据范围、计费账单按 `org_id` 隔离。
3. **角色/权限点层**：所有写操作必须经 `POST /api/v1/identity/verify`（U1）校验，业务代码不得自行判权（FLOW-05 红线）。
4. **缓存**：权限判定结果缓存 TTL ≤ 5s，角色/授权变更后 5s 内全站生效。
5. **对象级**：知识库、文档、工具连接、订单均需对象级校验，禁止「列表过滤了但详情接口没校验」。

## 8. 技术与协作风险（请架构师重点关注）

| # | 风险 | 影响 | 产品侧建议 |
| --- | --- | --- | --- |
| R1 | **端点基线扩张**：本阶段新增 38 个端点（业务域另行基线），原「30 端点」CI 断言（`len(business) != 30`）与 `docs/api/README.md`、架构文档三处一致性将被打破 | 若不同步，CI 直接红；若草率改断言，契约基线失去意义 | 建议把端点分两套基线：**适配层 30 端点（不变）+ 业务域端点（新基线，单独断言）**；所有 `[扩展]` 字段必须向后兼容并补 OpenAPI diff 断言 |
| R2 | **知识库凭据多租化 + 引用回链的片段稳定性**：per-kb 凭据要求按 `base_id` 解析凭据（现为全局单例），而回链依赖 `segment_id` 稳定；`R5` 重新处理后 `segment_id` 会变，历史引用必然失效 | 凭据改造影响 R1-R7 全链路；回链在文档重处理后大面积失效 | 建议引入「片段稳定标识」：`segment_id` 与内容指纹双写，失效时返回 `status=stale`（本 PRD 已按 200 而非错误设计），架构侧需明确 stale 判定与保留期 |
| R3 | **计量落库与 M4 一致性**：M4 现在读 Redis 计数，本阶段要落计量表并保证 ≤1% 偏差；流式结算、幂等重放、超时中断三种边界最容易出错 | 偏差大 = 账单不可信 = 商用不成立；也会导致 M4 与 `/billing/usage` 两处数字不一致被用户发现 | 建议「用量事件」单一写入源：生成完成后发一条幂等用量事件，M4 与 `/billing/usage` 均读同一存储；对账任务纳入 CI 或每日定时；架构需明确计量服务归属（业务层）与适配层计数器的关系 |
| R4 | 组织层级树与 Keycloak group 模型映射（Keycloak group 非严格树、成员可多组，且无「负责人」概念） | 组织树一旦映射错误，权限判定会大面积错 | 建议部门树权威数据放业务库，Keycloak group 仅做同步投影；U1 判权时以业务库为准 |
| R5 | 运营角色跨租户访问与「最小可见」边界 | 越权看客户内容 = 合规事故 | 建议运营端点只返回聚合与计数，**永不返回**对话内容、文档原文、成员邮箱明文 |
