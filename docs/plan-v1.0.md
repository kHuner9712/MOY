## 一、项目核心定义与验收基线

### 1.1 产品定位与本期范围

**产品定位（长期，见《项目总纲》§1.2）**：面向广泛工作需求的模块化 AI 工作平台。

**V1.0 范围定位（本期）**：以企业办公场景为首批落地切入点，交付一套可私有化、可跨生态集成、
岗位插件化的办公 AI 能力。本方案中的"企业级"指**交付对象的技术与合规要求**（权限、审计、隔离、部署），
不表示产品只服务企业用户，也不构成产品边界（总纲 §5、§6.1；ADR-0005 D-10）。

本期差异化（V1.0 范围内）：
- 不绑定单一办公生态，聚焦首批工具打通（验证状态见 `prd-v1.0.md` §5.1 成熟度列）；
- 以插件化体系覆盖首批岗位工作流；
- 支持 SaaS 与私有化双部署形态（成熟度以总纲第十一章分级为准）；
- 面向职场用户的界面屏蔽技术细节。

### 1.2 核心设计原则（强制执行）

1. **面向商用交付为目标，对外表述以已验证状态为准**：拒绝 Demo 级产物；功能是否"可用"以总纲第十一章状态分级为唯一口径，未达 L3（集成已验证）不得对外声明为已可用（ADR-0005 D-14）
2. **技术黑盒化**：面向终端用户的界面严禁出现模型名称、向量库、RAG、Agent 等技术术语，所有错误提示使用业务语言，禁止抛出代码报错与堆栈（适用范围：终端 UI；内部文档、运营后台、适配层日志不受限——ADR-0005 D-23）
3. **适配层唯一原则**：所有上层业务代码、场景插件，只能调用自研统一适配层的标准接口，**严禁直接调用 Dify 原生 API/SDK**，从架构上解耦上游依赖
4. **合规优先**：所有引入的开源组件必须经过协议审核，GPL/AGPL 等强传染协议组件禁止进入核心代码库
5. **体验一致性**：面向终端用户的主界面 UI、交互逻辑、文案风格统一（强制项），插件不得使用独立设计规范

## 二、整体技术架构

采用「**底座层 + 适配层 + 业务层 + 插件层 + 前端层**」的五层解耦架构，核心设计思想是：用成熟开源底座解决基础能力，用自研适配层屏蔽上游差异、保障自主可控，用插件化体系实现全场景扩展。

```
┌─────────────────────────────────────────────────┐
│  前端交互层 （自研Next.js + 统一组件库）          │
│  对话界面 / 知识库 / 插件市场 / 工作流可视化 / 团队管理 │
├─────────────────────────────────────────────────┤
│  场景插件层 （自研标准插件体系）                  │
│  研发工作台 / 内容运营工作台 / 行政人事工作台 / ...  │
├─────────────────────────────────────────────────┤
│  业务能力层 （自研业务逻辑）                      │
│  统一权限 / 计费计量 / 运营管理 / 数据统计         │
├─────────────────────────────────────────────────┤
│  🔴 自研统一适配层 （核心解耦层，必须100%自研）    │
│  模型服务接口 / RAG服务接口 / Agent服务接口 / 工具服务接口 / 用户服务接口 │
├─────────────────────────────────────────────────┤
│  底座能力层 （基于Dify二次开发，开源底座）         │
│  多模型调度 / RAG引擎 / Agent编排 / 工具接入 / 多租户权限 │
├─────────────────────────────────────────────────┤
│  基础设施层 （Docker + K8s）                     │
│  计算资源 / 存储 / 网络 / 监控告警 / 容器编排      │
└─────────────────────────────────────────────────┘
```

### 架构核心说明

1. **自研统一适配层是整个架构的核心**：所有底座能力全部通过适配层转换为自研标准接口，上层业务完全感知不到底层是 Dify 还是自研底座。未来替换底层底座时，仅需修改适配层，上层代码零改动。
2. **底座层仅做基础能力提供者**：不对 Dify 核心逻辑做深度魔改，仅做必要的功能补全与 Bug 修复，降低后续上游版本升级成本。
3. **所有场景能力全部插件化**：不做硬编码的场景功能，全部遵循统一插件标准开发，保障可扩展、可插拔、可由第三方贡献。

## 三、核心模块详细开发说明

### 3.1 底座能力层（基于 Dify 二次开发）

#### 职责

提供大模型调度、RAG 检索、Agent 编排、工具调用、基础多租户等底层原子能力

#### 技术底座

- 核心项目：Dify（Apache 2.0 协议）
- 配套组件：Milvus 向量库、Unstructured 文档解析、LiteLLM 模型路由

#### 开发任务

1. 部署并调试 Dify 社区版（Apache-2.0，`dify-api:1.17.1`）底座，完成基础功能验证（商业版仅作评估项，见 ADR-0006 D-31）
2. 接入首批模型矩阵：
   - 闭源 API：豆包、GPT-4o、Claude 3.5、通义千问
   - 开源模型：Qwen2.5 系列、Llama 3.1 系列、DeepSeek-Coder
3. 优化 RAG 分块策略与召回效果，达到商用级问答准确率
4. 补齐 Dify 原生不支持的办公工具对接（按需扩展）
5. 适配私有化纯离线部署场景，移除所有外网依赖

#### 输出标准

- 底座服务稳定运行，所有原子能力可通过原生 API 调用
- 支持单节点与集群两种部署模式
- 输出底座 API 接口文档（仅适配层开发可见）

### 3.2 自研统一适配层（核心模块，最高优先级）

#### 职责

屏蔽底层底座差异，定义全平台统一能力标准，是业务层与底座层之间的唯一中间层

#### 技术要求

- 独立服务部署，RESTful 标准接口，统一返回格式
- 无任何业务逻辑，仅做协议转换、参数校验、错误统一封装

#### 五大标准接口规范（必须严格定义）

1. **模型服务接口**
   - 统一对话调用、流式输出、模型切换、成本统计
   - 入参：prompt、上下文、模型类型、参数配置；出参：统一格式的回复内容、token 用量
2. **RAG 服务接口**
   - 统一文档上传、索引构建、检索问答、引用溯源
   - 入参：文档、知识库 ID、查询内容；出参：答案、引用片段、来源文档
3. **Agent 服务接口**
   - 统一任务创建、执行、状态查询、结果回调
   - 入参：任务描述、可用工具、工作流配置；出参：执行状态、步骤详情、最终结果
4. **工具服务接口**
   - 统一第三方办公工具的鉴权、调用、数据同步
   - 入参：工具类型、操作指令、参数；出参：执行结果、返回数据
5. **用户权限服务接口**
   - 统一用户、组织、角色、权限校验
   - 入参：用户 ID、权限点；出参：权限校验结果、用户信息

#### 强制约束

- 所有接口命名、参数格式、错误码完全自研定义，不与 Dify 原生接口保持一致
- 上层业务代码与插件，只能调用该层接口，严禁绕过适配层直接访问底座
- 适配层本身无状态，支持水平扩展

### 3.3 业务能力层

#### 职责

实现产品的业务逻辑与企业级能力，是产品商业化的核心支撑

#### 开发任务

1. **统一权限与组织架构**
   - 基于 Keycloak 扩展，支持企业组织架构、多级角色、细粒度权限控制
   - 支持团队邀请、成员管理、操作审计日志
2. **计费与计量体系**
   - 按 token 用量、调用次数、席位数量的多维度计量
   - 支持免费版、专业版、企业版三级套餐，支持订阅管理
3. **运营管理后台**
   - 用户管理、订单管理、数据统计、系统配置、风控审核
4. **数据统计与分析**
   - 全平台使用数据看板、功能使用率、用户活跃度统计

#### 输出标准

- 完整的企业级权限体系，满足中小团队到中型企业的管理需求
- 完整的计费与计量能力（计量、额度、订单、订阅管理）；**套餐结构与定价为设计假设，未经真实付费验证**，支付联调状态以 `prd-v1.0.md` §5.1 成熟度列为准（ADR-0005 D-18）

### 3.4 场景插件层

#### 职责

提供岗位级端到端工作流能力，是产品差异化核心，所有场景均以插件形式存在

#### 插件开发规范（强制执行）

1. **插件标准格式**：统一使用 JSON 配置文件声明插件信息、权限、输入输出、UI 扩展点
2. **能力调用**：仅允许通过统一适配层接口调用平台能力，不得直接访问底座与数据库
3. **交互规范**：所有插件前端组件必须使用平台统一组件库，不得自定义 UI 样式
4. **权限隔离**：插件必须声明所需权限，用户授权后方可调用对应工具与数据

#### V1.0 首批标杆插件（3 个，必须端到端全流程可用）

1. **前端研发工作台插件**
   - 核心流程：需求描述输入 → 需求拆解与技术方案生成 → 代码文件生成 → 单元测试生成 → Code Review → GitHub 提交
   - 复用资产：参考 Continue.dev、Aider 的代码 Agent 逻辑，适配为平台插件
   - 交付标准：输入一个明确的前端需求，可自动生成完整代码文件并提交到指定仓库
2. **内容运营工作台插件**
   - 核心流程：主题输入 → 热点素材检索 → 多平台选题策划 → 稿件生成 → 配图匹配 → 多平台定时发布 → 数据复盘
   - 对接工具：公众号、小红书、抖音、主流新媒体平台
   - 交付标准：输入运营主题，可自动生成多平台稿件并排期发布
3. **行政人事工作台插件**
   - 核心流程：招聘需求 → JD 生成 → 简历筛选与初评 → 面试邀约安排 → 入职流程生成 → 日常公文撰写
   - 对接工具：邮箱、企业微信 / 飞书、招聘平台
   - 交付标准：覆盖招聘全流程辅助与日常行政公文自动化

#### 插件市场

- 支持插件浏览、安装、启用、卸载、版本管理
- 支持插件分类、评分、使用说明
- V1.0 内置官方插件，预留第三方开发者接入能力

### 3.5 前端交互层

#### 职责

提供统一、流畅、大厂级的用户交互体验，屏蔽所有技术细节

#### 技术底座

- 前端：自研 Next.js App Router + shadcn/ui 风格统一组件库（方案阶段评估过第三方聊天前端方案，**未采用**；仓库 `deploy/` 与前端代码零引用，ADR-0005 D-13）
- 技术栈：Next.js + shadcn/ui + Tailwind CSS
- 自研统一企业级组件库

#### 核心改造与开发任务

1. **统一设计语言**
   - 建立独立产品品牌视觉（不引入任何第三方聊天前端组件），不依赖外部 UI 框架样式
   - 统一所有组件、按钮、弹窗、表单的交互规范，面向终端用户的主界面体验一致
2. **核心页面开发**
   - 对话主页：多会话侧边栏、对话窗口、附件上传、引用展示
   - 知识库页面：文档管理、知识库列表、上传与索引进度
   - 插件市场页面：插件浏览、安装、配置
   - 工作流可视化页面：任务执行进度、步骤详情、结果展示
   - 团队管理页面：组织架构、成员管理、权限配置
   - 个人中心：账户设置、套餐管理、使用统计
3. **体验优化强制要求**
   - 对话首字响应延迟 < 1s，流式输出流畅无卡顿
   - 首屏加载时间 < 2s，页面切换无白屏
   - 所有操作有即时反馈，加载状态有明确动画
   - 所有错误提示使用自然语言描述，不出现任何技术名词、错误码、堆栈信息
4. **移除所有技术向功能**
   - 去掉模型参数调节、提示词工程、工作流源码编辑等面向开发者的功能
   - 所有高级能力全部封装为一键使用的场景化功能

#### 输出标准

- 完整可运行的 Web 前端产品，响应式适配桌面端
- 交互体验达到大厂同级产品水准，无明显短板与粗糙感

### 3.6 部署与运维体系

#### 两种部署模式

1. **云端 SaaS 版**
   - 架构：K8s 多租户集群，数据逻辑隔离
   - 配套：监控告警、日志收集、弹性扩缩容、备份容灾
   - 指标：核心服务可用率 ≥ 99.5%
2. **私有化部署版**
   - 交付形式：Docker Compose 一键部署包，支持单服务器开箱即用
   - 离线支持：提供完整离线镜像包，支持无外网环境纯本地运行
   - 配套：部署手册、运维工具、升级脚本

#### 强制要求

- 两种部署模式共用同一套代码，通过配置区分运行模式
- 私有化版本支持 License 授权控制
- **成熟度口径（ADR-0005 D-18）**：私有化交付的 V1.0 承诺为「部署包 + 离线镜像 + 文档 + 运维工具」且达到 L2（功能可运行）；L3（集成已验证）需客户现场或准生产环境验证；SaaS 99.5% 可用率为验收目标，非当前实测值

## 五、强制开发规范（全员必须遵守）

### 5.1 代码规范

- 前后端均采用 ESLint / 对应语言 Lint 工具做强制代码检查，不符合规范代码禁止合并
- 核心模块必须编写单元测试，核心接口覆盖率不低于 80%
- 严格遵循 Git Flow 工作流，所有功能通过 Feature 分支开发，Code Review 后方可合并主干

### 5.2 接口规范

- 所有对外接口统一采用 RESTful 风格，统一返回格式：`{code, message, data}`
- 统一错误码体系，业务错误与系统错误分离，前端仅展示 message 字段
- 所有接口必须有完整的参数校验与异常兜底，禁止抛出未处理异常

### 5.3 开源合规规范

1. **协议黑白名单**
   - ✅ 白名单（可直接商用）：MIT、Apache 2.0、BSD
   - ⚠️ 灰名单（仅可独立进程调用，不可引入核心代码）：LGPL
   - ❌ 黑名单（禁止引入核心代码库）：GPL、AGPL、SSPL
2. **组件引入流程**：开发提申请 → 合规审核协议与成熟度 → 测试验证 → 引入依赖
3. **SCA 扫描**：每月执行一次全量依赖扫描，生成合规报告，不合规依赖限期整改
4. **版权声明**：产品 About 页面与开源声明文件中，列明所有使用的开源组件及对应协议

### 5.4 安全规范

- 所有用户数据传输与存储加密，敏感数据脱敏处理
- 所有接口做权限校验，防止越权访问
- 输入输出做安全过滤，防范 Prompt 注入、XSS、SQL 注入等攻击
- 私有化版本支持数据备份与恢复机制

### 5.5 体验规范

- 前端所有文案统一产品语气，专业、简洁、友好
- 禁止在用户界面出现任何技术术语、模型名称、组件名称
- 所有操作有反馈、所有等待有进度、所有错误有解决方案提示
- 交互逻辑符合主流办公软件使用习惯，不做反常识设计

## 六、最终验收标准（V1.0 一票否决项）

### 6.1 功能验收

- 基础能力：对话、知识库、代码辅助、团队管理四大模块可用，按 6 项可核验维度（对话 / 检索问答 / 代码辅助 / 工具调用 / 协作管理 / 成果交付）对齐通用办公 AI 的核心场景，逐维度输出「现状 / 对照结论 / 证据」（对标口径收紧，ADR-0005 D-20）
- 差异化能力：3 个标杆插件均可独立完成端到端工作流，达到岗位实用标准（涉及外部写入的环节须标注所依赖连接器成熟度）
- 跨生态能力：首批 5 款办公工具完成鉴权→调用→数据回流全链路联调并留记录；**当前为桩实现（L1），不得计为"深度打通"**（ADR-0005 D-19）

### 6.2 体验验收

- 交互一致性：全产品 UI、交互、文案 100% 统一，无割裂感
- 易用性：普通职场用户无需培训即可上手使用所有核心功能
- 无技术暴露：用户全程感知不到任何 AI 技术概念与底层组件

### 6.3 性能验收

- 首屏加载时间 ≤ 2s
- 普通对话首字响应 ≤ 1s
- 单页并发支持 ≥ 1000 用户同时在线
- 核心服务可用率 ≥ 99.5%

### 6.4 安全合规验收

- 开源合规审计 100% 通过，无强传染协议风险
- 安全渗透测试无高危、中危漏洞
- 数据加密与权限隔离机制完善

### 6.5 交付验收

- SaaS 版本可正常注册、付费、使用
- 私有化版本可一键部署，支持纯离线运行
- 配套文档齐全，可直接交付客户使用

## 七、风险预案与执行原则

### 7.1 核心风险预案

表格

| 风险点 | 应对方案 |
| --- | --- |
| Dify 底层能力不满足深度定制需求 | 统一适配层已做解耦，可针对单个能力模块替换为自研实现，不影响整体架构 |
| 上游开源项目停止维护 | 核心组件均储备 2 个以上备选方案，通过适配层可快速切换替换 |
| 场景插件开发难度超预期 | 优先保障核心流程跑通，非核心能力分期迭代，首版保证端到端可用 |
| 性能不达标 | 提前 2 周启动压测，针对瓶颈点做专项优化，必要时增加缓存与降级策略 |

### 7.2 执行总原则

1. **复用优先**：能使用成熟开源组件的，绝不从零开发；优先选择社区活跃、协议宽松的成熟项目
2. **接口先行**：所有模块开发先定接口规范，再做内部实现，保障并行开发效率
3. **质量底线**：宁可延期个别非核心功能，也不能降低商用级质量标准
4. **差异化优先**：研发资源优先投入到跨生态、场景插件、体验打磨等差异化领域，底座能力够用即可，不追求底层技术炫技
