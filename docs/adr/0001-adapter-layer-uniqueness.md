# ADR-0001：采纳「适配层唯一原则」作为一票否决级架构约束

- **状态**：已接受（Accepted）
- **日期**：2026-10-21
- **决策者**：齐活林（交付总监）、高见远（架构师）、寇豆码（工程师）、许清楚（产品经理）
- **相关文档**：`docs/architecture-v1.0.md` 第 1.4 节、第 3 章、第 6.2 节；`docs/plan-v1.0.md` 第 1.2 节
- **决策编号**：T01（项目基础设施 + 接口规范定稿）

---

## 一、背景

平台以 Dify（Apache-2.0 为基础的**修改版**，附加约束见 ADR-0002 §9.2）为底座提供 AI 原子能力，通过自研统一适配层向上层
（前端交互层、场景插件层、业务能力层）输出标准接口。

如果上层绕过适配层直接调用底座，将导致：

1. **底座替换成本爆炸**：总方案 7.1 已将「底座能力不足 / 社区停止维护」
   列为主要风险，预案是「相关能力模块替换为自研实现，仅修改适配层」。
   一旦上层直连，替换底座将退化为全仓库重构。
2. **技术黑盒化失效**：PRD 附录 A 系列红线要求终端用户全程感知不到
   AI 技术概念与底层组件。底座原生形态一旦泄露到前端，
   模型名、向量库、RAG 参数、Agent 节点类型都会暴露给用户。
3. **合规风险扩散**：底座 API 文档按总方案 3.1 的输出标准「仅适配层开发可见」，
   一旦上层直连，文档控制面将失效。

## 二、决策

**采纳「适配层唯一原则」为一票否决级架构约束，违反即打回重构。**

具体包含五条可执行的约束：

| # | 约束 | 落地机制 |
| --- | --- | --- |
| C1 | 上层只能调用 `/api/v1/...`，严禁以 HTTP / SDK / 源码引用直连底座 | CI 底座直连扫描门禁 |
| C2 | 底座 API 文档仅适配层开发可见，不进入上层代码库与文档 | 文档分发流程约束 |
| C3 | 底座原生 URL / 参数 / 响应结构 / 事件名 / 错误码一律不外泄 | `ErrorMapper` 形态防火墙 + OpenAPI 泄露扫描 |
| C4 | monorepo 中仅 `apps/adapter` 允许出现底座客户端依赖与底座 URL 配置 | CI 唯一出口校验 + 单元测试 AST 校验 |
| C5 | 违反后果：底座替换时将导致大面积重构，与核心设计目标直接冲突 | 交付验收一票否决 |

### 2.1 代码级落点

| 落点 | 职责 |
| --- | --- |
| `apps/adapter/app/clients/dify_client.py` | **全仓库唯一**底座调用出口，集中管理超时/重试/连接池/SSE 解析 |
| `apps/adapter/app/clients/keycloak_client.py` | 身份底座调用出口 |
| `apps/adapter/app/services/*` | **唯一允许**写协议转换的位置 |
| `apps/adapter/app/core/errors.py` 的 `ErrorMapper` | 形态防火墙：下游错误重写为自研错误码 + 业务语言文案 |
| `apps/web/src/lib/api-client.ts` | **前端唯一**适配层调用出口，禁止出现任何底座域名/路径 |

### 2.2 自动化防线

| 门禁 | 位置 | 检查内容 | 失败后果 |
| --- | --- | --- | --- |
| 底座直连扫描 | `dependency-scan.yml` → `base-layer-isolation` | `apps/web`（及未来插件 SDK）中出现 `dify` / `milvus` / `litellm` / `5001` / `chat-messages` / `workflow_run` / `retriever_resources` / `datasets/` / `/v1/` 即失败 | CI 红灯，禁合并 |
| 前端依赖扫描 | 同上 | `apps/web/package.json` 中出现底座 SDK 依赖即失败 | CI 红灯 |
| 唯一出口校验 | 同上 | 底座 URL 只允许出现在 `core/config.py` 与 `clients/dify_client.py` | CI 红灯 |
| OpenAPI 泄露扫描 | `ci-adapter.yml` → `openapi-export` | 对外文档中出现底座术语即失败 | CI 红灯 |
| 业务端点计数 | 同上 | 业务端点数必须恰为 30 | CI 红灯 |
| 能力清单一致性 | `ci-adapter.yml` → `registry-validation` | 注册表声明的 `operations` 与连接器 `SUPPORTED_OPERATIONS` 必须一致 | CI 红灯 |
| 目录树静态校验 | `tests/unit/test_model_service.py` | 底座原生路径只允许出现在 `clients/` 与 `services/` | 单元测试失败 |

### 2.3 契约层保障

除代码扫描外，接口契约本身也做了「去底座化」设计：

| 底座原生 | 自研对外 |
| --- | --- |
| `answer` | `content` |
| `metadata.usage.total_tokens` | `usage.total_units`（业务化口径，附录 A-7） |
| `retriever_resources` | `citations` |
| `indexing_status`（waiting/parsing/cleaning/splitting/indexing/completed/error） | `index_status`（processing/completed/failed 三态） |
| SSE `message` / `agent_message` / `message_file` / `message_end` / `error` | `delta` / `delta` / `citation` / `done` / `error` |
| 工作流节点类型名（`llm` / `if-else` / `code` 等） | 业务语言 `step.title`（由工作流模板配置注入） |
| 真实模型名 | 能力档位 `model_profile`（general / code / long_context / reasoning） |
| 召回参数 `score_threshold` / `search_method` | 封装在适配层配置，不对外暴露（附录 A-3） |

## 三、备选方案

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. 仅靠代码规范文档约束 | 不设自动化门禁，靠 Code Review 把关 | ❌ 否决：Review 易疲劳，且插件第三方贡献无法保证 |
| B. 仅靠运行时网关拦截 | 在网关层禁止上层访问底座端口 | ❌ 否决：源码中仍会出现底座字样，文档与认知泄露无法阻止；且插件离线运行场景无网关 |
| C. 允许上层直连但强制脱敏 | 允许直连，在 SDK 层做字段改写 | ❌ 否决：违反总方案 1.2 第 3 条；且把脱敏责任分散到多处，必然遗漏 |
| **D. 唯一原则 + 多层自动化门禁** | 架构约束 + 代码落点 + CI 门禁 + 契约设计四层防线 | ✅ **采纳** |

## 四、后果

### 4.1 正面

1. 底座可替换性：替换底座时仅需修改 `clients/` 与 `services/`，上层零改动。
2. 技术黑盒化在契约层得到保证，用户界面不出现任何技术概念。
3. 底座 API 文档的分发范围可控，降低信息泄露面。
4. 插件第三方贡献者可依赖稳定契约，无需了解底座细节。

### 4.2 负面 / 成本

1. **适配层是单点**：所有上层流量必经适配层，其可用性直接决定平台可用性
   （≥ 99.5%）。缓解手段：无状态 + 水平扩展（HPA 2-8）+ 统一熔断降级。
2. **多一层协议转换开销**：SSE 转发与 JSON 序列化有额外延迟。
   缓解手段：`first_byte ≤ 1s` 验收指标 + `StreamingResponse` 直出。
3. **新增能力的固定成本**：任何新能力都要先在适配层定义契约再实现。
   这是**有意接受的代价**——契约先行是总方案第四章的执行总原则之一。
4. **门禁本身有维护成本**：新增底座调用点时必须同步更新白名单与测试。

## 五、验证方式

| 频率 | 动作 | 负责角色 |
| --- | --- | --- |
| 每次提交 | CI 底座直连扫描 + 唯一出口校验 | 工程师（自动） |
| 每次合入 develop | OpenAPI 泄露扫描 + 端点计数 | 工程师（自动） |
| 每次发布 | 全链路验证上层零直连 | QA |
| 每季度 | 复核门禁规则是否覆盖新增的底座调用形态 | 架构师 |
