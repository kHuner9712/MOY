## 一、背景

总方案 5.3 规定了开源组件的协议黑白名单：

| 分类 | 协议 | 处置规则 |
| --- | --- | --- |
| ✅ 白名单 | MIT、Apache-2.0、BSD | 可直接商用、可进入核心代码库 |
| ⚠️ 灰名单 | LGPL | **仅可独立进程调用**，不可引入核心代码库 |
| ❌ 黑名单 | GPL、AGPL、SSPL | 禁止引入核心代码库 |

第 6.4 节验收标准 AC-11 要求「开源合规审计 100% 通过，核心代码库无 GPL/AGPL/SSPL 组件；
LGPL 仅以独立进程方式使用」。

平台基础设施层有两个组件踩到了协议边界：

### 1.1 Redis 7 —— SSPL / RSALv2 双许可

Redis 7 起改用 **RSALv2（Redis Source Available License v2）** 与 **SSPL（Server Side Public License）**
双许可。SSPL 属总方案 5.3 黑名单（与 AGPL 同类传染性），RSALv2 未在白名单中明确豁免。
若直接使用 Redis 7.2，将与 AC-11「无 SSPL 风险」直接冲突。

### 1.2 MinIO —— 主线转 AGPL-3.0，且上游仓库已整体下架

MinIO 对象存储在 2021 年后主线版本转为 **AGPL-3.0**（属黑名单）。总方案 2.1 要求对象存储
「S3 兼容，可单机可集群，私有化友好」，而总方案 3.6 要求私有化版本提供完整离线镜像包。

**更根本的问题**：MinIO 官方已停止分发容器镜像并进入维护模式，Docker Hub 仓库整体下架 ——
即使锁定 AGPL 之前的版本线，制品也已无法获取（详见 §2.2）。故最终采用 **SeaweedFS** 替代。

## 二、决策

**采用「协议安全的等价替代 + 版本线锁定 + 独立进程运行」三重策略**：

| 组件 | 决策 | 协议 | 落点 |
| --- | --- | --- | --- |
| 缓存 / 幂等键 | **Redis 7 → 替换为 Valkey 7.2** | **BSD-3-Clause**（白名单） | `valkey/valkey:7.2-alpine`，容器名 `oa-valkey` |
| 对象存储 | **MinIO → 替换为 SeaweedFS 3.80**（MinIO 上游仓库已整体下架，见 §2.2） | **Apache-2.0**（白名单） | `chrislusf/seaweedfs:3.80`，容器名 `oa-milvus-object-store` / `oa-object-store` |

### 2.1 关键论证

| 判据 | 说明 |
| --- | --- |
| **Valkey 替代 Redis** | Valkey 是 Linux 基金会旗下、由 Redis 核心贡献者主导的社区分支，**BSD-3-Clause 永久许可**，API 与 Redis 7 协议兼容。适配层代码仅通过 `redis` Python 客户端以标准 RESP 协议访问（协议接口，非代码链接），**切换不需改动任何业务代码**，仅替换容器镜像与连接地址。 |
| **SeaweedFS 替代 MinIO** | ① **可用性**：MinIO 上游 Docker Hub 仓库已整体下架，任何标签均无法拉取（见 §2.2），**「锁定 AGPL 前版本线」策略的技术前提已不成立**；② **协议**：SeaweedFS 为 **Apache-2.0**（白名单），比原「锁定 AGPL 前版本线」的灰名单处理**更优** —— 无需版本线锁定与灰名单登记；③ **S3 兼容**：提供等价 S3 接口，Milvus（`MINIO_ADDRESS`）与 Dify（`OPENDAL_S3_ENDPOINT`）两处接入点均已联动验证；④ **上游持续维护**，规避了 MinIO 进入维护模式后「安全补丁需自担」的长风险 |
| **镜像可离线获取** | 两个镜像均已固定版本标签，纳入 `deploy/offline/` 的离线镜像包清单（S4 交付），保证私有化断网环境可拉取。**版本标签必须经上游存在性核验后方可写入**（核验方法见 2.3），且**必须经 registry 可拉取性核验**（git tag 存在 ≠ 镜像可拉取，见 §2.2.2）。 |
| **不选其他替代品的理由** | Ceph RGW 引入体量与运维复杂度远超「单服务器一键部署」的私有化交付边界；MinIO 商业版 AIStor 需商业采购，不符合总方案 5.3 开源白名单前提。 |

### 2.2 MinIO 上游仓库整体下架（决策根本变更，QA BLK-03 实测）

> **本节记录一次使原决策技术前提失效的上游变更，是本 ADR 从 v1.1 升到 v1.2 的根本原因。**

**原决策（v1.0/v1.1）**：锁定 MinIO AGPL 之前的最后版本线 `RELEASE.2021-04-22T15-44-28Z`（Apache-2.0），以独立容器运行。

**实测结论（架构师独立复核确认）**：

```
minio/minio:latest                        → HTTP 404（仓库级）
minio/minio:RELEASE.2021-04-22T15-44-28Z  → HTTP 404（仓库级）
GET /v2/repositories/minio/minio/          → HTTP 404（仓库级）
对照组：valkey/valkey → 200，langgenius/dify-api → 200，ubuntu/squid → 200
```

**不是单个标签缺失，是整个仓库在 Docker Hub 不可见。** 上游背景：MinIO 官方自 **2025-10-15** 起停止分发容器镜像
（转为仅提供源码分发），**2025-12-03** 宣布项目进入维护模式，不再提供 Docker 镜像与 RPM/DEB 包。

**因此原决策失效的原因不是协议判断错误，而是「这个版本线的制品在今天的容器分发渠道上已无法获取」**——
法务签字时核验不到对应制品，**签字对象是虚的**。§2.2.1 的标签核验结论（标签存在 + LICENSE 为 Apache-2.0）**依然正确**，
但它只能证明「源码仓库的某个 tag 是 Apache-2.0」，**不能证明「该制品可获取」**。

**方案比较与选型**：

| 方案 | 许可 | 运维成本 | 结论 |
| --- | --- | --- | --- |
| A. 从 MinIO 源码自建镜像 | Apache-2.0 | 中（自建流水线 + 离线包固化） | ⚠️ 技术可行但**否决**：MinIO 已进入维护模式、不再有 CVE 修复，长期持有自建镜像意味着安全补丁全部自担，与总方案 6.4「安全渗透测试无高危中危漏洞」的长效要求冲突 |
| **B. 换 AGPL 合规替代品（SeaweedFS）** | **Apache-2.0** | **低** | ✅ **采纳** —— 换产品而非换标签，但换来的是「上游持续维护 + 协议直接进白名单」的双重改善；改动面限于编排配置与 Dify/Milvus 接入点，**不改业务代码与协议判定** |
| C. 采用 MinIO 商业版 AIStor | 商业许可 | 低 | ❌ 否决：需采购成本，不符合总方案 5.3 开源白名单前提，属商业决策范畴 |

**SeaweedFS 选型证据（三重）**：

| 证据 | 内容 |
| --- | --- |
| 可用性 | `chrislusf/seaweedfs:3.80` → HTTP **200**；`latest` → 200；拉取量 **33,866,599** |
| 协议（registry 元数据） | Docker Hub 仓库 license 字段：`Apache-2.0` |
| 协议（上游 LICENSE 首行） | `https://raw.githubusercontent.com/seaweedfs/seaweedfs/3.80/LICENSE` 首行 = `Apache License / Version 2.0` |

**接入点联动（已落地验证）**：

| 接入方 | 配置项 | 值 |
| --- | --- | --- |
| Milvus | `MINIO_ADDRESS` | `milvus-object-store:8333` |
| Dify（OpenDAL S3） | `OPENDAL_S3_ENDPOINT` | `http://object-store:8333` |
| 容器启动命令 | `server -dir=/data -s3 -s3.port=8333` | S3 网关端口 8333 |

> **待验收**：S3 语义兼容性（分片上传、预签名 URL、bucket 策略、生命周期）需在 Sprint 1 用真实用例回归；
> Milvus 依赖的 `MINIO_ADDRESS` 虽名为 MinIO，实际是 S3 兼容端点，**改名不影响功能**（Milvus 内部沿用该环境变量名）。

### 2.2.2 门禁盲区：git tag 存在 ≠ 镜像可拉取（第三例同型问题）

**问题**：`validate_images.py` 原实现对 `minio/` 前缀特判，走 `_github_tags()`（git tag 校验）而**跳过 registry 校验**。
后果：**在「部署必然失败」的配置上给了 PASS** —— 这正是我上轮报告中「14/14 上游存在性通过」的**错误来源**
（该结论对 minio 而言只验证了源码 tag，未验证镜像可拉取）。

**根因**：把「标签是否存在」与「镜像是否可拉取」当成了同一件事。二者已解耦：
`git ls-remote` 仍能返回完整的 minio tag 列表，但 Docker Hub 仓库已下架。

**修正（本次）**：

1. **删除 minio 特判** —— `source == "github"` 分支在校验 git tag 后**仍须**走 registry 可拉取性校验；
2. **新增 `--self-test` 模式** —— 把 ADR 中记录的历史缺陷固化为**会红的可执行断言**（ADR-0002 §2.2.1 强制要求
   「门禁必须有负样本验证，否则无法区分『门禁有效』与『门禁恒过』」）。当前固化的三个负样本：

| 负样本 | 期望 | 对应历史缺陷 |
| --- | --- | --- |
| `minio/minio:RELEASE.2021-04-22T15-44-28Z` | 判为不可拉取 | 仓库整体下架（§2.2） |
| `squidly/squid:5.2` | 判为不存在 | 合成仓库名（§2.2.2 前身） |
| `valkey/valkey:RELEASE.2021-04-22T23-11-00Z` | 判为不存在 | 合成标签（§2.2.1） |

3. **门禁的判定职责分离**（重要）：`git tag` 校验回答「版本号是否是拼错的」，registry 校验回答「制品能不能拿到」。
   **两者都必须通过**，缺一即判 FAIL。

**这一问题的普适性**：三次同型缺陷（合成标签、合成仓库名、仓库下架）**全部是「引用了看起来合理但未核验的镜像」**。
根因一致：凭印象填镜像名 + 凭单一手段核验。**作业规范第 1 条因此扩展为：标签存在性与可拉取性必须双证，
且两者须来自不同的核验通道（源码侧 / 分发侧）。**

> ⚠️ **本节记录一次已发生的引用错误及其纠正过程，作为后续「镜像标签引用」的唯一作业规范。**

**已发生错误（V1.0 初稿）**：初稿引用 `minio/minio:RELEASE.2021-04-22T23-11-00Z`，声称其为「AGPL 之前的最后版本线」。
该标签为**日期与时间戳交叉拼接产物**——`2021-04-22` 取自 `RELEASE.2021-04-22T15-44-28Z` 的日期部分，
`23-11-00Z` 取自 `RELEASE.2021-04-06T23-11-00Z` 的时间戳部分，两者组合**从未在上游存在过**。
该错误由 QA（严过关）在 Sprint 0 复核中以 `git ls-remote` 实测发现并报告，**属 P0 级**：标签拉不到 →
`milvus-minio` 容器起不来 → Milvus 依赖失败 → 私有化一键部署直接失败。

**纠正后标签**：`RELEASE.2021-04-22T15-44-28Z`

**上游核验证据（`git ls-remote --tags https://github.com/minio/minio.git`）**：

| 标签 | 协议 | 说明 |
| --- | --- | --- |
| `RELEASE.2021-04-06T23-11-00Z` | Apache-2.0 | 04-22 之前最近的候选，易被误拼接 |
| `RELEASE.2021-04-18T19-26-29Z` | Apache-2.0 | AGPL 前版本线 |
| **`RELEASE.2021-04-22T15-44-28Z`** | **Apache-2.0** | ✅ **AGPL 前的最后一个版本线，本决策采用** |
| `RELEASE.2021-05-11T23-27-41Z` | AGPL-3.0 | AGPL 起点，不可采用 |
| `RELEASE.2021-05-16T05-32-34Z` | AGPL-3.0 | 不可采用 |

**强制作业规范（后续任何镜像标签引用均适用）**：

1. **先核验，后引用**：任何镜像标签写入文档或编排文件前，必须先执行 `git ls-remote --tags <repo>`（GitHub 源）
   或 Registry API（Docker Hub / quay 源）确认标签真实存在；**严禁凭记忆或按日期规律推造标签字符串**；
2. **存在性 + 协议双证**：标签存在性（`git ls-remote` 或 Registry API）**与** 协议归属
   （取该 tag 的 LICENSE 首行）**两项证据同时具备**，方可判定为白名单；
3. **门禁必须精确匹配**：CI 门禁**不得使用前缀正则**（`minio/minio:RELEASE\.2021-04-22` 会对合成标签
   同样判 PASS，给错误配置签发合规通行证），须改为**精确标签匹配 + 存在性校验**，
   并引入 `deploy/images.lock` 清单作为唯一事实来源（见 2.4）；
4. **法务签字对象必须是可拉取制品**：ADR 状态从「待法务签字」转为「已签字」的前置条件是
   **镜像可拉取性实测通过**，而非仅凭文档声明——否则签字对象是虚的。

### 2.2.1 同型问题第二次出现：`squidly/squid` 仓库不存在

在落实 2.4 门禁并**实跑**该门禁时，发现了**同型问题的第二例**——这恰好验证了门禁的价值：

| 项 | 内容 |
| --- | --- |
| 问题 | 编排文件与 `deploy/offline/README.md` 引用 `squidly/squid:5.2`（作为 GPL-2.0 灰名单项），但**该仓库在 Docker Hub 上根本不存在**（实测连 `latest` 均为 404）。该引用同样来自「看起来合理但未经核验」的写法，与 MinIO 合成标签同源 |
| 发现方式 | 门禁实跑时 `squidly/squid:5.2` 报「上游不存在」——**若无门禁，此问题会一直潜伏到首次私有化部署失败** |
| 纠正 | 更换为 Canonical 官方维护的 `ubuntu/squid:5.2-22.04_beta`（squid 5.2 / Ubuntu 22.04，标签已核验存在，HTTP 200），协议仍为 GPL-2.0，仍按灰名单「独立进程调用」处理 |
| 附带修正 | Docker **官方镜像**（`postgres` 等）在 Hub 上实际托管于 `library/` 命名空间，但允许省略前缀引用。校验脚本未做归一化会把 `postgres:16-alpine` 误判为「不存在」→ 已在 `validate_images.py` 中增加 `_normalize_repo()` 归一化 |

**结论与规范升级**：

1. **「未经核验的镜像引用」是系统性风险，不是孤例**。两次问题均出在「写文档/编排时凭印象填镜像名」。
   故作业规范第 1 条（先核验后引用）**适用于所有镜像，不限于 MinIO**；
2. **门禁必须有负样本验证**：门禁上线后必须用「已知不存在的标签」验证其确实判 FAIL，
   否则无法区分「门禁有效」与「门禁恒过」。本次已实测三个负样本（合成 MinIO 标签 / 不存在的 squid 仓库 /
   lock 与 compose 不一致），全部正确判 FAIL；
3. **门禁本身的实现缺陷也要实测**：本轮实跑还发现门禁脚本把「网络受限（401）」与「标签不存在（404）」
   混为一谈 —— 若不修正，在受限网络环境下 CI 会全线飘红，门禁将被团队忽略而失去防护作用。
   已改为三态返回（存在 / 不存在 / 环境受限），仅 404 判 FAIL。

### 2.3 一致性保障

| 保障机制 | 落点 |
| --- | --- |
| 镜像标签固定（禁止 `latest`）+ 精确标签 | `deploy/docker-compose.yml`、`deploy/docker-compose.saas.yml`，标签取值以 `deploy/images.lock` 为唯一事实来源 |
| 镜像标签**存在性校验**（P0 门禁） | `.github/workflows/dependency-scan.yml` → `sca-scan` job：精确标签匹配 + 存在性校验，缺失即红灯（**Sprint 1 落地**） |
| SCA 协议扫描 | 同上 job，协议黑名单判定失败即红灯 |
| 依赖文档同步门禁 | 同上 job「依赖版本约束落在架构文档 8 章清单内」，Sprint 1 扩展为「包名 + 版本约束双校验」 |
| Valkey 健康检查命令静态校验 | 同上 job：compose 中 Valkey 服务的健康检查命令须为 `valkey-cli`（见 2.5 风险具体化） |
| 架构文档登记 | 架构文档 8.2 节 + 第 2.1 节选型表已登记 Valkey / MinIO 版本线 |
| 交付文档声明 | `docs/api/README.md` 第六节、`deploy/.env.example`、`deploy/offline/README.md`、产品 About 页与开源声明文件（总方案 5.3-4） |

### 2.4 镜像清单单一事实来源（`deploy/images.lock`，Sprint 1 落地）

**问题**：当前镜像标签散落在 4+ 个编排文件与文档中，任一处漂移即部署失败或合规判定失真。

**方案**：新增 `deploy/images.lock`，作为所有基础设施镜像的**唯一事实来源**，结构示例：

```yaml
# 基础设施镜像锁文件 —— 唯一事实来源
# 规则：tag 必须精确匹配、必须经存在性核验、禁止 latest、禁止任何合成标签
images:
  - name: chrislusf/seaweedfs
    tag: 3.80
    license: Apache-2.0
    role: S3 兼容对象存储
    note: 替代已下架的 minio/minio；Apache-2.0 白名单，独立容器运行
  - name: valkey/valkey
    tag: 7.2-alpine
    license: BSD-3-Clause
    role: 缓存/幂等键
```

**CI 校验规则**：`docker-compose*.yml` 中出现的每个 `image:` 引用**必须**能在 `images.lock` 中找到
`name:tag` 精确匹配项，否则红灯。同时校验：`images.lock` 中每个 tag 的**上游存在性**
（Registry API 或 `git ls-remote`）。

> **镜像层风险高于代码依赖层**：代码依赖违规会被 SCA 扫出来；**镜像标签拼错则 CI 全绿、部署才炸**。
> 因此本门禁的优先级高于「包名也在清单内」的文档同步增强。

**存在性校验的方法选型（实测结论，Sprint 1 实现依据）**

| 方法 | 适用镜像源 | 实测结果 | 结论 |
| --- | --- | --- | --- |
| `git ls-remote --tags <github-repo>` | GitHub 源 | ✅ 可用，能检出「日期×时间戳交叉拼接」的合成标签 | **用于版本号校验，但不能替代 registry 校验**（见 §2.2.2） |
| Docker Hub Registry API（`/v2/<repo>/manifests/<tag>` + token） | Docker Hub 源（valkey/valkey、milvusdb/milvus 等） | ⚠️ **在部分企业网络环境下被策略阻断**（实测：连 `latest` 均返回 401，`hub.docker.com/v2` 与 `registry-1.docker.io/v2` 同此） | **必须做降级** |
| `docker pull` | 全部 | ⚠️ 需 Docker daemon；CI agent 与开发机可能未运行 daemon | 兜底手段，非首选 |

**实现要求**：

1. **按镜像源分别选择方法**：GitHub 源镜像走 `git ls-remote`；Docker Hub 源镜像走 Registry API；
2. **Registry API 必须有降级路径**：当 API 因网络策略不可用时（表现为**任意标签都返回 401**，
   而非仅不存在的标签 404 —— 二者必须区分，否则会把"网络受限"误判为"标签不存在"），
   **降级为「跳过在线存在性校验 + 依赖 `images.lock` 白名单 + 记录警告」**，不得直接判 FAIL；
3. **网络受限与标签不存在的区分是硬要求**：404 = 标签不存在（**判 FAIL**）；401/超时/连接错误 = 环境受限（**降级放行 + 警告**）；
   误判会导致 CI 在受限网络下全线飘红，门禁将被团队忽略，反而失去防护作用；
4. **离线模式**（私有化断网流水线）：`images.lock` 中已核验条目视为通过。

### 2.5 Valkey 边缘命令差异的风险具体化

初稿将「Valkey 边缘命令差异」列为泛化风险，经与 QA 复核后**具体化**为可落地检查项：

| 项 | 结论 |
| --- | --- |
| 服务端命令兼容性 | ✅ `docker-compose.yml` 实际用到的 `redis-server --requirepass --maxmemory` 等启动参数与 `PING` 等基础命令，Valkey 7.2 与 Redis 7 **完全兼容**，无差异风险 |
| **客户端二进制名（真实风险点）** | ⚠️ Valkey 官方镜像内的客户端二进制名为 **`valkey-cli`**，**不存在 `redis-cli`**。当前 compose 健康检查已正确使用 `valkey-cli`（`deploy/docker-compose.yml:71`），**但这是当前恰好写对**——若后续有人参照 Redis 文档改写为 `redis-cli`，在纯 Valkey 镜像中会**直接失败**（command not found），且失败信息与合规问题无关，极易被误判为环境问题 |
| 强制措施 | ① CI 增加静态校验：compose 中 Valkey 服务的 `healthcheck.test` 若含 `redis-cli` 即红灯；② 架构文档 9.5 环境变量与运维约定中登记「Valkey 服务健康检查一律用 `valkey-cli`」 |

## 三、备选方案

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. 直接使用 Redis 7 + MinIO 主线 | 零改造 | ❌ 否决：SSPL 与 AGPL 均触黑名单，AC-11 必然不通过；且 MinIO 制品已不可获取 |
| B. Redis 7 独立进程 + MinIO 锁版本 | Redis 走灰名单范式，MinIO 锁版本 | ⚠️ 部分采纳：Redis 侧因 Valkey 为协议兼容的 BSD 替代品，无额外成本，不采用 SSPL 灰名单范式；**对象存储侧该方案已因制品下架失效** |
| C. Redis 7 商业许可（RSALv2 商业授权） | 付费获取授权 | ❌ 否决：需法务采购流程，私有化客户二次分发场景授权边界不清，交付成本高 |
| D. 引入新缓存/存储组件（KeyDB / Ceph / SeaweedFS） | 换用其他实现 | ❌ 否决：KeyDB 为 SSPL；Ceph 体量与运维成本超边界；SeaweedFS 为 Apache-2.0 但 S3 语义兼容性与运维熟悉度不足 |
| **E. Valkey 替代 + SeaweedFS 替代 MinIO** | 双组件均直接落入白名单协议（BSD-3 / Apache-2.0），无灰名单登记、无版本线锁定 | ✅ **采纳** |

## 四、后果

### 4.1 正面

1. AC-11「核心代码库无 GPL/AGPL/SSPL 组件」在基础设施层同样成立，合规审计无遗留项。
2. Valkey 为协议兼容替换，业务代码零改动，无迁移成本。
3. 镜像标签固定，离线包可重现、可校验。

### 4.2 负面 / 成本

1. **换用 SeaweedFS 需回归 S3 语义兼容性**（分片上传、预签名 URL、bucket 策略、生命周期）—— 列入 Sprint 1 回归项；Milvus 侧 `MINIO_ADDRESS` 环境变量名沿用 MinIO 命名，**改名不影响功能**（Milvus 内部沿用），无需改 Milvus 镜像。
2. Valkey 与 Redis 在少数边缘命令上存在行为差异（当前适配层仅用 GET/SET/SETNX/EXPIRE/INCR 等通用命令，无差异风险；若未来使用 Lua 脚本或 Stream 需重新评估）。**客户端二进制名为 `valkey-cli` 而非 `redis-cli`**，已由 CI 静态校验守护（见 2.5）。
3. **`images.lock` 引入额外的清单维护成本**：新增/升级任一基础设施镜像须同步三处（`images.lock`、compose 引用、ADR 8 章登记），漏改即 CI 红灯。
4. **镜像标签存在性校验依赖外网**（Registry API / `git ls-remote`）：私有化断网环境的 CI 需提供**离线白名单模式**（`images.lock` 中已核验条目视为通过），否则该门禁在离线流水线中无法运行。
3. 长期维护成本：需持续跟踪 Valkey 与 SeaweedFS 版本状态，列入月度 SCA 与版本巡检。SeaweedFS 上游持续维护，**规避了 MinIO 维护模式下安全补丁自担的长风险**。

### 4.3 遗留

| 项 | 处理 |
| --- | --- |
| SeaweedFS 镜像的 CVE 人工核查 | S4 离线包制作清单新增条目（上游持续维护，风险低于 MinIO 锁版） |
| Valkey 边缘命令差异 | 适配层 Redis 客户端使用命令清单登记，超出清单需架构评审；健康检查命令固定为 `valkey-cli` |
| 法务/合规最终签字 | **待主理人协调**（见第五节） |
